# Algorithms survey: modern methods per hot path

*Status: survey, 2026-10-24. Written for the owner directive of the same date: "new methods and math approaches for some of these tasks may have been discovered since the original implementations ... see if we can use those new algorithms by implementing for this platform." Nothing here is adopted yet; each row is a candidate for a phase brief (`docs/process.md`, Hardware features and State-of-the-art items).*

**How to read it.** Each table row gives what the code does today (file:line, checked in this tree), the state of the art with a citation, a judgement of fit for the PP5022 (two ARM7TDMI cores: no FPU, no ARMv5E DSP ops, SMULL/SMLAL available, 8 KB cache each, branches and unaligned/byte loads expensive), the core that suits it, the roadmap phase, and a priority (H/M/L/none).

**Evidence honesty.**
- **[fetched]** means I read the cited page during this survey.
- **[search]** means a search result summarised it but I did not read the primary text.
- **[memory]** means it is from my own knowledge of the literature; the citation is given so it can be checked, but I did not re-verify it here. Treat every [memory] gain figure as an estimate to be measured, not a promise.
- No gain figure below is measured on a PP5022. Per `docs/process.md`, each adopted item needs a before/after on the device (or the instruction-count benchmark in the sim) before it ships.

**Short verdict.** The decode paths (FLAC, MP3, Vorbis, AAC) were already tuned in ARM assembly by Rockbox developers for exactly this CPU class and are at or near the state of the art for an ARM7TDMI; the largest honest wins are in the **non-codec** paths: sample-rate conversion quality (19-13), library-side data work (sorting, hashing, compression of blobs), JPEG for album art, and a few UI primitives. Time-stretch is the one place where newer research changes the quality picture materially, but only a cheap SOLA/WSOLA refinement fits the CPU.

Core key: **CPU** = PP5022 CPU core, **COP** = PP5022 second core (the front-end/UI core under `front-end-back-end-cores`), **VC** = BCM2722 vector unit (`docs/bcm2722-reference/`), **sync** = on-device sync-time work (after USB, in a maintenance window; never while browsing). There is no host or sync app in the product (mission: drag-and-drop, firmware-only fixes); a Mac-side tool may only be a developer convenience, never required.

## 2. DSP

| Area | Today (file:line) | State of the art (citation) | Fit and expected gain | Core | Phase | Priority |
|---|---|---|---|---|---|---|
| Sample-rate conversion | 4-point Hermite, `resample_hermite()` (`lib/rbcodec/dsp/resample.c:100`), ARM asm in `dsp_arm.S`; ratios in `docs/design/resample-plan.md` | Half-band polyphase FIR: one polyphase branch is a pure delay, roughly 50% fewer MACs than a plain FIR [search: MathWorks and an audio-SRC patent]; cascaded halves for /4, /8; Julius O. The only genuinely newer idea (soxr's) is for arbitrary ratios, which this product never needs. Keep the plan as is. | CPU (asm) | P19 (19-13) | **H** |
| Time-stretch (audiobook speed) | SOLA with cross-correlation search: `lib/rbcodec/dsp/tdspeed.c` (`tdspeed_apply` at `:174`; fixed buffers `FIXED_BUFCOUNT 3072` at `:44`); wired in `apps/ipodui/ab_speed.c` | WSOLA (Verhelst and Roelands, ICASSP 1993) [search: ISCA Eurospeech 1993]; cost is dominated by the normalised cross-correlation search, which can be cut 40-56% by restricting the window around a pitch estimate [search: GIST 2010; Korean 2012 paper]; Signalsmith Stretch (2022-2023, MIT) is an STFT phase-prediction stretcher, best at 0.75-1.5x, quality comparable to Rubber Band [fetched, design article; README via search]. Rubber Band v4.0 (Oct 2024) added the R3 engine [fetched, news only]; its internals were not retrievable here. | Speech at 0.75-2x is exactly where time-domain methods are best: they preserve transients and cost a few correlation passes. | EQ biquads | Software biquads `dsp/eq.c`, coefficients `dsp_filter.c:136 filter_pk_coefs` (s5.26 fixed point); hardware WM8758 EQ for presets (P15) | Direct-form-I with error feedback / noise shaping; transposed DF-II has worse fixed-point noise [memory: Dattorro, JAES 1997 "Effect design"]; Cytomic (Andrew Simper) state-variable filter for good modulation behaviour [memory] | Software EQ is only for custom curves (P12). Biquad cost is 5 MACs/sample/band; with 5 bands and two channels at 44.1 kHz that is 2.2 M MAC/s, a few percent of CPU. Already adequate; hardware EQ covers the common case. | CPU | P12 | none |
| Dither and noise shaping | TPDF-ish random plus a 3-tap error feedback in `dsp_sample_output.c:105-134` | Gerzon-Craven noise shaping (JAES 1989) and Wannamaker's optimal-weighting shapers (1992) [memory]; "psychoacoustically optimal" 9-tap shapers (e.g. SoX `-D`, `dither` filters) | The 3-tap shaper is the standard cheap design. Better shapers cost more taps for an inaudible gain on a headphone DAC at 16 bits. | CPU | none | none |
| Crossfeed | Meier / custom IIR in `crossfeed.c` | Bauer stereophonic-to-binaural (1961) and Meier / Linkwitz and Chu-Moy are the standard; no newer low-cost method I know of | Off by default for the 7G look (hidden setting). | CPU | none | none |
| ReplayGain / Sound Check at sync time | Gains applied in `dsp_misc.c:39-108`; Sound Check hardware path in `apps/ipodui/sc_hw.c` (loudness from tags) | ITU-R BS.1770 (-4, 2015; -5, 2023) K-weighting + gating, EBU R128 (2014) and EBU Tech 3341/3342; reference code `libebur128` (MIT) [search]; a note from De Man et al., AES Conv. 145 [search] that filter equations are absent from the standard | Do this at **sync/build time on the host** (`scripts/prokbox-library.py`) with `libebur128` or the Python `pyloudnorm`, never on the device: it is the same two biquads plus 400 ms block power, trivially cheap but the file must be decoded once, which costs minutes per 1 TB library on the PP5022. ## Ranked top 15

Ranked by (expected benefit to the owner's mission) x (confidence) / (cost and risk). Priorities **H** are worth a brief; **M** worth a probe or a spike; **L** is opportunistic.

| Rank | Item | Why | Phase |
|---|---|---|---|
| 1 | **Half-band / polyphase sample-rate conversion** (19-13) | Established method, planned, removes aliasing in hi-res FLAC and images in audiobooks, cost at or below Hermite | P19 |

| 14 | **STFT stretcher (Signalsmith / Rubber Band R3 style) on the VC as a research spike** | Higher quality at extreme speeds, but breaks dark-playback (needs the BCM awake); a spike, not a plan | P19 spike |
| 15 | **xxHash32 or slicing-by-4 CRC for any future bulk checksum** | Only for new bulk-verify features (art pack verification); do not touch existing keys | when needed |

## Don't bother

- **Switching the MP3, Vorbis or Opus decoders.** libmad and Tremor are the fixed-point references and already have ARM assembly for this CPU class; Helix is encumbered by RCSL/RPSL; minimp3 and libopus 1.5 DNN features are float or NEON/AVX work for CPUs we do not have [search].
- **Opus Deep PLC / DRED.** Loss concealment for streaming; local files never lose packets, and the NN inference is far beyond the PP5022 [search].
- **FNV to xxHash/wyhash.** FNV-1a on 20-60 byte names is already within a small factor, and a change invalidates every stored art and book key for no user-visible gain [fetched xxHash page: small-input gains come from inlining, not from the core hash].
- **Slicing-by-8/16 CRC on the device.** 8-16 KB of tables against an 8 KB D-cache would evict hot data; the current CRCs are over short inputs.
- **Switching Rice decoding to multi-symbol tables.** Upstream FLAC *removed* its decoder asm in 2022 as a small benefit [fetched]; the Rockbox ARM path is tuned already.
- **Dual Kawase blur.** Its advantage is GPU texture bandwidth [search]; the running-sum box blur on a downscaled plane is already O(1) per pixel.
- **CORDIC for trig.** A table and one multiply beats 16 shift-add iterations on this CPU.
- **Tickless kernel / deadline scheduler.** The tick is not the power cost; the risk to clickwheel and audio timing is real.
- **Custom noise shapers beyond the existing 3-tap.** An audible gain needs more taps; on a 16-bit headphone DAC it is inaudible.
- **zstd on device.** Needs a window of tens of KB for a size win that I/O does not need [search].
- **STFT time-stretch on the CPU.** FFT sizes of 2-4k points per channel at 24-80 MHz do not fit the dark-playback clock.
