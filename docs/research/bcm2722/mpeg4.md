# MPEG-4 Part 2 Simple Profile: plan and feasibility

Issue #60 / #64. **Status: plan only, no code.** H.264 Baseline is built, bit-exact and on its way to the device (`decoder.md`, `player.md`). This is the second codec Apple's firmware played, and the one many older iTunes-era and drag-and-drop `.mp4`/`.m4v` files use.

## 1. What the 5.5G played

From Apple's 5G/5.5G technical specifications; the figures are from memory, marked ≈, and should be checked against Apple's published spec page before the brief quotes them:
- **MPEG-4 video,** Simple Profile, up to **2.5 Mbps** ≈, **480×480** ≈ at 30 fps (the 5G spec), and **640×480** ≈ on later 5.5G spec sheets, with AAC-LC audio in `.m4v`, `.mp4` and `.mov`.
- **H.264** (already built): Baseline, up to 768 kbps at 320×240 and up to 1.5 Mbps at 640×480 (Low-Complexity).
- Apple's own decoder exists as `mpg4dec.vll` (236 functions, the same shape as `h264dec.vll`: control code around vector kernels; `approach.md`). That's the proof it fits the hardware. It's reference only; none of its code is used.

**Target:** the same envelope. Simple Profile only (no Advanced Simple: no B-VOPs, quarter-pel, GMC or interlace), up to 640×480 and 2.5 Mbps, scaled to the 320×240 panel by the existing display path.

## 2. What Simple Profile needs

| Tool | In SP | Notes |
|---|---|---|
| I-VOP, P-VOP | yes | no B-VOPs |
| Short header (H.263 baseline mode) | yes | the same decoder with fixed tables; cheap to include |
| 8×8 DCT, H.263 quantisation | yes | SP has no MPEG quantisation matrices (`quant_type` 0) |
| Intra AC/DC prediction | yes | per-block direction from the DC gradients |
| Half-pel MC with rounding control | yes | bilinear; `vop_rounding_type` alternates per P-VOP |
| 4MV (inter4v) and unrestricted MVs | yes | edge extension of the reference, as H.264's MC already does by clamping |
| Resync markers | yes | must parse; concealment on errors |
| Data partitioning, reversible VLC | yes (error resilience) | rare in practice; parse them, or refuse cleanly at first |
| In-loop deblocking | **no** | the biggest saving next to H.264 |
| Post-processing (deblock/dering) | optional, out of loop | not for bit-exactness; a later quality option |

**The bit-exact trap:** MPEG-4 Part 2's IDCT is defined only to an accuracy bound (IEEE 1180), not bit-exactly. So unlike H.264, two conforming decoders can differ by ±1, and the error drifts through P-VOPs until the next I-VOP. **Our oracle is ffmpeg with `-idct simple`** (its `simple_idct`, the integer IDCT most encoders and decoders match). Our C and vector IDCT must reproduce it bit for bit, so the existing bit-exact test harness carries over unchanged.

## 3. Feasibility on our VPU at 150 MHz

**The budget:** 150 MHz ÷ 30 fps = 5.0 M cycles per frame. 4b in session 7 confirmed the clock: all 69 kernels ran 5.56 times faster at 150 MHz.

**What carries over from the H.264 decoder (`bcmfw/h264`):**
- **The bit reader** (`h264_int.h`) and the generated row-word VLC table scheme (`gen_tables.py`): MPEG-4's TCOEF, MCBPC, CBPY and MVD tables fit the same generator.
- **MC:** the H.264 eighth-pel chroma kernel is a bilinear filter. Half-pel MPEG-4 MC is the same shape, (a+b+1−r)>>1 and (a+b+c+d+2−r)>>2 with rounding control r. That's a small new set of vector kernels generated by `gen_vpu.py`, with 16×16, 8×8 (4MV) and chroma 8×8 blocks. Edge clamping is reused.
- **Arena, frame stores, reference handling** (one reference, simpler than the DPB), and the display path: YUV→RGB565 on the VPU, scaling, DMA push.
- **The session layer:** `hostproto` codec 2 (`HP_CAP_MPEG4_SP`) is already reserved (`hostproto.md`). FIFO, STATUS, A/V sync and the PP player don't change.
- **Device-verified vector rules** apply as they are: the store layout, `vmulhrs` with no clamp, ties rounding away from zero, and `vadds` clamping (`isa.md`).

**What's new:**
- **8×8 IDCT,** row/column with `simple_idct`'s constants and shifts. Two 8×8 blocks fill a 16-lane row group, so one call handles a pair, the same layout trick as the 4×4 kernels.
  - **Rounding:** `simple_idct` rounds with explicit adds before shifts, so the tie-rounding behaviour of `vmulhrs` must be avoided: use `vmul` + add + shift, or prove each rounding site is never a tie.
- **AC/DC prediction:** scalar, per block: a few comparisons and a 7-coefficient row or column copy.
- **VOL/VOP header parsing,** resync and video packet headers.

**Instruction estimate per frame** (≈, from H.264's measured profile; `decoder.md` "Per-stage profile"):
- H.264 on the iPod clip is about 5,500 instructions per macroblock with vector kernels: 1.66 M a frame at 320×240 (300 MBs). Deblocking was about a quarter of the scalar total, and SP has none.
- **Per macroblock (est.):**
  - parse 1,500–2,500, rising with the bitrate;
  - MC 600–900 (bilinear is cheaper than the 6-tap);
  - IDCT and add 400–600 (6 blocks, 3 vector pairs);
  - control and prediction about 800.

  That gives **about 3,300–4,800 a macroblock.**

| Size | MBs | Estimate (M instr/frame) | Share of 5.0 M at 150 MHz |
|---|---|---|---|
| 320×240 | 300 | 1.0–1.4 | 20–30% |
| 480×480 | 900 | 3.0–4.3 | 60–85% |
| 640×480 | 1,200 | 4.0–5.8 | 80–115% |

**Verdict: feasible** for everything up to 480×480, with room to race to idle at 320×240. **640×480 at 2.5 Mbps is marginal,** like H.264's 640×480 I-frames (`decoder.md`). The parse cost at the top bitrate decides it, so it gets measured first (step 2 below). Fallbacks, in order: a vectorised coefficient unpack, then dropping frames gracefully (the player already drops whole GOP tails), then documenting 640×480 SP as best-effort.

## 4. Source baseline and licensing

- **Our own C, clean-room from the standard** (ISO/IEC 14496-2), structured like our H.264 decoder: same arena, same kernel interface, same tests.
- **Structure references, read but not copied wholesale:** ffmpeg's `mpeg4videodec.c`, `h263dec.c`, `mpegvideo*.c` and `simple_idct` (LGPL 2.1+, GPL-compatible), and Xvid (GPL v2+, compatible). If any table or function is ported, keep its copyright header and licence (`hostproto.md` §10 lists the H.264 files from memory; the same rule applies: pin a release tag and verify the files and licences before porting).
- **Rockbox's own `libmpeg2`** (mpegplayer, GPL) has an MPEG-1/2 IDCT and MC already. Its IDCT isn't `simple_idct`, so it isn't the bit-exact reference, but its MC structure is a useful second reference.
- **Patents:** MPEG-4 Part 2 Visual patents have largely expired, ≈ (the MPEG LA pool's last listed patents ran out around the late 2020s; check before any commercial release, per the owner's product question). For a personal firmware this doesn't change anything.

## 5. Container and player changes (ARM side)

- **Sample entry `mp4v`:** `mp4demux.c` currently refuses with `MP4_E_NO_AVC`. It needs to accept `mp4v` and read `esds` (ES_Descriptor → DecoderConfigDescriptor, objectTypeIndication 0x20 = MPEG-4 Visual → DecoderSpecificInfo).
- **DecoderSpecificInfo** holds the VOS/VO/VOL headers (start codes `000001B0`/`B5`/`00`/`20`). They're sent first after every `OPEN`, exactly where the H.264 path sends SPS/PPS.
- **No Annex B rewrite:** Part 2 samples are VOP start-code streams already (`000001B6`), so each sample goes into the FIFO as it is. That's simpler than H.264's length-to-start-code rewrite.
- **`.vix`:** add a codec field to the header, or a version bump (`vix.h`), so the player picks codec 2 in `OPEN`. Key frames come from `stss`, as for H.264, or from VOP type if `stss` is missing (every VOP an I-VOP is legal).
- **The Python oracle** (`tests/video/mp4demux.py`) gets the same changes first; the C port must stay byte-identical, as today.
- **Classification:** `mp4v` counts as video (`shell-contract.md` §4).

## 7. Order of work

1. **Container:** `mp4v`/`esds` in the Python oracle, then the C demuxer, `.vix` codec field, and tests (ARM side; no device).
2. **Measure first:** a scalar C decoder for I-VOPs only (headers, TCOEF, AC/DC prediction, IDCT), compiled with `vc2cc` and profiled in `vc2sim` on `m_iframes_q2` and `m_vga_2500k`. This answers the 640×480 parse question before any kernel work.
3. **P-VOPs:** MC in C, 4MV, rounding control, unrestricted MVs. Bit-exact on the whole corpus with the C kernels.
4. **Vector kernels:** paired 8×8 IDCT + add, then half-pel MC, each against its C reference in `vpu_test.py` style, using only device-verified forms (`forms_test`).
5. **Image integration:** `hostproto` codec 2 and `HP_CAP_MPEG4_SP`, `video_test.py` end to end, the stage 6 clip variant.
6. **Error resilience:** resync concealment, data partitioning and RVLC (or a clean refusal), plus a fuzzed-input test that must never hang the image.

## 8. Device checks needed

- **Stage 6 with an MPEG-4 clip:** pacing, A/V sync, the decode time per frame at 150 MHz for 320×240 and 640×480 (`STATUS` words 13–15).
- **New vector forms** the IDCT and MC kernels use that aren't device-verified: a bench check per form, informational on its first run, the same pattern as the H.264 checks in sessions 6–7.
- **Thermal and power at 2.5 Mbps,** 640×480 sustained: run alongside a power-log A/B (`hardware.md`, "Rundowns and A/B tests").
