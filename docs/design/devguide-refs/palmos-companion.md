# Palm OS Programmer's Companion (Volume I, document 3004-006-HW, 18 April 2003, and Volume II "Communications", same release; PalmSource, Inc.; HTML edition from the Palm OS 5 SDK documentation set)

Source used: the Wayback Machine capture of PalmSource's developer documentation site,
`http://web.archive.org/web/2003id_/http://www.palmos.com:80/dev/support/docs/palmos/` (pages
`CompanionTOC.html`, `Companion2TOC.html`, `CompanionAbout.html`, `Companion2About.html`,
`Companion_Front.html`, `CompanionIX.html` and the chapter pages). The HTML was generated by
Quadralay WebWorks Publisher from the printed/PDF master, so headings, numbering and captions
match the book; page numbers become hyperlinks. Local copy in `refs/palmos-companion/` (HTML plus
stripped `.txt`). The title page credits two writers and some fifteen engineering contributors.

Read in full: the front matter and "About This Document" for both volumes, the complete
Volume I and II contents, chapters 1 (Programming Palm OS in a Nutshell), 3 (Event Loop),
5 (Memory) and 12 (Debugging Strategies). Read in part: chapter 2 (Application Startup and
Stop), chapter 10 (Palm System Support: reset, power modes, microkernel, ARM-native code),
Volume II chapter 5 (Serial Communication: hardware, byte order, tips, common errors) and the
Volume I index. The Companion has no appendices or glossary of its own (see Structure).

Relevance: this is a conceptual "how-to" guide for application programmers sitting on top of
an OS, so it maps most directly onto our **games SDK guide** and **firmware guide**, with some
pages (resets, power modes, troubleshooting) that suit the **user guide**. It is weak as a model
for register-level hardware references.

## Structure

The Companion is one half of a deliberate pair. The SDK's "About This Document" table lists four
books: the *API Reference* (every function and structure), the *Companion* (concepts and
how-to), a resource-editor guide and a development-tools guide. The Companion never repeats
function prototypes; it explains and then points.

The front matter says the volume is built for random access: any chapter can be read in any
order, though the first three are aimed at newcomers. Each chapter ends with hyperlinks into
the Reference.

**Volume I** (13 chapters, then Index):

1. Programming Palm OS in a Nutshell: why handheld programming differs (screen, quick
   turnaround, PC sync, input, power, memory, no file system, backward compatibility);
   programming concepts; API naming conventions; integrating with the system; writing robust
   code; creator IDs; running on different devices; tools; where to go next.
2. Application Startup and Stop: launch codes, normal launch, launching other apps, stopping,
   notifications, helper services; summary tables of launch codes and notifications.
3. Event Loop: the application loop; low-level event management (handwriting, key, pen and
   system event managers).
4. User Interface: by far the longest; drawing, high-density displays, forms and dialogs, each
   control type, menus, tables, lists, bitmaps, colour, launcher integration.
5. Memory: hardware background, memory architecture, heaps, the Memory Manager, performance.
6. Files and Databases: Data Manager, Resource Manager, file streaming.
7. Expansion: slots, file systems, VFS and Expansion managers, card insertion, volumes, files,
   directories, custom calls, debugging.
8. Text: characters, strings, fonts.
9. Attentions and Alarms.
10. Palm System Support: features, preferences, sound, boot and reset, ARM-native functions,
    power modes, microkernel, serial number, time, floating point.
11. Localized Applications.
12. Debugging Strategies: error-manager macros and the try/catch mechanism.
13. Standard IO Applications.

**Volume II, Communications** (10 chapters, then Index): object exchange; exchange libraries;
personal data interchange; beaming; serial communication; Bluetooth; network communication;
SSL; internet and messaging applications; telephony.

**Back matter.** Each volume ends with an index only. There is no glossary and there are no
appendices: the compatibility appendix, the per-event reference and the error-code tables all
live in the separate *API Reference*, and the Companion cites them there (sometimes down to a
table and page number in the other book).

## How one block or topic is laid out: Chapter 3, "Event Loop"

1. **Chapter mini-contents.** The page opens with the chapter's own section list (two heading
   levels), each entry a link.
2. **Scope paragraph.** One paragraph names the subsystem (the Event Manager), says it is the
   main interface between system and application, and says the chapter will use code fragments.
   A bulleted list of the two top-level sections follows.
3. **Scope limits and pointers.** A second paragraph states the chapter's focus (writing the
   main loop) and sends the reader to the *API Reference* chapter on events for per-event detail,
   and to the User Interface chapter for per-control event flow.
4. **Figure first.** A numbered figure (3.1) shows control flow through a typical application
   before any prose about the loop itself.
5. **"The Application Event Loop".** Three short paragraphs recall the previous chapter (startup
   routine, loop, stop routine), state the loop's job, and say the app stays in it until the
   system queues a stop event. Then **Listing 3.1**, captioned as taken from the shipping
   Datebook application: a dozen lines of real code, including a debug-only `#if` block.
6. **Numbered walk-through.** Six numbered steps explain the listing call by call. Each step
   says what the call does, what it returns, and what happens next. Step 2 explicitly says that
   not every application needs that call. Step 6 nests a dash-list showing the event sequence
   when one form replaces another, with a parenthetical aside discouraging preloading forms.
7. **Closing principles.** A few one-line paragraphs draw the moral: rely on the system's
   default handling, some events are really requests, only the active form handles events.
8. **"Low-Level Event Management".** Lists the five ways a user can give input, maps three of
   them to dedicated managers, and says most applications never call these managers directly.
   This "most applications don't need this" framing recurs at the top of every subsection.
9. **One subsection per manager** (handwriting, key, pen, system event). Each opens with what
   the manager does, then when you would bypass the event layer and call it yourself. The pen
   section gives hard numbers: digitiser resolution, sample rate, the polling interval while
   the pen is down, and the assumption that calibration is linear (offset plus scale).
10. **Embedded traps.** Two `IMPORTANT:` callouts mark deprecated calls. The system-event section
    has the chapter's best gotcha: the new handwriting engine can emit one character, then a
    backspace, then the real multi-stroke character. It explains the mechanism with a concrete
    letter pair and lists the four characters that can start such a sequence.
11. **Two state tables.** "Pen queue management" and "Key queue management" are two-column
    tables whose headers read as a sentence pair (what the user does / what the system does).
    The key table also carries the hardware timing (a 10 ms timer task for debounce and repeat).
12. **Auto-off control.** A short closing section on how input resets the sleep timer.
13. **Summary.** "System Event Manager Summary" lists every function in the chapter's managers,
    grouped by task under small headings (main queue, pen queue, key queue, power on/off), each
    name linked into the Reference. Names only, no descriptions.

The Memory chapter (5) follows the same pattern but goes further down: it describes the heap
header, master pointer table and the 8-byte chunk header field by field in prose, each part
prefaced by a callout saying the structure will change and you should use the API.

## Conventions

- **Callouts.** Inline paragraphs led by a capitalised label and colon: `NOTE:` for side facts,
  `IMPORTANT:` for things that will hurt you, `TIP:` for pointers to related advice, and
  `WARNING!` (with an exclamation mark) used rarely, for example to tell two almost identical
  function names apart. In the chapters sampled I counted 16 IMPORTANT, 15 NOTE, 4 TIP and
  2 WARNING. The levels are never defined anywhere in the front matter, and IMPORTANT covers both
  "this API is deprecated" and "this will corrupt the user's data". Identical IMPORTANT
  paragraphs are repeated word for word in two or three places in the same chapter.
- **Implementation disclaimers.** Before describing internal structures the book adds an
  IMPORTANT box saying this is the current implementation and may change, and that you must go
  through the API. Structure detail is given anyway, for understanding.
- **Tables.** Numbered per chapter (`Table 3.1`), caption above. Column headers are often written
  as half-sentences that pair up ("If you set X to..." / "The compiler..."), so each row reads
  as a sentence. Large summary tables (all launch codes, all notifications) sit at chapter end.
  One multi-column comparison table (dynamic heap budgets across OS versions) is cramped and
  hard to read even in the original.
- **Code.** `Listing n.m` with a caption naming its source; code drawn from the built-in
  applications whenever possible, then explained in numbered prose steps. Short fragments sit
  inline without captions. Comments inside listings carry rules ("you must structure your code
  exactly like this").
- **Figures.** `Figure n.m`, caption above; few of them (control-flow diagrams, layer diagrams).
- **Cross-references.** By chapter number and quoted title ("see Chapter 7, 'Expansion'") or by
  quoted section title alone; in HTML these are links. Cross-book references name the other book
  in italics. Some go to a specific table and page in the Reference, which ages badly.
- **Version annotations.** Behaviour is dated inline by OS release: "In 3.5 and earlier...",
  "Starting in 4.0...". Old API names survive with a version suffix, which the Nutshell chapter
  explains.
- **Footnotes.** Occasional numbered footnotes at chapter end (for example, one extra reserved
  ID).
- **Summary lists.** Every chapter ends "Summary of X": function names grouped by task.
- **Troubleshooting format.** The serial chapter has "Tips and Tricks" with two parts:
  debugging tips (bold imperative headline, then a paragraph) and "Common Errors" (symptom as a
  bold headline, cause and remedy beneath).
- **Index.** One per volume; two-level (main term, indented subentries); in the HTML each
  occurrence is a numbered link. Function names are indexed as their own entries.
- **Typography.** The Volume II front matter defines it: fixed-width for code elements,
  fixed-width underlined for emphasis inside code, bold for other emphasis, blue underlined for
  links. Trademarks get ® or ™ on first use in each chapter.
- **Chrome.** Every section heading carries a "back to top" link and every page a navigation bar
  (contents, previous, next, index): an artefact of the HTML conversion.

## Voice

Second person throughout ("you", "your application"), present tense, imperative for rules.
Sentences are mid-length, mostly 15 to 30 words, plain and unhurried; paragraphs are short
(two to five sentences). The tone is that of a patient platform engineer briefing a newcomer:
helpful, prescriptive, rarely clever. Humour is almost absent; the nearest thing is a dry aside
that users will not thank you for filling a sync log with debug output.

The book is good at explaining *why* a constraint exists before giving the rule: the
"why is this platform different" section grounds every later rule in screen size, battery,
session length or memory. It states priorities as ordered rules (heap space before speed before
code size), which is memorable.

Uncertainty is handled with "currently", "may change", "in this version", and with honest
vagueness where the figure varies ("slightly less than 64 KB", with a parenthesis admitting no
exact figure can be given). Danger is handled by stating the concrete consequence, for example
that two applications sharing an ID will replace each other and may corrupt data. Hardware
detail is given when it helps the application writer (sample rates, poll intervals, power
modes), never for its own sake. The voice slips into product marketing in places: the
trademarked phrase for the device appears in nearly every paragraph, and some features are
described as things users will welcome.

## Borrow

1. **A "why this platform is different" opening chapter.** Ground every later rule in the
   machine's constraints (small screen, click wheel only, battery, a hard disk that is slow to
   spin up, little RAM). Suits the **games SDK guide** (chapter 1) and the **firmware guide**;
   a lighter version suits the **user guide**.
2. **The chapter opener pattern:** mini-contents, a one-paragraph scope, a bulleted topic list,
   then an explicit "this chapter does not cover X; see Y". Suits **all manuals**.
3. **Real code from the real product as the canonical listing**, captioned with its source file,
   followed by numbered steps that walk the listing call by call. For us: the actual ProkBox main
   loop or a shipped example game. Suits the **games SDK guide** and **firmware guide**.
4. **"Most programs never need this" framing** at the top of each low-level subsection, then
   "here is when you would". Keeps beginners on the high road without hiding the low road.
   Suits the **games SDK guide** (direct LCD or codec access versus SDK calls).
5. **Implementation disclaimer before internals.** Describe internal structures fully but mark
   them as not a stable interface. In our books this pairs naturally with evidence tags: an
   `[apple-RE]` or `[hypothesis]` structure plus a "do not depend on this" note. Suits the
   **games SDK guide** and **firmware guide**.
6. **Sentence-pair table headers** ("The user..." / "The system...", "If you set... / The build
   does..."). Very readable for state and action tables. Suits the **user guide** (button
   combinations), the **firmware guide** (build options) and **WM8758** (power-up step / codec
   response).
7. **Reset and recovery combinations documented in the developer book**, each with exactly what
   is cleared and what survives. The iPod's reset, disk-mode and diagnostic-mode combinations
   deserve the same treatment. Suits the **firmware guide** and **user guide**.
8. **Power modes as a short list of named states**, each saying what is clocked, what is off,
   what wakes it, and a guideline for programs (block in the event wait, never spin). Suits the
   **PP5022** power chapter and the **games SDK guide** (frame pacing and battery).
9. **"Tips and tricks" plus "Common errors" by symptom.** Symptom as headline, then cause, then
   fix. Suits the **firmware guide** (serial console, I²C, boot failures), **WM8758** (pops,
   silence, distortion) and the **user guide** troubleshooting appendix.
10. **Concrete hardware numbers inside a software guide** (sample rate, poll interval, debounce
    timer) where they explain behaviour the programmer sees. For us: click-wheel sample rate,
    LCD update cost. Suits the **games SDK guide**, each number carrying its evidence tag.
11. **A naming-conventions section** for the API (prefix per subsystem, case rules, type
    suffixes) placed early. Suits the **games SDK guide** and **firmware guide**.
12. **A "writing robust code" checklist**: check results, never allocate zero bytes, don't poke
    hardware behind the API, restore state you change. Suits the **games SDK guide**.
13. **Inline version annotations** ("from SDK 0.3 onwards...") rather than separate per-version
    books. Suits the **games SDK guide** and **firmware guide**.
14. **State byte order explicitly**, in one sentence, wherever data crosses a boundary. Suits
    **PP5022** (host/BCM link, USB) and **BCM2722**.
15. **A concrete worked trap.** The handwriting "character, backspace, real character" example is
    the model: name the mechanism, show one specific case, list the triggers, give the defence.
    Suits **all hardware references** (gotchas sections) and the **games SDK guide**.

## Avoid

- **Undefined callout levels.** IMPORTANT is used for both trivia and data loss, and no level is
  defined in the front matter. We should define our levels once and keep them distinct.
- **Repeating the same callout verbatim** several times in one chapter. Say it once and link.
- **Bare-name summary lists.** The end-of-chapter summaries are just function names; useful
  online with links, nearly useless in print. If we keep summaries, give each entry a one-line
  description and a section number.
- **Depending on a sister book for essentials.** With no glossary and no appendices, the
  Companion cannot be read alone. Our brief says each manual stands alone.
- **Page-number references into another book** ("Table N on page M of the other book"). They
  rot with every revision. Use stable section numbers.
- **Brand saturation.** The trademarked device phrase in every paragraph, plus ® and ™ marks,
  reads as marketing. We must not do this with "iPod": name the hardware once, then say "the
  player" or "the 5G".
- **Stale model references** (named handheld models and OS versions that silently went out of
  date) and front-matter chapter lists that disagree with the contents (Volume II's overview
  skips chapter 6). Generate overviews from the real chapter list.
- **Vague figures where a measurement is possible** ("slightly less than"). We should measure
  and tag, or tag as `[hypothesis]`.
- **Marketing asides** about what users will welcome.
- **HTML chrome** (back-to-top links on every heading, navigation bars) has no place in
  Markdown sources.
- **Crowded comparison tables** with many version columns; split them or turn them round.

## Distinctive details

1. **The two-book split, stated up front.** The Companion explains, the Reference specifies,
   and every chapter ends by handing you over to the Reference. The division of labour is
   explicit in the front matter table of SDK documents.
2. **Shipping application code as the textbook.** The event loop is shown from the built-in
   calendar application, debug `#if` and all, rather than a toy, and the SDK grants a
   royalty-free licence to reuse it.
3. **Ordered optimisation priorities** given as a rule (heap, then speed, then code size), and a
   whole bullet list of robust-coding rules in chapter 1.
4. **The paperclip chapter.** A developer guide that tells you which keys to hold while poking
   the reset hole, and exactly what each combination clears or skips. Pure operational lore,
   written as reference.
5. **Internals described with a health warning.** The memory chapter gives the chunk header
   byte by byte and the lock-count limit, each preceded by a box saying not to rely on it.
6. **The handwriting backspace trap**, explained with a specific letter pair and a list of the
   risky first strokes: the best single "this does not do what you expect" passage in the
   material sampled.
