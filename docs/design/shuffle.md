# Shuffle over the whole library (#27)

Status: **integrated** (Phase 5, branch `np-p`). The core is `apps/ipodui/shuffle_core.{c,h}` (host-tested by `tests/nowplaying/test_shuffle.c`, including `shuf_group_order()`), the runtime is `apps/ipodui/lib_shuffle.c`, the facade `np_playback.c`. The integration points below are kept as the design record; the deltas from them are listed under "As built".

## Problem
Upstream playlists hold at most `max_files_in_playlist` entries, 2,000 on the PP502x (`settings_list.c`). Today `lib_shuffle_all()` takes a random 2,000-track sample and `lib_play()` takes a 2,000-row window. The 7G shuffles the **entire** library: every song comes once before any repeats.

## Options and their cost at 50,000 tracks

| | Raise the playlist cap | Library-backed shuffle (chosen) |
|---|---|---|
| RAM | `playlist_init()` allocates `indices` (4 B) and, because the device build compiles `HAVE_DIRCACHE` even with dircache off, `dcfrefs` (`struct dircache_fileref`, 12 B) **per slot of the cap**, for the whole session: **16 B/slot**. 2,000 slots (today) = **32,000 B**. 50,000 = **800,000 B** (+768,000 B); 65,536 = **1,048,576 B**. The cap's setting range also stops at 32,000 (upstream edit needed) | **44 B** of iterator state (`struct shuf_songs` / `struct shuf_albums`, measured with `arm-none-eabi-gcc -mcpu=arm7tdmi`), plus the existing 2,000-slot playlist used as a window. No new allocation |
| Start-up | one `tagcache_retrieve(tag_filename)` per track (file names are not in the RAM cache): upstream measures ~10 s per 2,000 on a PP5020, so **~4 min** for 50,000 with the UI blocked, plus `playlist_shuffle()` | 50 file-name reads for the first window (~0.25 s at the same rate; since p090 only 4 before the first sound, the rest behind it: "Instant start" below), then a refill of 50 every ~3 h of music |
| Flash writes | the control file gets every path (~70 B each): **~3.5 MB per shuffle**, re-parsed by `playlist_resume()` at every boot (seconds) | ~3.5 KB per refill, plus a 92 B resume record |
| Code | none | `shuffle_core.o` **1,284 B** `.text`, 0 data/bss (ARM, `-Os`) |
| Quality | Fisher-Yates over the list (perfect) | keyed Feistel permutation: a true bijection, no repeats until every track has played; at N = 50,000, 0 fixed points and 1 ascending neighbour pair (test output) |

Raising the cap costs most of a megabyte of the audio buffer for the whole session and minutes of blocking I/O per shuffle, and it would still have a cap. The library-backed design costs 44 B and runs in the background.

## The permutation
`shuf_perm_at(p, k)` maps position `k` in `[0, N)` to an item in `[0, N)`:

- a 4-round balanced Feistel network over `4^h >= N` (the domain is < 4N), whose round function is a 32-bit integer hash (two `MUL`s) of the right half XOR a round key. The round keys are derived from the seed.
- **cycle walking**: re-apply the network until the value lands in `[0, N)`. Following a cycle of a permutation from a point inside `[0, N)` back into `[0, N)` is itself a permutation of `[0, N)`, so the map is a bijection for every N (tested at N = 1, 2, 3, 4, 5, 16, 17, 255-257, 2,000, 50,000, 65,536, 65,537 with four seeds).
- **Cost**: measured average and worst Feistel evaluations per lookup: N = 2,000 → 2.05 / 16; N = 50,000 → 1.31 / 10; N = 65,537 (worst case for the domain) → 4.00 / 50. One evaluation is ~60-80 cycles, so a lookup averages a few µs on the PP5022 and stays under ~50 µs in the worst case. Nothing is O(N).
- **Deterministic**: the order is a function of (seed, N). Resume stores (seed, N, lap, pos, first, last), 24 B of it, and the whole struct is plain data.
- **Both ways**: "previous" past the playlist window is position `k - 1`; no inverse is needed.
- **Laps** (Repeat on): lap `L` uses `shuf_lap_seed(seed, L)`, a fresh order. If the new lap would start with the track just played, the next lap seed is taken instead (deterministic, so resume still works).

## Modes
- **Songs**: items are tagcache master index entries `0 .. tagcache_ui_count() - 1` at the time the run starts. The iterator yields entry numbers, and **the caller skips** what isn't music: `tagcache_ui_seeks(e, &flag) == NULL` (deleted) or `!class_ok(C_MUSIC, flag)` (books, podcasts). That is a RAM-only check, and the expected number of skips is `total / music` per track, so a skipped entry costs no I/O and nothing per track is stored. `first` (the song the user picked, or `SHUF_NONE` for Music → Shuffle Songs) plays first and is skipped when the order reaches it in lap 0.
- **Albums**: items are the rows of the precomputed album list (`LIB_ALBUMS` ROWS in `database_lib.dat`, with each album's COUNT). The album order is permuted. Within an album the tracks play in album order (disc, track). The caller supplies `album_len(album)` (the COUNT column; 0 = skip). The iterator yields `(album, track-in-album)`.

## Integration points (Phase 5, owners of `library.c` / Now Playing)
None of this is implemented yet. `library.c` is owned by other agents, so this lists what to add there.

1. **Source.** A queue started from Music → Shuffle Songs, or from Songs with more tracks than the playlist cap, is a *library source*. Every other queue (an album, an artist, a playlist ≤ 2,000) stays an ordinary Rockbox playlist, and the shelf's Songs/Albums act on it with `playlist_shuffle()` / `playlist_sort()` as today. (Shelf "Albums" over a small queue: order the playlist by album groups using `shuf_perm` over the groups.)
2. **Start (`lib_shuffle_all()` and the over-cap `lib_play(shuffle)` path).** Instead of sampling: `shuf_songs_init(&st, tagcache_ui_count(), seed = current_tick ^ entropy, first)`, then `play_begin()`, add the first **W = 50** music entries via `play_add()`, `playlist_start()`. Store the iterator, the source and the database stamp (`tagcache_ui_generation()` + `tagcache_ui_commitid()`) in the shell's playback state.
3. **Refill.** On `PLAYBACK_EVENT_TRACK_CHANGE` (audio thread: only set a flag, never insert from there), the UI thread's idle path checks the tracks left ahead in the playlist. With **≤ 10 left**, it appends the next 50 from the iterator. With ≤ 2 left, it does it at once. Otherwise it waits until `storage_disk_is_active()` so the refill rides an existing wake-up (one wake per refill at most, every ~50 tracks, i.e. ~3 h of music). The playlist is kept under the 2,000 cap by deleting the oldest played entries (keep ~100 of history) with `playlist_delete(…, 0)` in the same batch. Each refill is ≤ 50 file-name reads plus one control-file append, and it yields between entries. **Database states:** *ready*, refill as above. *Rebuilding or RAM cache unavailable* (`tagcache_ui_count() < 0`): no refill, the queued window keeps playing, and the next track change retries. *Dirty or changed* (a new generation or commit id): see item 6. Each state needs a sim script once this is wired (checklist item 10).
4. **Previous track.** Inside the window, the playlist handles it. Before the window's first entry, `shuf_songs_prev()` / `shuf_albums_prev()` gives the entry to insert at position 0 (only within the current lap).
5. **Resume.** The playlist control file already restores the window. The iterator struct (44 B) plus the stamp is saved with the window on every refill (the disk is awake then) in the shell's own state, not in `global_status`, to keep upstream untouched. At boot, if the stamp matches, refills continue the same order.
6. **Library changed** (USB sync, a commit: the generation changes). Entry numbers are meaningless after that. The queued window keeps playing (paths stay valid; deleted files are skipped by playback). The next refill restarts the iterator with the new N and `shuf_lap_seed(seed, lap + 1)`. Songs heard before the sync can come back sooner than a full lap; the 7G reshuffles after a sync too. **Albums** needs the new album list (the libfile is rebuilt by the precompute), so it restarts the same way.
7. **Albums: track lists.** `database_lib.dat` has album rows and counts but no per-album track order. Starting each album with `lib_open(LIB_SONGS, album filter)` is an O(N) scan, measured at 2.4 ms for 50k in the sim, so **~1 s on the device per album**, boosted, every ~40 min. Proposed follow-up for the libfile owner: a `LIB_ALBUMS` TRACKS column (master indices grouped by album in album order, 4 B × N = 200 KB on disk, read as one slice by the COUNT prefix sum), so starting an album is one small read.
8. **Shelf → playback.** `np_state` emits one `shuffle_commit` when the Shuffle step is left (not per wheel click). The screen maps it: library source → re-init the iterator in the new mode from the current track (`first` = the current entry) and replace what is queued after the current track. Ordinary queue → `playlist_shuffle()` / `playlist_sort()`. The setting itself is `global_settings.playlist_shuffle` plus a shell-side "albums" flag.

## Device-reality notes
- **Threads:** the iterator is UI-thread data. The audio thread only raises a flag. Refills take the playlist mutex the same way `lib_play()` does today.
- **Storage:** one wake per refill at worst (≤ 1 per ~50 tracks), usually none (it piggybacks on buffering). The raise-the-cap option would have rewritten ~3.5 MB per shuffle.
- **Memory:** no `core_alloc` while playing. The window reuses the existing playlist arrays, and the refill uses `library.c`'s existing play scratch (one file name).
- **Scale:** O(1) per track at any N up to 2^30. The Songs filter's skips are RAM-only.
- **Device checks (P10):** the refill latency (50 file-name reads) during playback, measured with the disk asleep and awake; the boot resume of the iterator after a power-off mid-refill (the control file and the state record must agree: write the state after the control file is synced).

## As built (Phase 5)
- **Trigger:** the track-change and buffering callbacks set flags and post `NP_PB_WAKE` (D7); `lib_shuffle_idle()` refills with ≤ 10 left when storage just ran (a buffering event) or is active, at once with ≤ 2 left. Every refill ends with `playlist_sync()` (control file fsync, then a flush and reload of the tracks ahead, so the audio thread sees the appended entries): the reload is one extra fill per ~50 tracks (device check P10).
- **Database states:** not ready (`tagcache_ui_count() < 0` or busy) → no refill, the window plays on, the next event retries; a new generation with a different stamp (commit id, entries, `SORTKEY_VERSION`, albums sum) → a new lap; the same stamp after a reload (every boot) → the run continues.
- **Boot:** `npshuf.dat` is read once (92 B; a 0.8.0 record of 80 B is upgraded and its run goes on in a new lap) at the first idle pass; its stamp is checked at the first refill. A playlist with fewer than `queued`, or more than `queued + 50` entries is another queue (the record is dropped); up to 50 more is a power cut after the control-file sync (a new lap).
- **PREV before the window's first entry** is out of scope for v1 (Revision 1 item 9): the global PREV does what the playlist does.
- **Albums on an ordinary queue** (Revision 1 item 10): `lib_play()` notes album boundaries of the queue it builds (256 B static bitmap, ≤ 2,048 entries); the shelf's Albums calls the guarded `playlist_reorder_ipodui()`: back to insert order, `shuf_group_order()` in RAM, one shuffle command in the control file. ⚠️ A resume replays that command as a plain song shuffle of the same tracks (the control file cannot express the album order); the shelf still reads Albums, and choosing it again restores album order. A queue built elsewhere (no bitmap) plays in order.
- **Albums as a library source** reads each album's tracks from the #49 TRACKS section (two small reads per album: the start pair, then one entry per track), else builds the album-filter view once per album. The slice is not checksummed on this path (it is read in pieces): entries are range-checked.
- **Over-cap Songs:** an unfiltered Songs list played shuffled with more rows than the playlist cap starts a library source with the chosen song first. Filtered lists over the cap still take a sample.
- **Now Playing counter (0.8.1):** over a library source the counter reads library-wide ("56 of 302"), not the window ("56 of 100"). The record (version 2, 92 B) keeps `struct lib_shuf_count`: the entries the source queued (all laps), and where the current and the previous lap began. Each insert of a refill counts one (`lib_shuf_count_queued()`); a lap change of the iterator (Repeat) or a restart sets `LIB_SHUF_F_LAP`, so the next entry counts from 1; a shelf commit drops what it deletes and starts a lap at the playing song. Now Playing asks once per snapshot, `lib_shuffle_lap_pos(entries after the current one)` (O(1), no I/O), and takes M from `lib_stats()` (the music songs, counted at sync time). The history trim at the playlist start does not matter: positions are taken from the end. A 0.8.0 record (80 B, version 1) is upgraded at the boot read; the first refill then restarts its lap and numbers the resumed queue from its start. Spec decision (Songs and Albums): `spec/now-playing.md`, "Shuffle counter".

## Instant start (p090-shuffle, owner 2026-11-13)
Owner: "build the initial playlist quickly and then backfill the remainder of the songs, so it still opens instantly." Tracker #363 measured ~20 s from the press to sound on the emulator's HDD 32 MB model with 50k songs (its HDD timing is an estimate, not bench-calibrated).

### Today's path (before this change)
1. Main menu › Shuffle Songs: `menu.c:215` → `ui_shuffle_songs()` (`ui_main.c:358`) → `lib_shuffle_all()` (`library.c:4102`) → `lib_shuffle_start(SONGS, SHUF_NONE)` (`lib_shuffle.c`). The only other entry is an unfiltered Songs list played shuffled with more rows than the queue setting (`library.c:4016`, the chosen song first). No button hold starts a shuffle.
2. `lib_shuffle_start()`: `rec_load()` (92 B, once per boot), `source_init()` (`tagcache_ui_count()`, the stamp, `shuf_songs_init()`: O(1)), `playlist_create()` (a new control file), then `refill()`: **the whole 50-entry window, synchronously**. Each entry is a permutation step (O(1)) and a RAM-only `is_music()` check, then `lib_scratch_path()` → `tagcache_retrieve(tag_filename)` (file names are not in the RAM cache: 2 `read()` calls at a random place in the file-name tag file) and `playlist_insert_track()` (a control-file append, ~3.4 `write()` calls). Then `refill_finish()`: one `fsync` of the control file and the 92 B record.
3. `playlist_start()` → `audio_play()` → playback's start (`playback.c` "audio start": stop, fill, codec, prefill) → the first PCM. `ui_show_wps()` pushes Now Playing, whose counter is already library-wide ("1 of 302", 0.8.1).

Nothing is O(N): no database walk, no RNG pass over N, no N-sized array, no RAM-cache load (Shuffle needs the cache loaded and refuses otherwise). Now Playing's art comes from the art cache after the push and does not delay the sound.

### Measurements
Simulator, 50k library (`tests/perf/shuf_start50k.sh`: five starts from the main menu on a clone of `build/sim-50k`), the host's own disk (no latency model), 2026-11-13:

| | queued before `playlist_start()` | UI-thread `read()` calls | `write()` calls | start build (wall, median of 5) | play request → first PCM (`audio start ms=`) |
|---|---|---|---|---|---|
| base behaviour (all 50 first; `LIB_SHUF_FIRST` set to 50) | 50 | 100 | 165–170 | 67 ms | 260–550 ms |
| instant start | 4 | 8 | 17–21 | 37–86 ms (host noise) | 170–1,260 ms (two runs over 1 s under host load) |

The backfill (+46, 10 chunks of ≤ 5) lands 290–1,330 ms after the start in the simulator, behind the first sound.

What the device pays (an estimate, not a device measurement): the start's cost is its random reads. A 1.8" 4,200 rpm drive needs ~15–20 ms per random read (seek plus half a turn), so 50 file names cost **~0.75–1.0 s** on a spinning HDD unit (the spin-up, if any, both designs pay), and 4 cost ~60–80 ms. On flash a random 4 KB read is ~0.5–1 ms: ~25–50 ms before, ~2–4 ms now. The control-file writes go through the sector cache and reach the disk at the `fsync`.

**Most of #363's 20 s is elsewhere.** In the emulator's numbers, `audio_start_ms` (the play request to the first PCM, after the queue is built) is 18.5 s of the 20.1 s on HDD 32 MB, and 0.2–0.7 s on flash 64 MB. The queue build is ~1.5 s of the press-to-sound time there; the rest is in playback's start (stop, fill, codec load, prefill) on the HDD 32 MB model, while the library/art maintenance runs in the same window. This design takes the ~1 s of file-name reads out; the 18.5 s needs #363's watched emulator run (its "audio start" lines split stop/fill/codec/pre) and a separate fix.

### Design
- **First batch.** A start queues `LIB_SHUF_FIRST` = 4 entries as a complete refill (control file synced, then the record) and calls `playlist_start()`. Four, not one: three NEXTs before the backfill lands still find a song, and a song that does not play (#286) has neighbours. Each entry is one file-name read.
- **Backfill.** The start leaves a backfill owed (`start_fill`) and posts a UI wake. `lib_shuffle_idle()` begins it at once (disk up or not) as an ordinary chunked refill (`SHUF_CHUNK` = 5 entries per UI pass, `HZ/20` apart) of `LIB_SHUF_WINDOW - LIB_SHUF_FIRST` = 46 entries. The window stays 50, so every later refill, the history trim, the record and the boot check are unchanged. It ends with the usual `refill_finish()`: the control file's fsync and the record. Since p090 that sync is `playlist_sync_append_ipodui()`: the audio thread keeps every track it has buffered (`audio_playlist_appended()`, ledger 3.18) instead of `playlist_sync()`'s flush, which dropped them and read them again at every refill.
- **When it runs.** Its first chunk waits for the first sound (this start's first track began, `lib_shuffle_track_changed()`, and `pcm_is_playing()`), a pause, the first batch running low (`left_ahead() <= LIB_SHUF_URGENT`: NEXTs, or failing songs), or `LIB_SHUF_START_WAIT` (2 s), polling every 20 ms. Then it runs between the buffering thread's reads rather than after the whole fill. (Written when the refill still flushed: a backfill after the whole fill would have dropped tracks 2–4. With the append it no longer matters for the bytes; landing early still gets the queue past the first batch sooner.)
- **The order** is the existing keyed Feistel permutation ("The permutation" above): O(1) state (44 B), lazy, no N-sized array, the whole library in one lap with no repeats, the first song at position 0. An index array for Fisher–Yates would cost 4 B × 50,000 = 200 KB for the session (a `core_alloc` during playback, against the memory floors) and an O(N) shuffle before the first song. The lazy permutation is what makes a first batch possible: position 0 is known without building the rest.
- **Uniformity (fixed here).** A chi-square test over many seeds (`tests/nowplaying/test_shuffle.c` `test_uniform`) found the permutation far from uniform for small libraries: with 1–3 bit Feistel halves the round function takes too few values (n = 7: chi-square 87,502 on 5,039 dof over all orders, 16× the 0.1% critical value; n = 5..7 failed in both seed families). The narrowest half is now `SHUF_HALF_MIN` = 5 bits (a 1,024 domain): every test passes, worst at 0.94 of the critical value. 4 bits passed only at the edge (1.00 at n = 64). Only libraries of ≤ 256 songs get a new order; larger ones keep exactly the order they had, and the width is stored in `struct shuf_perm`, so a run saved by an older build resumes in its own order. Cost at n ≤ 256: ~1,024/n Feistel evaluations per lookup (n = 2: ~0.5 ms on the PP5022, once per track).

### Edge cases
- **NEXT before the backfill lands:** the first batch covers three; with ≤ 2 left the wait ends and the backfill runs at once. A NEXT past the last queued entry is brought back into range by playback (`audio_on_skip()`), not an error. PREV within the window is the playlist's, as before. Tested: `ipodui-shuf-instant` B (backfill held after one chunk: five NEXTs reach the 6th song, then it completes).
- **Shuffle Songs again:** `lib_shuffle_start()` drops an open backfill (`ses.on = false`, `start_fill = false`) before the new queue replaces the old; nothing of the old one is written. Tested: C.
- **USB or a library update mid-backfill:** the refill rules as before. A new RAM-cache generation stops the chunk ("refill stop (gen)"), the entries so far stay, and the next track change retries; a changed database restarts the lap with the new N (item 6).
- **Unplayable songs (#286, #281):** playback ends a queue once every entry has failed in a row (`MIN(playlist_amount(), 50)`). With a growing queue that count is the queue's length when it happens: the all-unplayable 3-song library now stops at 14, not 50 (`ipodui-shuf-unplayable-3`, still at most 2 record writes). With some unplayable songs, the backfill starts at the first failure (the batch runs low) and adds 5 per ~50 ms, faster than songs fail (~25–35 ms each on the device), so a normal library plays on. ⚠️ Device check: on an HDD the failures and the chunk's reads share the disk; a library where most songs cannot play is the case to watch.
- **Power-off or sleep mid-backfill:** `lib_shuffle_settle()` ends it at the entries it has and writes the record, so the next boot resumes the run (`shuf: boot record 0`; tested: D). A power cut without the settle leaves the first batch's record (queued = 4) with up to 46 more entries: `boot_resume_check()` takes it as a cut after the control-file sync and starts a new lap, as for any refill. The playlist file format and the record are unchanged (record version 2, 92 B).
- **Resume after a reboot:** the control file restores the window and the record the iterator; the same order continues.
- **Up Next / queue views:** they show the playlist as it is: 4 entries for the first fraction of a second, then 50. Now Playing's "n of M" is library-wide from the first frame ("1 of 302" over a queue of 4; `ipodui-shuf-counter`).
- **32 MB vs 64 MB:** the same logic and window on both; a 64 MB unit just buffers more of the next tracks.
- **HDD spin-up:** the first batch is 4 reads in one burst with the control file; the backfill rides the disk the first track's fill has already woken. Sorting each chunk's reads by file offset would shorten HDD seeks but needs the chunk's file names held at once (5 × 260 B); not done.
