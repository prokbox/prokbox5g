# Quirks and gotchas

One list of everything that bites. Each item names the file with the detail.

## Start-up and memory

1. **Both cores run the same entry code.** Branch on `PROCESSOR_ID` (`0x6000_0000`, low byte `0x55`/`0xAA`) before touching anything shared. [rockbox] (`boot.md` §4)
2. **The remap must run from IRAM**, once per core, CPU first. Rewriting MMAP0 while fetching from SDRAM pulls the floor out from under the code. [rockbox] (`memory-map.md` §3)
3. **Probe the RAM size before the remap**: after it the image has already assumed a size. [rockbox]
4. **Zero all MMAP registers and disable the cache before jumping to another image**, or it starts with your mapping. [rockbox] `rolo.c`
5. **`CACHE_CTL_VECT_REMAP` survives into the next image**; some images do not clear it and hang. [rockbox]
6. **The ROM leaves its own state in the last 256 bytes of IRAM** and Apple's firmware reads a boot-failure flag in upper IRAM; clear `0x4000_C000`–`0x4001_FFFF` before powering off if Apple's firmware must boot cleanly next. [rockbox] `power-ipod.c`
48. **What a reset leaves in SDRAM (for a record that must outlive one).** By the code: Rockbox's `crt0-pp.S` clears only `.ibss` and `.bss`/`.ncbss` (below `_end`, ~1.1 MB) and writes one byte each at physical `0x11FF_FFFF` and `0x13FF_FFFF` (the 32/64 MB probe); our bootloader loads the image at `0x1000_0000` (up to 8 MB) and puts its `.bss` at `0x1100_0000` (+204 KB); the ROM loads `osos` (Apple's OS plus the bootloader, under 8 MB) at `0x1000_0000`. So the 256 bytes under the codec buffer (fw-ui: logical `0x03EF_FF00`, physical `0x13EF_FF00`; a 32 MB unit `0x11EF_FF00`), which `HAVE_PANIC_RECORD` keeps out of the audio buffer, are written by none of them. [rockbox] (code reading, 2026-10-19). Whether the bytes **survive** is a separate question: a `DEV_RS` system reset stops SDRAM refresh until the ROM sets the controller up again, and the MENU+SELECT reset's mechanism is not known (it could cut power to the SDRAM). [hypothesis] until the device test in `docs/hardware.md` ("Panic record") is run. Holding MENU starts Apple's firmware, which uses all of SDRAM: a record is lost then. Write such a record only through the uncached alias, or a dirty cache line is lost at the reset. (`memory-map.md` §5)
51. **A misaligned halfword or word access to SDRAM is a data abort.** A Thumb `strh r3, [r4]` with `r4 = 0x0033_F319` (odd) aborted at that instruction, every time the game started (Chute's, then called Airdrop, state record handed out at `state_img + 17`). The simulator, the host tests and unicorn all accept the access silently, so only the device catches it: anything the firmware hands to code that casts it to a struct (a game's state record, a buffer) must be aligned to at least the struct's alignment; we use 8. [silicon] (P12 device bench 2026-10-24, `ipodui.log` boot 13:52:25: `panic pc=0033e266`, r0–r7 in the record; fix `SDK_REC_OFF`, `apps/ipodui/sdk/sdk_core.h`). **How we catch it before the device** (2026-10-25): the UBSan sim runs with `-fno-sanitize-recover=alignment` and a misaligned access anywhere in the shell, target or bcmfw code fails the gate; every host test is compiled through `scripts/align-shim` (alignment sanitizer, no recovery); `tests/aligncast` baselines byte-offset casts to 16/32-bit pointers. Rule: `docs/process.md` lean coding rule 12. The host-side findings so far were test models, not firmware: a chip-memory stub that cast a 2-mod-4 address (`tests/bcmjob`), and a shim config that took `fat.c` down its non-`UNICODE32` path (`tests/fatcrash`)
79. **Quirk 51 again, decided by the link: a `static char` array written through an `(unsigned short *)` cast.** Upstream's `ata_get_info()` (`firmware/drivers/ata-common.c`) stored the IDENTIFY words with `strh` into `static char vendor[8]`, `product[16]`, `revision[4]`. A char array's alignment is 1, so where it lands depends on what else is in `.bss`: years of even addresses, until a day's merges moved `.bss` by an odd number of bytes (b0ece13127: `vendor.1` 0x1e3a25). The first `disk_mount()` then took a data abort 0.37 s after start, and the developer build's silent panic restart (`panic.c`) made it a boot loop with no log, since the panic comes before anything is written. [silicon] (sitting 4gh, 2026-11-06: owner's photo of the diagnostics build `out/bisect-4gh/c-b0ece-diagscreen`, kind 2 data abort at `pc` 0xf9c08 = that `strh`, trace `disk_init` > `disk_mount` > `storage_thread`). None of quirk 51's nets could see it: the simulator has no ATA driver, and the host tests and `tests/aligncast` don't link the target's `.bss`. **The net now:** `scripts/misaligned_access_check.py` runs a data flow over the linked ELF, from literal-pool addresses of static data through `ldrh`/`strh`/`ldr`/`str`, and fails any misaligned one (`validate.sh`, every ARM build, bootloaders included). It flags exactly these two stores in b0ece13127 and nothing else. **The debugging lesson:** a boot loop with no log gets a diagnostics build that halts and shows the panic record (`-DPANIC_DIAG_SCREEN`, branch `diag-4gh-panicscreen`) as the first device step. One photo named the instruction, where static work had cleared crt0, Thumb interworking, the link regions and the boot-time power code without finding it.
80. **Open: the panic reboot-loop guard did not stop the 4gh loop.** `panic_shell_exit()` arms two guard words at the top of the panic record's area before `system_reboot()`, and a second panic within `PANIC_GUARD_TICKS` of the restart should switch the unit off (or, with a cable in, halt dark). On the device the 4gh panic looped instead. So either the guard words don't survive a `DEV_RS` system reset (SDRAM refresh stops until the ROM sets the controller up again: quirk 48's open question, now with evidence against survival), or the next boot overwrote them before the second panic (the bootloader loads the image at physical `0x1000_0000`, far below the area). [hypothesis] The diagnostics build can settle it: write a pattern to the area, `system_reboot()`, read it back on the next boot. Tracked as a ticket note (sitting 4gh).
7. **Most register pages are mirrored** and unused words read `0xCACA_D0D0`; a wild pointer into `0x6000_xxxx` often reads plausible values. [external] siggi `08`
92. **An initialiser on a variable in a section the boot zeroes is dropped without a word.** `SHAREDBSS_ATTR`/`NOCACHEBSS_ATTR`/`XCORE_BSS` place a variable in `.ncbss`, `IBSS_ATTR` in `.ibss`. GCC does not treat those names as BSS, so the object carries the initialiser (`objdump -h`: CONTENTS), but the linker script makes the output section NOLOAD and `crt0-pp.S` zeroes it: the variable boots as 0. `wmcodec_gate_mask = DEV_EXTCLOCKS | DEV_I2S` did, so the AW-5 gate never closed (#313; the laptop emulator's DEV_EN model found it, the b12 `f3261f9651` ELF confirmed it). An initialised shared variable belongs in `.ncdata` (`SHAREDDATA_ATTR`, `XCORE_DATA`), an IRAM one in `.idata`. `scripts/zeroed_init_check.py` fails the gate on any non-zero byte or relocation in an object's `.ncbss`/`.ibss`. [ours] (objdump of fw-ui, 2026-11-12)

## Cache and coherency

8. **No coherency between the cores' caches**, and none with DMA. Shared data goes in IRAM or the uncached alias (`0x1000_0000 | logical`). [rockbox] (`cores-and-threads.md` §4)
9. **Do not invalidate with `CACHE_OPERATION`'s invalidate bit.** Rockbox rewrites every status word to "valid, clean, unused address" with interrupts off, because invalid lines corrupted memory under heavy writes plus instruction fetches. Initialise the cache by reading 8 KB so every line is valid. [rockbox]
10. **Cache maintenance is whole-cache only** (8 KB flush per operation). [rockbox]
11. **Cacheability is by address window** (`CACHE_MASK`): logical SDRAM `0x0`–`0x03FF_FFFF` and flash `0x2000_0000`–`0x23FF_FFFF` are cached; physical SDRAM `0x1000_0000` is not. [rockbox]
87. **Open: does each core have its own cache data array?** There is one data window but two status windows. [hypothesis] one array per core; the bench row **COP row C2** decides it (`cores-and-threads.md` §3; `../research/bcm2722/bench-p19.md` C2).
52. **A cache write-back is per core.** `commit_dcache()` writes back only the calling core's cache. So a DMA start on the COP (`e2port_start()`) does not write back the CPU's dirty lines of its source: the producer core must write them back itself. [ours] (code reading, 2026-10-24). Whether engine 2 runs correctly when started and polled from the COP is open until **COP row C1** runs. [hypothesis]
53. **Open: polling with `yield()` keeps a core awake.** The yielding thread is still runnable, so the scheduler never reaches `core_sleep()`. On the COP, where the poller is often the only thread, the core never sleeps. [hypothesis] until **COP row C3** runs (`cores-and-threads.md` §7).
54. **A cross-core mutex does not make the data it guards coherent.** Both cores take the lock in turn, but each still reads its own cached copy of the guarded words: one core's write stays in its cache (or lands in SDRAM under the other's stale line). Guarded state that both cores use goes in the uncached alias as well. [silicon] symptom, bench sitting 3 (2026-10-26: the DAC's standby wake replayed over music with the UI on the COP); [ours] mechanism by code reading and the host model `tests/audioxcore` (`../data-paths.md` R7 item 8, D15)
55. **The PCM driver and mixer are single-core.** The playback DMA interrupts the CPU's FIQ only; `pcm_play_lock()` masks that FIQ (from either core, but its depth counter is a plain increment) and the mixer's control words are cached. A COP that starts a channel or the PCM leaves the CPU's FIQ playing stale frames (the replayed click: a tone). Requests go to the CPU. [silicon] symptom (sitting 3); [rockbox-derived] driver (`pcm-pp.c`: "dual core support will require other measures"); [ours] the rule (`../data-paths.md` R7 item 8). Single-core **by Rockbox's wiring**: the controller routes per core and Apple serves source 26 on the COP [apple-RE]; sitting 4h's P-1 probes that route on our unit (`interrupts-timers.md` §6)

88. **A cache line is the unit of ownership between the cores, not the variable.** The PP5022's data caches write back whole 16-byte lines and do not snoop each other. A static the COP writes dirties its whole line in the COP's cache; when that line goes back (an eviction, or the whole-cache write-back at every remote call), the other words on it are overwritten with the COP's copies, which may be stale. With `cache_lru` (the disk cache's LRU list head, written by the CPU) on the same line as `bidi_buf` (the text drawing's scratch, written by the COP), the CPU's LRU list lost entries until `dc_get_buffer()` found none: "file_cache_alloc - OOM" in the tagcache thread, 11 s after the first boot with the UI on the COP. Data written by different cores therefore sits on separate lines: the linker places the shell's data, and separately the file layer's, on lines of their own (`app-pp.lds`; checked by `scripts/xcore_line_check.py`). [silicon] symptom, bench 4f (2026-11-05, build 647b965d80-261105, panic record symbolised against a matching rebuild); [build] the line, from the map (the same object order in `fw-ui`: `cache_lru` at 0x15d010, `bidi_buf.0` at 0x15d014); [ours] mechanism, host model `tests/febe/cachemodel.c` protocol D (a shared line loses the CPU's word in 122 of 300 seeds, separate lines in 0) (`../data-paths.md` R7)

90. **One core writing uncached and the other through its cache is not coherent either.** An uncached store goes to memory, but it does not touch the other core's cache: a clean line there keeps answering reads with the old value, and once that core writes any word of the line it is dirty and its write-back puts the old copies of the other words back over the uncached stores. Memory both cores write needs lines of its own, reached by **both** cores through the uncached alias; reused memory (a buffer carved again) needs the CPU's cache written back and dropped once before the first uncached use, or a dirty line from the earlier use lands on it later. Case: the codec's id3 (playback.c `CODEC_ID3`, in the audio scratch area) with the decode on the COP: the codec writes length, frequency, tail_trim and elapsed uncached, the CPU wrote elapsed and offset through its cache (#196, `apps/codec_id3.c`). [ours] (code reading, 2026-11-07; not seen on the device); mechanism shown by the host model `tests/codecid3` (0.8.0-rc.4's placement loses a COP write in 1,870 of 2,000 runs, the fix in 0).

## Clocks

12. **The PP5022's PLL must run at ≥ 96 MHz before its post-divider**; get 30 MHz as 120/4, not 30/1. [rockbox]
13. **Every `CLOCK_SOURCE` write needs both cores stalled** (`scale_suspend_core`) and interrupts off. Step to 24 MHz before retuning the PLL. [rockbox] (`clocks-power.md` §4)
14. **`DEV_TIMING1` must follow the clock** (`0x0808` at 80 MHz, `0x0303` below): raise before speeding up, lower after slowing down. [rockbox]
15. **Clock frequency changes stall both cores** (one clock for both). [rockbox]
16. **UDMA above mode 2 needs 80 MHz**; Rockbox boosts per transfer. [rockbox]
17. **The host port's throughput is bound by the PP clock** (~10.5 PP cycles per 16-bit transfer): a full LCD frame costs ~27 ms of CPU at 30 MHz. [silicon] S8

## Interrupts and timers

18. **Reading `TIMERn_VAL` acknowledges the timer**; reading a DMA channel's `STATUS` acknowledges it too — read it anywhere else and the handler never sees the interrupt. [rockbox]
19. **The wheel controller raises the I2C interrupt** (high source 40). An I2C driver that enables that source will receive wheel events. [rockbox]
20. **The COP gets no tick of its own** in Rockbox's design; the CPU wakes it from the Timer 1 handler. [rockbox]
21. **An interrupt enable followed by a disable must take effect in order** (Apple's and Rockbox's code depend on it). [external] siggi `06`
56. **A branch to address 0 after boot used to spin for ever.** After `cpu_init` copies the vectors to 0, address 0 holds `ldr pc, [pc, #24]` and the reset word it loads was `start`, which links at 0 as well: a NULL function call (or a `--wrap` whose real body was never linked, the 2026-10-26 freezes) looped on that one instruction with the IRQ mask as it was, so with IRQs masked nothing (no tick, no watchdog task) ever ran again and no record was kept. The reset word now points at `reset_reentry_handler` (`crt0-pp.S`), which reports "Jump to 0" through `UIE()` (record, restart). No real start uses that word: the ROM, our bootloader and ROLO all enter the image at `DRAM_START` before the remap, and a restart is a `DEV_RS` reset. [rockbox] (code reading) + [build] (`.vectors` dump: word 0 = `reset_reentry_handler`); the device has not yet taken this path.
57. **The interrupted pc is the IRQ stack's top word.** `irq_handler` (a GCC `interrupt("IRQ")` function) starts `sub lr, lr, #4; push {r0-r3, ip, lr}`, and IRQs never nest here, so inside a tick task the word just below `irq_stack` (crt0-pp.S, now global) is the pc the tick interrupted; System mode's sp/lr are the interrupted thread's, readable by a brief `msr cpsr_c, #0xdf`. The hang watcher uses both (`firmware/common/hang_watch.c`). [build] (fw-ui disassembly, gcc 16, 2026-10-26); re-check after a compiler change.
78. **Apple's audio DMA interrupt is the CPU's FIQ; the COP's FIQ vector is a trap.** Apple routes source 26 (and 27) to the CPU's FIQ through a CPU-only interrupt service, and the COP never writes `COP_INT_PRIORITY` or reads `COP_FIQ_STAT`. The COP's FIQ target at IRAM `0x4000_0000` is two zero words then an exception return without the `- 4`, so a COP FIQ there would return one instruction late and never be acknowledged. Apple is therefore no evidence for or against a COP FIQ route: that is ours to prove (`apple-cop-audio.md` §0, §7). The old "COP enables bit 26 at `0x3F`" was the per-core cache set-up (`0x0400_0000` cacheable size, `0x3F` cache field). [apple-RE], 1.2.1/1.2.3/1.3

## Peripherals

22. **I2C moves at most 4 bytes per transaction** and has no visible NAK. [rockbox] (`gpio-i2c.md` §6)
91. **A byte read at `0x7000_C00D` (byte lane 1 of the I2C data word) data-aborts.** The word store at `0x7000_C00C` and the byte reads at the lane-0 addresses do not. Touch the I2C data registers only at `C00C`, `C010`, `C014` and `C018`, as Rockbox's driver does. [silicon] sitting 4gh-b7 (`gpio-i2c.md` §6.1)
23. **The WM8758 is write-only**; keep a shadow of every register. [rockbox]
24. **The codec is the I2S master**; set `IISCONFIG.MASTER` and the PP fights it. [rockbox] (`audio.md`)
25. **Stopping I2S DMA does not stop the transmitter**; Rockbox leaves `TXFIFOEN` set and the PP keeps shifting an empty FIFO. [rockbox]; [silicon] S34
93. **The I2S TX FIFO drains only while the codec clocks the bus.** With the WM8758's PLL off (ProkBox's DAC standby: BCLK/LRCLK stop) the FIFO never empties, and a playback DMA channel told to stop (START cleared) stays busy while its last word waits for room. Upstream's `while (!IIS_TX_IS_EMPTY)` and `while (DMA0_STATUS & BUSY)` then spin for ever: the b11 bench row ebt13 hung there [silicon, #311], the laptop emulator at the start [emulator, b12 `390dee0bf3`]. ProkBox bounds both (8 ms: the FIFO's 16 words at 8 kHz, four times), then sets `IIS_TXCLR` and waits once more (`pcm-pp.c` `pcm_wait_bounded()`, #312), and wakes the codec before any PCM start (`pcm.c`). Whether `IIS_TXCLR` lets a stopped channel finish its word with no BCLK, and what the FIFO register reads with `DEV_I2S` gated, are [hypothesis]: the bound returns either way (host model `tests/pcmwait`); a `pcm PCM FAULT` line in the log says which arm ran.
26. **Never read the ATA status register during a DMA transfer**: it hangs; wait on `IDE0_CFG` bit 3. [rockbox]
27. **DMA engines (general, IDE, USB) use physical addresses**: add `0x1000_0000` to logical SDRAM addresses. [rockbox]
28. **ATA DMA reads need 16-byte-aligned buffers**; DMA writes are slower than PIO on hard disks. [rockbox]
29. **The 5.5G's partitions are in 2048-byte units on a 512-byte drive.** [rockbox] (`storage.md` §4)
30. **Our flash adapter negotiates UDMA 2**, because it leaves IDENTIFY words 76 and 93 at 0. [silicon]
31. **Disabling the USB block in a bootloader stops Apple's firmware from loading.** [rockbox]
32. **The PP5022 needs its USB PHY sequence after every controller reset.** [rockbox] (`usb.md` §2)
33. **The backlight has no absolute brightness register**: count pulses from the known level 16 after enabling. [rockbox]
34. **A 32-bit read through the BCM host port is two 16-bit reads** and can be torn by the BCM writing between them. [silicon] S11, S12
89. **Program the I2S DMA in whole words.** Upstream's `pcm-pp.c` set the chunk to `sample_rate >> 6` bytes, which is not a multiple of 4 at 48, 44.1, 24, 16, 12 and 8 kHz (44.1 kHz: 689 + 335 bytes per 1 KB frame), so chunks after the first started off a word boundary with a 32-bit `DMA0_INCR`. ProkBox rounds the chunk down to whole words (#191, `tests/pcmdma`). What the PP5022 does with a part-word length or an unaligned `DMA0_RAM_ADDR` (truncate, round up, or ignore the address's low bits) is unknown [hypothesis; the emulator truncates; bench row `dmaodd` answers it] (`dma.md` §2)
35. **Rockbox's host-port waits are unbounded**; an unpowered BCM reads `0xFFFF` and the waits hang. Bound them. [rockbox]; [ours]
36. **PP DMA into the BCM's host port has never delivered a byte.** S8 reported SRAM clean, but the CPU had just written the same frame there, so that readback was invalid; S32–S33 lost and shifted words in SDRAM, and S34/S35 landed nothing in SDRAM or SRAM (S35). DMA was never faster than the CPU copy either. [silicon] (`dma.md` §4; `../data-paths.md` D1)
37. **After a DMA block to the port, wait for the port's write-ready bit** before setting a new address: the engine finishing is not the port accepting. [ours] after S32
38. **Rockbox's `DEV_PIEZO` equals `DEV_OPTO`** (`0x1_0000`, the wheel); the piezo's PWM is bit 17 (`DEV_PWM`). [external] siggi `05`; [rockbox]
39. **Standby without `CHGWAK` or `EXTONWAK` in the PMU's `OOCC1` leaves the unit unable to wake.** [rockbox] (quoting iPodLinux)
40. **The PMU's interrupt flags are cleared by Apple's boot ROM**, so firmware cannot tell why it woke. [rockbox]
41. **The drive's write cache is on and flushed only at standby and shutdown** (upstream `ata.c`): the order write commands complete in is not the order sectors reach the media at a power cut [hypothesis]. Our shell build issues FLUSH CACHE at every write-order point of the file layer (`../data-paths.md` R11; #91). Whether our flash adapter reports or honours the cache is open question #32. [rockbox]; [ours]

## Scheduling (measured on our unit)

85. **At 30 MHz, priority beats frequency**: a feeding thread below the codec's (boosted) priority ran up to 2.1 s late; with the right priority it held 16 ms drift unboosted. [silicon] S31, S34
42. **The ROM changes nothing back**: a kernel cannot rely on any peripheral being in its reset state at entry (the BCM is running, the wheel block enabled, the IDE controller initialised). [rockbox]; [external]
## USB (measured on our unit)

43. **A USB INQUIRY reply in a movable or cached buffer may never retire.** Use a static, page-aligned buffer through the uncached alias. [silicon] (`usb.md` §6)
44. **USBMODE's stream-disable bit does not exist on the PP5022**; it reads back unset. [silicon] (`usb.md` §6)
45. **Offset `0x164` (TXFILLTUNING on other ARC cores) reads back 0 here**, and writing it correlated with dead enumeration. Leave it alone. [silicon] (`usb.md` §6)
46. **A bus reset leaves queue-head RAM as it was**; clear each endpoint's overlay, halt and toggle at configuration. [silicon] (`usb.md` §6)
47. **A bulk-IN dTD can sit ACTIVE for ~304 ms with no error bit** until the host resets the bus; ATA DMA running at the same time is a material cause. [silicon] (`usb.md` §6; `../data-paths.md` D12)
86. **USB audio (an isochronous configuration) reportedly hangs a 5G.** The podbox fork disabled its USB audio class for the iPod Video in commit `f445e15231` (AnthonyF), citing a hang. Not tried on our unit; anything that adds an isochronous endpoint should test for it first. [external, unverified] (`../research/podbox.md`)
58. **Isochronous endpoints: used by Apple on this chip, unproven under Rockbox.** Apple's 5G firmware 1.2.1 and 1.3 enumerate a UAC1 *source* with an isochronous IN endpoint (EP1 IN, 192 bytes, synchronisation none, 8-48 kHz). So the ARC core's isochronous IN has worked on the PP5022 [apple-RE] (`osos.bin` `0x69DFB8` / `0x6A1FAC`). Isochronous OUT and the real endpoint count (`DCCPARAMS` bits 4:0; Rockbox assumes 3) are unknown. podbox's "hang when the host configures the isochronous endpoint" is most likely in Rockbox's code, not the silicon [hypothesis]. Our driver treats an isochronous TR_ERR (a normal missed packet; Linux ignores it) as fatal and flushes with interrupts off. `prime_transfer()` flushes and rebuilds a still-primed chain and spins up to 3 × 2 ms. `usb_drv_ep_deinit()` leaves the disabled direction as control type. `usb_audio` runs `dsp_process()` in the interrupt. Settle it with the bench probe in `../research/usb-digital-audio.md` §7. The rules are host-tested (`tests/usbaudio`, 2026-11-05) and the probe is built (`--usb-isoprobe`, variants A/B/C; bench sheet `../research/usb-isoprobe-bench.md`); not yet run on silicon. Our USB IDs: `usb.md` §7.1.
59. **The core can be a USB host; this board probably cannot.** Apple's 5G firmware has an EHCI-style host stack (root hub, hub and PTP camera drivers) for the camera connector [apple-RE]. On the USB-C mod, CC presents a sink and VBUS only feeds the charger. So host mode also needs Rp on CC and a switched 5 V supply [hypothesis] (`../research/usb-digital-audio.md` §4).
49. **Our bootloader (`bootloader/ipod.c`) never reads the battery.** Its `adc_init()` sits in `#if 0`. It brings up the LCD and backlight, initialises ATA, mounts and loads the firmware whatever the cell's voltage. A flat cell that has recovered at rest therefore reaches the firmware, which must make the battery decision itself (the boot battery guard, `docs/hardware.md`). [ours] (source reading, 2026-10-22; not changed: bootloader edits need the owner's sign-off)
50. **The FAT layer's sector is not the BPB's on the 5.5G.** With `MAX_VIRT_SECTOR_SIZE` the file layer works in 512-byte sectors (`fat_file_sector_size()`, `LOG_SECTOR_SIZE`) while `fat_get_bytes_per_sector()` returns the BPB's 2,048; code that sized a one-sector file by the latter skipped its write, and the owner's unit carried 0-byte `.rename_intent` and `.bootbatt` files. [silicon] (device backup 2026-10-23; host model `tests/fatcrash/fsreplay records`)

## Sleep and power, from Apple's code (2026-11-05)

60. **Apple's sleep code runs from IRAM because SDRAM is in self-refresh.** It sets `XMB_RAM_CFG` bit 22 and waits for bit 30 before it gates clocks, and reverses that only after the PLL is back. Any sleep routine that copies this must keep its code, stack and data out of SDRAM until bit 30 clears. [apple-RE] (`apple-power.md` §2.3); the self-refresh meaning is [hypothesis] (open question #39)
61. **Apple never sleeps the core with a USB cable in.** It spins at the crystal clock on `0x7000_0028` bit 2 and `CPU_INT_STAT` instead of `PROC_SLEEP`. A soft sleep should do the same or hand the USB case to the USB handler. [apple-RE] (`apple-power.md` §2.3)
62. **Apple's power-off never rewrites `OOCC1`'s wake enables.** It sets only `GOSTDBY` (or `TOTRST`) on a shadow read at boot. Ours writes `GOSTDBY | CHGWAK | EXTONWAK` (quirk 39); both work, but the shadow approach cannot leave a unit unable to wake. [apple-RE] (`apple-power.md` §3.3)
63. **`hibe` in the partition directory is Apple's suspend-to-disk image**, and `0x4001_FF10` = 8 at entry means "resume from it". A bootloader or kernel that scribbles on the last 256 bytes of IRAM can break Apple's resume, as quirk 6 already says for its boot flag. [apple-RE]; the ROM's part is [hypothesis] (open question #47)
64. **Apple never idles awake on the crystal.** Its clock governor clamps to 26–80 MHz on the PLL. Only light sleep runs from the 24 MHz crystal with the PLL off. ProkBox's 24 MHz-PLL-off idle is outside anything Apple shipped, so it is ours to prove; dark FLAC has run there for hours [silicon] (`../design/p19-placement.md` §4.1). [apple-RE] (`apple-power-catalog.md` §2.1)
65. **Apple's governor wakes the COP every 10 ms pass while the audio engine runs** (`osos 0x100C_FB08`), after reading both idle totals. It stops while the audio-stop hold `0x1493_7139` is set (disk mode). The pulse exists because Apple's COP adds its idle time only on leaving its idle routine, so a sleeping COP would otherwise read busy. "The COP is woken only by work" is true of Apple's design, not of its running firmware. Parking the COP fully (K-1) goes beyond Apple, and needs an idle read that sees a sleep in progress (quirk 81). [apple-RE] (`apple-dual-core.md` §5, corrected 2026-11-06)
66. **There is no global disk spin-down timeout in Apple's firmware.** Each client releases the disk with its own linger, from 0 ms to 30 s. A port that looks for "the" timeout will not find it. [apple-RE] (`apple-power-catalog.md` §2.2)
67. **Apple waits for the PMU ADC's done bit** (20–35 µs, then a poll of ADCS2 bit 7) before reading a conversion. Rockbox reads at once and relies on the I2C round trip for the delay. [apple-RE] (`apple-power-catalog.md` §2.8)
68. **`osos 0x1028_4374` is `AlarmTask`, not `PCFPowerMgr`.** It handles the alarm beeps and the low-battery message `0x94`. `PCFPowerMgr` (`osos 0x1028_4FF4`) only programs the interrupt masks and blocks on the PMU interrupt. It corrects `apple-power.md`'s first edition. [apple-RE; the task names by table position: hypothesis]
69. **Apple turns the codec's master clock (`DEV_EXTCLOCKS`) on and off with codec power**, and clears `DEV_I2S` when it stops the audio engine for disk mode. Rockbox leaves both on for the whole boot. [apple-RE] (`apple-power-catalog.md` §2.4, §2.7)
70. **A self-refresh routine has to be written without a stack.** A C function in IRAM still pushes and pops its frame on the caller's stack, which is in SDRAM; between the request (`XMB_RAM_CFG` bit 22) and the acknowledge clearing, nothing may touch SDRAM. The bench row `psrf` uses a naked ARM routine that keeps everything in registers and an IRAM block, saves its registers before the request and restores them after the release. Reading `DMA0_STATUS` or the second engine's status acknowledges its interrupt (`data-paths.md` R9), so a pre-flight check reads only the command words. [ours] (`clocks-power.md` §11)
71. **On the iPod Video, the start-up `DEV_EN` (`0xC200_0124`) already leaves every named-unused block unclocked.** FireWire (23), the LCD controller (26) and the Sansas' SD/ATA block (14) have no code that turns them on; `USB1` follows `USB0`, and the UARTs come on only for the dock's serial port. Awake clock gating beyond that means bits whose users are unknown (5, 8, 30, 31), which Apple keeps on too, except 5. [rockbox-derived] (`clocks-power.md` §11)
72. **Both cores share the FIQ vector's one target word.** A FIQ either core can take must read `PROCESSOR_ID` first (Apple: `osos 0x1000_015C`; ours: `fiq_by_core`, `pcm-pp.c`). Upstream's `crt0-pp.S` also gave the COP no FIQ stack of its own: `cop_fiq_stack` was the top of the CPU's. Developer builds now reserve 1 KB for it (`HAVE_CORE_LAYOUT_A`) [code; apple-RE].
73. **`next_tmo_check` is the only thing the tick's COP pulse was for.** Every other wake of a COP thread already goes through `core_wake()`. With the pulse gone (K-1), a COP thread that polls a flag by spinning or yielding still works, because it stays runnable; one that waits without a kernel object or a timeout would sleep for up to a minute. None does today [code survey, 2026-11-05: `cop_job.c`, `fe_be.c`, `codec_cop.c`].
74. **Upstream never unmasks the COP's FIQ.** The CPSR is per core, and only that core can write it. `crt0-pp.S` starts both cores with IRQ and FIQ masked (`0xdf`); `main.c` clears F on the CPU only, and `core_sleep()` re-enables IRQ only. A COP routed for a FIQ (priority bit, enable, vector all right) therefore takes nothing: sitting 4gh's P-1 read `cop_cpsr=0x5f`, 0 FIQs on either core, and DMA0 played one 8 KB piece then stopped. Layout (A) builds now clear F in the COP's own start-up (`system-pp502x.c`) [silicon, sitting 4gh, 2026-11-06; code].
75. **`0x6000_5014` ("RTC") does not count while awake** on the 5.5G: 0 at both ends of 11 s, no edge, against the PMU's RTC [silicon, sitting 4gh]. Apple converts it to seconds somewhere, but it is no free wall clock for us.
76. **The `CPU_CTL` count-mode stalls don't hold.** With IRQ and FIQ off at 80 MHz, `0x4200_000A` (10 µs) stalled 12 µs once and 0 µs twice; `CPU_CTL` read back with the count field cleared. Apple's self-timed waits (`0x48…`, `0x42…`, `0x41…`) cannot be copied; time waits with `USEC_TIMER` [silicon, sitting 4gh].
77. **Apple's sleep pad values are already the awake values here.** `0x7000_0010`/`14`/`18`/`1C` and `DEV_INIT2` read the words Apple writes before sleep, and `0x6000_6044` reads Apple's `0x3F` [silicon, sitting 4gh `preg`], so copying those writes saves nothing.
81. **A cross-core idle total needs a real snapshot, not a re-check of one word.** ProkBox's governor read a core's idle total and its sleep stamp, then re-checked only the stamp. The writer adds the slept time and then clears the stamp, two stores; a read that lands between them sees the new total with the old stamp and counts the same sleep twice. The next window then reads as 100 % busy (the negative delta clamps to 0), so the governor steps up for nothing. Fixed with a sequence counter, odd while the writer updates; uncached stores leave in program order, as corelock already assumes, so no barrier is needed. The `COP_CTL` sleep bit is no substitute: the clock change writes the other core's control register, and an aborted `core_sleep()` never sets it. [code] (`firmware/export/pgov_idle.h`, host-tested over every interleaving in `tests/ppgov/test_idle.c`; `../design/pp-governor.md` §17.6)
82. **Apple's disk channels and predictive spin-up predate 1.3.** Firmware 1.2.1 already releases channels up to 44, including the 2 s rapid-skip pre-spin; 1.2.x only lacks their debug names. The one 1.3 change found is the pre-spin hold, 10 s → 500 ms. This corrects the first edition of `apple-power-catalog.md`. [apple-RE] (`apple-disk.md` §7)
83. **Apple asks for the disk "only if it is already spinning"** for settings and play-count writes, album art and UI activity. If it is stopped, the work waits for the next spin-up; UI activity extends a spinning disk by 3 s but never starts it. Writes release with 0 ms. [apple-RE] (`apple-disk.md` §4)
84. **Apple's drive power-on has no fixed settle**: 4 ms after the rail, 10 ms after the controller clock, then a 10 ms poll for ready. Rockbox waits 250 ms, citing a core stall on early IDE access (seen on the Mini 2G). Whether the 5.5G stalls is untested (`apple-disk.md` T-FASTON). [apple-RE]
