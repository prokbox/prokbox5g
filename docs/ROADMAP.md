## Phase 10 device checks (the simulator can't exercise these)
- **Deleted files, dircache branch** (Phase 4 second review N2): the device build has `HAVE_DIRCACHE` compiled in, so the reverse scan goes through `dircache_search()`; the simulator has no dircache and takes the `file_exists()` branch. Check: delete one track over USB, eject; after the disconnect the track leaves Songs (no reboot), and `logf` shows "Entry no longer valid". Repeat with dircache on (developer mode). Then reboot: no reverse scan runs at boot (no disk activity after the boot-time walk).
- **Reverse scan and import times at the owner's library size**: the post-USB reverse scan (estimated 2-8 min at 50k), a changelog import after a rebuild (estimated 1-2 min), the boot-time directory walk. Record them in `docs/hardware.md`.
- **Power-off during a commit**: it powers off within ~12 s (the boosted sort at 50k) and never more than 60 s (`tagcache: power-off wait timed out` in the log otherwise); the next boot shows the library after a silent rebuild (estimated 15-45 min at 50k: time it), and play counts and resume points are still there. A power-off in an update commit's last stage (numeric indices, est. 2-4 s at 50k) finishes the commit instead: no rebuild at the next boot.
- **Files deleted outside a firmware USB session** (on another computer, in Apple's disk mode): not noticed until the next USB session or update. Check that they stay listed until then, that playing one skips it without a splash, and that the next USB disconnect drops them.
- **No gap while a commit or reload is pending**: add files over USB, eject, and start music at once (while the post-USB update still scans); playback never stutters, and the library updates within 1 s of stopping it.

## Architecture decisions
- **Hardware features catalog (owner, 2026-10-24):** `docs/hardware-features.md` lists every PP5022, BCM2722 and WM8758 feature (including ones Apple never used), its status and probe, and a "By phase" table. Every brief must name the blocks it could use (`docs/process.md`).
- **Use every hardware path, all of it ProkBox's own (owner, 2026-10-11).** Direction for the whole project: the bootloader, video decode, image processing and the rest done by ProkBox code, on whichever processor or block does each job best, so the hardware is used to its fullest:
  - **WM8758 codec:** volume, EQ, Sound Check gain, power states (Phase 15).
  - **BCM2722 VideoCore:** the screen path, H.264 decode (Phase 14), 2D work such as art scaling, reflections, blurs, compositing and Cover Flow (#60).
  - **COP (second ARM core):** offload where a measured job fits.
  - **Our own bootloader and flash-resident code:** toward no Apple code at any stage (#62).
  - **Definition of done (owner, 2026-10-11):** take a perfectly empty drive, install ProkBox, and it is Apple-free. First an **Apple-free drive** (our installer writes only the ProkBox bootloader and FAT32; our own BCM image, so the display no longer needs Apple's vmcs), then **no Apple code running at all** (our own NOR loader, behind #62's brick-safety gates).

  The rule that keeps it honest: **a job moves to a hardware path when a device measurement shows it is faster or cheaper on battery at the same fidelity**; the CPU path stays as the fallback, behind a flag. Expected to help stock 5G/5.5G units too (#43), and more so there: smaller batteries, hard drives that are costly to spin up, and the same CPU.

- **No skin engine in our UI** (2026-10-06): the shell, and Now Playing from Phase 5, draw natively. Nothing new depends on Rockbox's skin engine or themes. It's removed from the `HAVE_IPOD_UI` build in Phase 9, once the stock WPS hand-off is gone; developer mode's stock menus display unthemed. That reclaims code plus the boot-time skin buffers for the audio buffer.

- **Developer mode is minimal (owner, 2026-10-06):** only Rockbox's **debug screens** (hardware info, RAM and buffers, battery, database stats, logs) plus a USB and recovery path. The stock menus, file browser, settings UI, quickscreen, themes and plugin and theme browsers are **all removed** from the `HAVE_IPOD_UI` build.
- **Removal list (Phase 9; each lands when its replacement does):**
  - **Replaced by our UI:** the skin engine and themes; the stock WPS, quickscreen and pitch screen (P5/P6); `tagtree.c` and `tagnavi.config` (already replaced, P4); playback's album-art slots (P5/P7); `onplay.c` context menus and the playlist viewer and catalogue UI (P11); the plugin system and plugins (P7/P12, which frees the 512 KB plugin slot); the stock UI font; the splash, yes/no and progress UI.
  - **Dead on this hardware:** iAP, serial, the remote tuner and line-in recording; radio; recording and encoders; USB HID and audio; dircache.
  - **Better done elsewhere:** utf8proc normalisation (341 KB, move to sync time); the voice system. (The **language system stays**: owner COMP-6, 2026-10-07. v1 is English only, more languages later, so all shell strings use translatable IDs.)
  - **Rockbox's own UI layer:** root menu, menus, file browser, settings screens, stock list widget (developer mode is minimal).
  - **Kept:** kernel, drivers, playback and buffering, codecs (format breadth is a separate decision), tagcache, settings storage, bookmarks and resume, and the debug screens.
  - **Expected result:** roughly **half the stock firmware size**, and **0.5–1 MB+** back to the audio buffer beyond the audit's numbers. Measured in P9.
- **Library precompute file: 30 of 32 sections used (#59, 2026-10-10).** `database_lib.dat` (`apps/ipodui/libfile.h`) has room for `LIBFILE_MAX_SEC` = 32 sections, and #59's author-order books slice brought it to 30 (`LIB_PRE_SECTIONS` in `library.c`). A precompute that needs a 33rd section writes no file at all (`pre_sec_begin()`). **Before any phase adds sections** (Videos or Photos in Phase 14, series grouping if it returns), raise `LIBFILE_MAX_SEC` to 48 or 64 and bump `LIBFILE_VERSION`. The header grows (update `lib_hdr_size_check` in `library.c`), and so do the readers that walk all `LIBFILE_MAX_SEC` entries: the `tracks_hdr()` loop in `library.c` and the art cache's copy of the header (`artfmt.c`). The version bump costs one precompute, not a database rebuild.
