# Changes from upstream Rockbox (living ledger)

*Every way this tree differs from `upstream/master`, so rebasing (`docs/upstream-sync.md`) and sending patches upstream stay easy. First written 2026-10-09 at `main` `66bd3b4c51` / `p11` `ec1e371a51`; upstream base `2890d4a40d`. **Update at every phase close** (`docs/process.md`, "Ledgers"): run `scripts/upstream_changes.sh` (and `scripts/upstream_changes.sh main p11` while a branch is pending), reconcile the table below with the output, and fix any row that has drifted.*

**Columns.**
- **Guard**: the macro that compiles the change out of a stock build. `HAVE_IPOD_UI` is set by `tools/configure --ipodui`. `HAVE_METADATA_EXTRAS` is defined in `lib/rbcodec/metadata/chapters.h` when `HAVE_IPOD_UI` or `WARBLE` is set. `HAVE_IPOD_BOOTSCREEN` and `HAVE_IPOD_UI_DEVMODE` are set by `--ipodui`. `HAVE_IPOD_DOCK30` comes from `--dock30`. `HAVE_BATTERY_LEARN` is set by `--ipodui` on the iPod Video (#70).
- **Stock-identical**: *yes* means a stock (non-`--ipodui`) build compiles to the same code as upstream for that file (checked by the gate: stock `.text` is compared with `build/fw/.size-baseline`, and the stock bootloader by bytes). *No (by design)* means the change is unguarded on purpose. *n/a* means the file is not part of the firmware image (tools, simulator, host tests).
- Rows marked **(P11, merging)** exist only on branch `p11` (Phase 11), or grow there. They move to `main` when it merges.

Counts below are from `scripts/upstream_changes.sh` (399 files on `p16` at its close, 2026-10-22; 110 files on `main` 357a6bf6fa, which carries p11; 142 on `p9` after the Phase 9 Part 1 integration, 2026-10-10; excluding `apps/ipodui`, `docs`, `tests`, `scripts`, `art`, `.claude`).

## 1. Shell-only additions (no upstream file touched)

`apps/ipodui/` is the whole new UI shell: screen stack, header, smooth list, panels and drift art, Now Playing, audiobook pages, library and precompute, art cache, Settings tree, Search, hold-SELECT menu, On-The-Go store, About/Legal/Reset, system screens (boot, USB, charging, unlit clock face), developer mode, and the shell's fonts (`apps/ipodui/fonts/`, TeX Gyre Heros via `convttf-shell.c`). It compiles only when `HAVE_IPOD_UI` is set (listed in `apps/SOURCES`), so upstream never sees it and it can never conflict in a rebase. Also ours alone, outside the firmware tree: `docs/`, `tests/` (host tests, UI scripts, goldens), `scripts/` (gate, simulator capture, forgejo client), `art/` (artwork generators) and `.claude/` (agents and skills).

#### 2.29.2 19-1c: codec placement, decoding pinned to the CPU (branch `p19-1c`, 2026-10-24)

**Owner decision (2026-10-24): decoding is pinned to the CPU (PP1) permanently, with no CPU↔COP migration; the UI moves to the COP in a later package.** The default is therefore the plain path: no load is bound to the COP's view (`&ci` as upstream, no `ci_cop` shims, no field copy-back, no worker, nothing reserved at the top of the codec slot: the codec gets those 12,288 B back), and MP3's synthesis runs inline (`cop_assist` false). Option B + D of `docs/design/p19-placement.md` section 4 survives as **developer A/B modes only** (M-2): "2nd core" (Fit-2, the old default) and "by screen". The default never binds a load, never observes the screen, never logs a placement.

**(i) The A/B modes.** A load taken by an A/B mode is bound to `ci_cop` with the worker stack reserved, and `codec_cop_run()` picks the core per run. In "by screen", dark (the backlight off and the panel asleep after `lcd_sleep()`) runs on the CPU and lit runs on the COP. The rule re-selects at the first run after a load (playback start, a codec change; no hold) and at each track boundary (a new `Q_CODEC_RUN`), which moves the decode only when the screen state has held 30 s. It never re-selects at a seek's re-run, never by a reload, and the dim window moves nothing. The pure rule is `apps/codec_place_core.c` (host test `tests/codecplace/`, which also runs `codec_cop.c` itself on stub headers). The CPU branches of `codec_cop.c`'s callbacks copy the playback fields back into `ci_cop` (a run on the CPU through `ci_cop` left `curpos` stale after `advance_buffer`/`seek_buffer`, a latent bug of the old fallback path too), and the id3 alias follows the run, not the worker. A mode change takes effect at the next codec load.

**(ii) D, the main win, in every mode:** on a full PCM buffer the codec sleeps until the level drains to a low watermark (half the band above the boost watermark, never under 0.25 s of it) instead of polling at HZ/20; a message still ends the wait at once. The playback FIQ cannot post to the codec's queue, so the wake is a deadline computed from the drain rate (`pcmbuf_full_wait_ticks()`); an early wake only recomputes it.

**(iii)** `struct codec_api` gains `cop_assist`: false by default; true only for a run an A/B mode puts on the COP. `mpa.c` reads it at the run's start: inline synthesis, or the COP thread as before. Host test `tests/mpainline/` (review M1) builds `mpa.c` and libmad for the host twice, once with the second-core path compiled in (the thread on a pthread) and once without (upstream's single-core path). Inline equals the single-core path bit for bit: one run, a seek, and gapless pairs with the switch flipped either way around the thread. Upstream's thread loses one 1,152-sample frame at each run start and seek (it reads `synth.pcm.length` before the thread writes it); the pinned default no longer takes that path.

### 2.32 The JPEG decoder's restart bound (branch `p19-jpeg-oob`, 2026-10-24)

Two upstream bugs in the bit-serial entropy decoder, one cause (`docs/research/bcm2722/jpeg-spike.md` §12 and §15 on `p19-bcm-prep`; `docs/upstream-backports.md` on `main`). On a restart, `search_restart()` set the bit count to `marker_ind`, the bits read since the marker, with no bound. A marker met early (a corrupt file) makes that 8 + 16 for each fill since, past the buffer's width. The decoder then shifts by more than the word (undefined in C). `peek_bits()` and `get_bits()` then see different bits, so the slow Huffman walk starts below the length's first code, and `pub[]` is read at a negative offset, 1,044 B before `struct jpeg` [host, ASan, with the state first in the work area as on `p19-bcm-prep`].

### 2.39 USB plugged in while paused: no OOM panic (branch `p19-usboom`, 2026-10-26)

### 2.41 Settings saves that never lose the settings (branch `p19-cfgsafe`, 2026-10-26)

Device (build 207956fb84): `config.cfg`, `config.cfg.new` and `config.cfg.old` all 0 bytes after two freezes and resets. The stock scheme writes `.new` with `O_TRUNC` (FAT records the size only at close, so a save cut before its close leaves 0 bytes), and the next boot renames `.new` over `config.cfg` unchecked, the good file going to `.old` and, a boot later, away. Three cut saves lose everything. A changed setting was also written only when the disk next went idle, so a reset a few seconds after a change lost it (Clicker). Now a save writes `config.cfg.tmp` whole, fsyncs it and renames it over the file at once; the boot never promotes an empty file and puts `.old` back over a missing or empty one; a change is written ~2 s later (at most 8 s while changes keep coming).

### 2.42 iAP fitted to the player: small static buffers, lazy thread (branch `p19-iapfit`, 2026-10-26)

The stock 0.8.0 shape (`--dock30`) had `_end` 1,548,656 B, over the 1,500,000 B cap. The costs were iAP's static 64 KB RX buffer, its 8 KB thread stack and 2.4 KB of soft-double libgcc. A first version (32868becef) allocated the buffers on demand. Review found that it caused a playback gap at docking, that a stray 0xFF started a 73 KB allocation, that lost queue events could leave iAP dead, and that it made a cross-thread stop inside buflib's walk. It was replaced by this one (option A): the buffers stay static but sized for the player, and the thread comes up lazily with no allocation. Stock-shape `_end` is now 1,487,216 B (64 and 32 MB; 1,483,120 B with a 1.5 KB RX buffer, which was not taken: a dropped accessory packet cannot be tested without hardware). The protocol logic is untouched. See `docs/hardware.md`, "iAP memory".
