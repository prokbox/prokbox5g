**Goal (owner, 2026-10-19):** sleep and wake like the stock firmware, *"an important part of feeling like a real alternative"*; *"I rarely remember the base firmware showing me the full boot."* Today hold PLAY runs `sys_poweroff()` (`ui_main.c` `global_hold()` on `p16`), so every start is a full boot through Apple's ROM and our bootloader. Stock use is play, pause, sleep, wake. P18 makes it:

1. **Sleep with RAM kept (#86).** Hold PLAY, or a paused idle timeout, puts the unit into a *soft sleep*: screen, video chip, codec and storage off, both cores asleep at 24 MHz with the PLL off, the kernel frozen, SDRAM kept refreshed. A button press brings back the same screen, the paused queue and the audio buffer **in about the time a backlight wake takes today (0.37 s for the small hello_dma image [silicon, S30]; ~0.39–0.41 s estimated with the resident video image, which has not run on silicon yet [estimate], Revision 2)**, with no boot glyph.
2. **Fall back to a real power-off after a long sleep (#86).** After `SLEEP_DEEP_AFTER` (⚠️ Q1) or on a low battery, the soft sleep becomes today's PMU standby, and the next wake is a full boot that P16's boot window hides.
3. **Cost little per day asleep**, measured on silicon (§4.0), with a time-boxed deeper tier (32 kHz with SDRAM self-refresh) only if the measured soft-sleep current is over budget (⚠️ Q5).
4. **Run the CPU at 24 MHz with the screen lit** now that full-width pushes go by the second DMA engine (#113, R10), and **power the flash adapter off** after a long idle and in every sleep (#114, A3).
5. **Trust the battery number** (#70): the learned discharge table validated by one full rundown, with sleep added as its own charge class and the busy weight measured instead of guessed.

## 2. Out of scope
- **Suspend-to-disk / hibernation** (the "boot-time window and hibernation later" note). After a PMU standby, Apple's ROM loads `osos` (Apple's OS and our bootloader, under 8 MB) to `0x1000_0000` (`boot.md`), over the low 8 MB that hold our firmware, so a RAM image cannot survive a power-off through the ROM ([rockbox-derived] `crt0-pp-bl.S` and [external] siggi `07`, via `boot.md`; not tested on silicon) (Revision 1, L2). A warm boot would need a disk image and a bootloader change; it is a later phase with owner sign-off.
- **Any bootloader change.** P18 needs none: soft sleep never leaves the running firmware, and the deep tier is today's power-off. A proposal that needs one goes to the owner first (standing rule).
- **Changing Apple's firmware or its recovery path.** Hold MENU at a full boot still starts Apple's firmware; the deep tier goes through the same cold boot.
- **Keeping the BCM powered while asleep** (re-audit C8) as a shipped default **unless** 18-3's gates pass (stage 5i proven, the power A/B favourable); until then it is a developer switch.

### 3.1 `firmware/export/power_sleep.h` (new): the platform's soft sleep
```c
/* Soft sleep (Phase 18-1): RAM kept, kernel frozen, both cores asleep.
 * Called on the UI thread only (the main thread, 8 KB stack in IRAM,
 * app-pp.lds :134-139), after ui_sleep_quiesce() returned SQ_SLEEP:
 * screen dark, codec in standby, drive off, every button released, no
 * cpu_boost (get_cpu_boost_counter() == 0) and no PLL hold. The BCM is
 * either cut (rq->bcm_cut_after_s == 0: the cut-only build, or stage 2
 * of the two-stage display sleep) or powered with the panel in standby
 * (stage 1, 18-3, a developer switch until its gates pass);
 * power_sleep() never touches it. Returns when a wake source fires or a
 * deadline ends. current_tick does NOT advance while asleep: thread
 * timeouts resume as if no time passed; wall time comes from the RTC. */
enum sleep_wake {
    WAKE_NONE = 0,
    WAKE_BUTTON,        /* a valid wheel packet with a button PRESS EDGE
                         * (a bit of 8-12 set that was clear before) */
    WAKE_VBUS,          /* USB or charger inserted (GPIOL bit 4) */
    WAKE_ALARM,         /* the RTC reached rq->alarm_rtc */
    WAKE_DEEP,          /* rq->deep_after_s elapsed, or the failure rule:
                         * caller powers off */
    WAKE_LOWBATT,       /* a timer-wake battery read at or under
                         * rq->low_mv (Q6 "reaches", Rev 4a) */
    WAKE_HOLD,          /* hold switch off, only if rq->wake_on_hold */
    WAKE_BCM_CUT,       /* rq->bcm_cut_after_s elapsed: the caller cuts the
                         * BCM (lcd_sleep()) and calls power_sleep() again
                         * with the remaining deadlines; never shown */
};
struct sleep_req {
    uint32_t deep_after_s;    /* 0 = no deep timer */
    uint32_t alarm_rtc;       /* seconds since 2000, 0 = none */
    uint32_t bcm_cut_after_s; /* 0 = the BCM is already cut (Rev 3, M1) */
    uint32_t hold_wake_s;     /* Q12: Hold-off wakes while the time since
                               * entry is under this (SLEEP_HOLD_WAKE_S,
                               * 600); 0 = never. power_sleep() reads the
                               * RTC by the raw path at every Hold edge
                               * and takes "since entry" from it (Rev 4a) */
    uint16_t low_mv;          /* 0 = no battery check; wake at mv <= low_mv */
    uint16_t poll_s;          /* timer-wake period (fallback polls, battery,
                               * alarm, deadlines); SLEEP_POLL_S = 60 */
    uint8_t  buttons_at_entry;/* button bits 8-12 (>> 8) as the driver last
                               * saw them: 0, or only PLAY still held from
                               * the hold that started the sleep (Rev 4, N6);
                               * the press-edge rule starts from it */
    bool     wake_on_hold;    /* developer: Hold-off always wakes */
};
struct sleep_result {
    enum sleep_wake why;
    uint32_t slept_s;       /* RTC difference */
    uint16_t timer_wakes;   /* poll wakes taken */
    uint16_t spurious;      /* source-40 or GPIO interrupts that were no
                             * wake source (no packet ready: an I2C
                             * completion; a release, a touch, 0x3A,
                             * 0xFFFFFFFF; a press with Hold on). Only the
                             * bad ones count toward SLEEP_SPURIOUS_MAX:
                             * no packet, 0x3A/0xFFFFFFFF, out of step, a
                             * GPIO that changed nothing (Rev 4a) */
    uint16_t resyncs;       /* out-of-step packets resynchronised */
    uint8_t  wake_buttons;  /* WAKE_BUTTON: the pressed bits (>> 8); the
                             * shell swallows them up to their release */
    uint8_t  hold_edges;    /* Hold changes seen while asleep */
    uint16_t last_mv;       /* last raw battery reading, 0 = none (Rev 4,
                             * N1: seeds the battery filter at wake) */
    uint32_t sdram_crc_ok;  /* developer builds: guard-region check, 1/0 */
};
bool power_sleep_supported(void);  /* false in the sim's stock build */
void power_sleep(const struct sleep_req *rq, struct sleep_result *out);

/* Pure, host-tested (Revision 3, H1; Rev 4a: in firmware/export/
 * sleep_wake_core.h with sleep_classify(), sleep_poll_deadline() and
 * sleep_req_remaining(), firmware/common/sleep_wake_core.c, so
 * power_sleep() never includes apps/): one wheel event against the
 * previous button bits. Returns the packet's class, sets *press_edge to
 * the newly pressed bits (0 = no wake) and updates *prev. pkt_ready is
 * WHEEL_STAT bit 26: false = source 40 without a packet (an I2C
 * completion or noise). */
enum wheel_pkt { PKT_NONE, PKT_VALID, PKT_IGNORED, PKT_OUT_OF_STEP };
enum wheel_pkt sleep_wheel_packet(bool pkt_ready, uint32_t pkt,
                                  uint8_t *prev, uint8_t *press_edge);

/* Revision 1, H1 (wording fixed in Revision 3, M4): kernel-free PMU
 * access for use inside power_sleep() only (interrupts masked, tick
 * frozen). It drives the PP's own I2C block at register level (the
 * registers i2c-pp.c uses; no bit-banged GPIO) with no mutex, no
 * yield(), no current_tick. The block moves at most 4 bytes per
 * transaction (quirk 22), so the 7-byte RTC read is one address write
 * (0x0A) and then two block reads of 4 and 3 bytes, the split
 * i2c_readbytes() already makes (i2c-pp.c :173-197). Each wait is
 * bounded by USEC_TIMER (1 MHz, independent of the core clock) or, if
 * D2 shows USEC_TIMER stops while the core sleeps, by a loop count
 * calibrated at 24 MHz. Returns false on timeout (the caller treats it
 * as WAKE_DEEP). In firmware/target/arm/pp/pmu_raw-pp502x.c (new). */
bool pmu_raw_battery_mv(uint16_t *mv);   /* ADC ch. 2: write 0x2F, read 2
                                          * bytes at 0x30; x 6000 >> 10 */
bool pmu_raw_rtc_seconds(uint32_t *s);   /* RTC 0x0A-0x10 (4 + 3 bytes),
                                          * seconds since 2000 */
```
- **Raw path rules (H1):** called only from `power_sleep()` with the normal I2C driver idle (its mutex free, asserted before masking interrupts); after wake, the cached ADC value is invalidated (a new `adc_invalidate()` in `adc-ipod-pcf.c` sets each channel's `timeout` so `_adc_read()` :41 reads fresh; a guarded edit with a ledger row) so the kernel path reads fresh. Host test: the transaction state machine against a scripted bus (ACK, NAK, a held-low line → timeout false, never a hang; the RTC read issues exactly one address write and two block reads of 4 and 3 bytes).
- **Wheel packets inside the sleep (Revision 3, H1).** While asleep, IRQs stay masked at the core (as Rockbox's `core_sleep()` does: `PROC_SLEEP` wakes on any source enabled in `CPU_INT_EN`/`CPU_HI_INT_EN`, and the handler does not run) [rockbox-derived], so `ipod_4g_button_int()` never sees these packets; `power_sleep()` reads them itself. On each wake with source 40 pending: if `WHEEL_STAT` bit 26 is clear, it is not a packet (an I2C completion from the raw path, or noise): `spurious++`, no wake. Otherwise read `WHEEL_DATA`, re-arm exactly as the handler does (`WHEEL_STAT |= 0x0C00_0000`, `WHEEL_CTL = 0x400A_1F00`), and pass the packet to `sleep_wheel_packet()`: `(pkt & 0x8000_00FF) == 0x8000_001A` is valid; `0xFFFF_FFFF` and type `0x3A` are ignored (`spurious++`); anything else is out of step and gets Rockbox's resync (`input.md` §3, the 2 ms wait by `USEC_TIMER`), `resyncs++`. A valid packet wakes **only on a press edge**: a bit of 8–12 set that was clear in the previous packet (`prev` starts at `rq->buttons_at_entry`, which must be 0). So PLAY's release after the hold, a bare touch (bit 30 with no button bit), a wheel turn and a still-held button never wake; Hold on (GPIOA bit 5 low) overrides everything. The raw I2C path runs with source 40 masked in `CPU_HI_INT_EN`, and its pending flag is ignored until `WHEEL_STAT` says a packet is ready; **after every raw read, before `PROC_SLEEP` again, the loop re-checks `WHEEL_STAT` bit 26 and handles a packet that arrived during the read** (Revision 4, N7), so a press during a poll's I2C transaction is never left waiting for the next interrupt. A `spurious` count over `SLEEP_SPURIOUS_MAX` (start 1,000 per hour) is the failure rule (→ `WAKE_DEEP`).
- **The waking press is swallowed (H1).** `wake_buttons` goes back to the shell; `ui_wake_restore()` sets the input layer's swallow mask (the pattern of `sleep_on_release` in `global_hold()`, `ui_main.c` on `p16`), so every event of those buttons, including a long press and the release, is dropped until all of them read released. At exit `power_sleep()` also resets the driver's wheel state through `clickwheel_sleep_exit()` (new, `button-clickwheel.c`: `wheel_position = -1`, `int_btn` = the last packet's buttons), so the first touch after a wake is not a jump from the stale absolute position (a phantom scroll).
- **Hold and the wheel controller (Revision 3, H2).** Rockbox powers the opto off under Hold and re-inits it on release from the tick (§1); with the tick frozen, a Hold-off would leave the buttons dead until the next poll (60 s). Two designs, the first by default, chosen by D2/D3:
  1. **Hold as an edge interrupt** (GPIOA bit 5 on `GPIO0_IRQ`, high source 32, polarity flipped per edge as the VBUS handler does, `interrupts-timers.md` §5) [hypothesis until D2]: on Hold-on, `DEV_EN &= ~DEV_OPTO`; on Hold-off, `power_sleep()` runs the full opto bring-up (`input.md` §2, through `clickwheel_sleep_opto_init()`, the existing `opto_i2c_init()` made callable, with `udelay` by `USEC_TIMER`) and keeps sleeping (Q2: Hold-off itself does not wake), so the next press wakes by interrupt.
  2. **Fallback: the opto stays powered through the whole sleep**, whatever Hold says; **if Hold is already on at entry, the driver has already turned the opto off, so entry brings it up with the full bring-up first** (Revision 4, N5); a packet while Hold is on is classified and dropped (no wake, counted in `spurious`). Used if D2 shows GPIOA does not interrupt from `PROC_SLEEP`. Its cost (the wheel controller's own current, unknown, `input.md` §4, plus a wake per accidental press in a pocket) is a D3 row.

  Either way, at exit `DEV_OPTO` matches the switch (on iff Hold is off) and **`clickwheel_sleep_exit()` syncs the driver's Hold tracking** (Revision 4, N1: `button_read_device()`'s `static bool hold_button`, `button-clickwheel.c` :454, is hoisted to file scope and set to the current `button_hold()`), so the driver's next tick sees no change and does not run `opto_i2c_init()` again (revision 3 called that re-run "harmless" without evidence: it resets the controller with `DEV_RS` and could drop the packet of the press that follows). If the switch differs from what the driver saw at entry, `clickwheel_sleep_exit()` calls `backlight_hold_changed()` once, as the driver would have. The poll still reads Hold, but only as the backstop, never as the Hold-off path. D2 row and script below.
- **Sequence inside `power_sleep()`** (18-1 implements, [ours] built from [rockbox-derived] pieces): every `cpu_pll_hold` released and `cpu_boost` count 0 (asserted; refuse otherwise, logged); **park the COP by handshake (Revision 1, M3):** the CPU posts a park request; the COP acknowledges only when its queue is empty, no `cop_job` is pending or running and it holds no corelock, then enters `PROC_SLEEP` with tick wakes off; the CPU waits for the acknowledgement **and** `PROC_CTL(COP)` bit 31 (asleep) before going on, with a bounded wait (refuse → `WAKE_DEEP`); Timer 1 stopped (`TIMER1_CFG = 0`); `CPU_INT_EN` reduced to the wake set; `CLOCK_SOURCE = 24 MHz` and the PLL powered off (the existing `CPUFREQ_DEFAULT` path); `PROC_SLEEP` in a loop; on each interrupt classify it, on a poll wake (`PROC_WAIT_CNT` seconds unit, or Timer 2; **unproven at 24 MHz with the PLL off, and D2's first test**, Revision 1 H4) read the battery and the RTC through the raw path and poll Hold/buttons as a **fallback for wake sources that do not interrupt**; on a real wake restore the interrupt mask, Timer 1 and the COP's tick wakes, in the reverse order.
- **Poll deadline (Revision 1, M5):** each poll is programmed for `min(poll_s, alarm_rtc − now, deep_after_s − slept, bcm_cut_after_s − slept)` (the last term only while `bcm_cut_after_s` ≠ 0, Revision 3 M1), so an alarm or the deep timer fires on time, not up to 60 s late. Cost: a 60 s poll is one wake of a few ms a minute, est. ≪ 0.01 mA against Q5's 2.5 mA (an estimate, L3; D3 measures it).
- **Wake-source rule:** a source that is not proven to interrupt from `PROC_SLEEP` on silicon (§4.0 D2) is covered by the poll; the poll period is the worst-case wake latency for that source, so a source with only poll coverage is not a Q2 wake source until it is proven or the poll is short enough (owner round, with the number).
- **Identity vs validity:** `slept_s` is from the RTC (identity of time); nothing caches `current_tick` across the call.
- **Trace:** `ui_log("sleep", "wake why=%d s=%lu polls=%u spurious=%u crc=%lu")` from the shell after the call (firmware cannot trace); `UPDATE_TRACE("sleep …")` in the sim. A trace rule that finds no `sleep wake` line in a sleep script fails.
- Host test `tests/sleep/`: the classifier (interrupt status + the `sleep_wheel_packet()` result + Hold + VBUS + RTC + battery → `enum sleep_wake`) as a pure function `sleep_classify()` over a table, including Hold on (no wake), Hold off with and without `wake_on_hold`, simultaneous sources (priority: LOWBATT > VBUS > ALARM > BUTTON > HOLD > DEEP > BCM_CUT). **Revision 3 rows (H1, H2):** PLAY release after the hold (`prev` = PLAY, packet with no button: no wake); a bare touch (bit 30 only: no wake); a wheel turn (position change, no button: no wake); a button still held from before (no edge: no wake); a press edge (wake, `wake_buttons` = that bit); two buttons pressed in one packet; source 40 with `WHEEL_STAT` bit 26 clear (an I2C completion: `spurious`, no wake); `0xFFFF_FFFF` and type `0x3A` (ignored); an out-of-step value (resync, no wake); a press with Hold on (no wake); Hold-off edge then a press (wake, `hold_edges` = 1); the spurious cap (→ `WAKE_DEEP`).

### 3.2 `apps/ipodui/sleep.h` (new): the shell's sleep policy

```c
    SLEEP_HOLD_PLAY,     /* global_hold() */
    SLEEP_IDLE,          /* handle_auto_poweroff() path (Q4) */
    SLEEP_TIMER,         /* P12 Sleep Timer */
    SLEEP_UNPLUGGED,     /* left the charging screen by unplugging (Q9) */
};
enum ui_sleep_tier { TIER_SOFT, TIER_OFF };
/* Any thread: posts SYS_SLEEP_REQUEST to the UI queue; never sleeps
 * inline. */
void ui_sleep_request(enum ui_sleep_reason r);
/* Pure policy (host-tested; Rev 4a: sleep_tier_pick() in sleep_core.c

enum ui_sleep_tier ui_sleep_tier(int mv, int pct, bool charger,

 * at once, PLAY's release awaited, the sleep-entry window (Q7, capped by
 * SLEEP_MAINT_MS or SLEEP_WALK_MS), then the sleep-entry persistence
 * subset (section 4.3, never clean_shutdown()) and drive, codec, display

 *   SQ_SLEEP  ready: the caller calls power_sleep();

 *             the caller runs sys_poweroff();

enum sleep_quiesce ui_sleep_quiesce(void);

 * was cut, sleep-out if it was in panel standby), the last frame pushed,
 * the screen lit; the waking buttons swallowed up to their release; drive
 * and codec stay off until their first use. */
void ui_wake_restore(const struct sleep_result *r);
uint32_t ui_sleep_deep_after_s(void);   /* Q1, scaled by IPOD_BATTERY_MAH:
                                         * min(24 h, stock, 5 % of the cell
                                         * at the sleep current), the
                                         * current 2.5 mA until D3
                                         * measures it, floor 1 h (Rev 4a;
                                         * sleep_deep_after_s() in
                                         * sleep_core.c) */
```
- **One thread (Revision 3, M1).** Request handling, `ui_sleep_quiesce()`, `power_sleep()` and `ui_wake_restore()` all run on the **UI thread** (the main thread: `main()` calls `ipodui_main()`, `apps/main.c` :277 on `p16`; its stack is the 8 KB `.stack` in IRAM, `app-pp.lds` :134–139, filled with `0xDEADBEEF` by `crt0-pp.S` :299–300 [rockbox-derived]). There is no sleep thread. `power_sleep()`'s frame (the request, the result, the loop's locals) is budgeted at ≤ 256 B of that stack; 18-1 reports the measured high-water mark (`stackbegin`'s `0xDEADBEEF` fill) before and after a sleep. Jobs in the sleep-entry window run on their own threads (tagcache thread: commit, walk, rebuild; art thread: chapter books, top-up, rotation), as they do in P16's paused window.
- **"BCM off" depends on the display-sleep stage (M1).** Cut-only (the default until 18-3's gates pass): `lcd_sleep()` cuts the BCM in quiesce step 4 and `bcm_cut_after_s` = 0. Two-stage (18-3, developer switch): step 4 puts the panel in standby with the BCM powered, `bcm_cut_after_s` = `SLEEP_BCM_CUT_AFTER`; on `WAKE_BCM_CUT` the UI thread calls `lcd_sleep()` and re-enters `power_sleep()` with the remaining deadlines (screen stays dark, nothing logged to the user); a wake before it runs the panel's sleep-out, after it a cold start.
- **Boost discipline (Revision 3, M2).** The only boost the UI thread takes in entry is one `cpu_boost(true)` when the window opens, released by one `cpu_boost(false)` at the window's single exit, which every path leaves through: the window ends normally, a key (`SQ_WOKEN`), USB (`SQ_USB`), or the window's cap. `SQ_OFF` can only come after that exit (the steps it bounds follow the window), so it never carries a boost into `sys_poweroff()`. Jobs on other threads release their own boosts at their safe point. Before step 5 the UI thread checks `get_cpu_boost_counter() == 0` and no PLL hold, waiting within `SLEEP_QUIESCE_MS`, else `SQ_OFF` (logged `sleep refused why=boost n=`); `power_sleep()`'s assertion is the backstop (refuse → `WAKE_DEEP`). `ui_wake_restore()` boosts only while composing the first frame, one pair. On the device the counter is real; the sim has no counter (`system.h` :100), so balance there is checked by the `CPU_BOOST_LOGGING` lines in 18-1's review and on the device by the `sleep boost=` line logged before each `power_sleep()`.
- **Subscribers** use the existing event system (`events.h`): `SLEEP_EVENT_PREPARE` (synchronous; each subscriber finishes its flush before returning) and `SLEEP_EVENT_WAKE` (asynchronous). The full list, with what each does and does **not** do, is in §4.3 step 3 (Revision 1, H2); a writer not on it is a review failure (checklist 12).
- **No shutdown intent (H2):** sleep never calls `clean_shutdown()`, `tagcache_prepare_shutdown()` or `audio_stop()`; `ui_shutdown_intent` is never set by a sleep, so nothing has to clear it at wake. If a sleep falls back to `TIER_OFF`, the ordinary power-off path runs from the start.
- **No disk write at wake** (the "no disk writes at USB screen entry" spirit, and Q7): every write owed after a wake waits for the next natural disk wake.
- **Timers at wake (Revision 1, M1):** `ui_wake_restore()` calls `reset_poweroff_timer()` (else `last_event_tick`, `powermgmt.c` :1292, is stale and a VBUS or alarm wake sleeps again at once) and restarts P16's pause age through a new `maint_pause_restart()` in P16's `maint.c` (sets `paused_since` to the wake tick; agent B, §5), so the paused window does not open the moment the user wakes the unit.
- **The waking press is swallowed (Revision 3, H1):** `ui_wake_restore()` copies `r->wake_buttons` (and, Rev 4a, `rq->buttons_at_entry`: PLAY held into the sleep, whose release the driver delivers after the wake wherever it came; `sleep_swallow_arm()` in `sleep_core.c`) into the input layer's swallow mask (the `sleep_on_release` pattern in `global_hold()`, `ui_main.c` on `p16`); events for those buttons are dropped until each reads released, so a wake by SELECT does not also select and a wake by MENU does not also go back. `SQ_WOKEN` does the same for the key that cancelled the entry.
- **Fresh first frame (Revision 1, M6):** before the first push, everything on screen that shows time is redrawn from the RTC: the header clock (Time in Title), the unlit face, the live calendar tile, Now Playing's elapsed/remaining; **and the header battery glyph from the fresh level below (Revision 4, N1).**
- **Frozen-kernel state fixed at wake (Revision 4, N1).** Besides the wheel (§3.1), three pieces of state assume the tick ran:
  - **Battery filter:** `powermgmt.c`'s `voltage_avg`/`voltage_now` (:162) still hold the pre-sleep average. `power_sleep()` returns its last raw reading in a new `sleep_result.last_mv`; `ui_wake_restore()` calls a new `battery_wake_reading(mv)` in `powermgmt.c` (`reset_battery_filter(mv)`, :557, then the static `battery_status_update()`, :389, so `battery_level()` is fresh) **before it composes the first frame**; the scheduler is cooperative, so the power thread cannot run between the two. A wake with no raw reading (a refused read) falls back to `reset_battery_filter(_battery_voltage())` through the normal driver.
  - **`lcd_awake()`'s 50 ms guard:** it sleeps `lcd_state.update_timeout + HZ/20 − current_tick` when that is between 0 and `HZ/20` (`lcd-video.c` :1124–1127); with the tick frozen across the sleep the guard can add up to 50 ms to D4 though seconds have passed. A new `lcd_wake_aged()` in `lcd-video.c` (sets `update_timeout` to `current_tick − HZ/20`) is called by `ui_wake_restore()` when `slept_s ≥ 1` (the RTC proves the BCM has been off ≥ 50 ms); `SQ_WOKEN` (no sleep) keeps the guard.
  - **Backlight thread's LCD-sleep countdown:** step 1's backlight-off starts `lcd_sleep_timer` (`backlight.c` :202–230), which the backlight thread counts down and then calls `lcd_sleep()` (:720–725) from its own thread, possibly inside the entry window, racing the UI thread's step 4. A new `backlight_sleep_hold(bool)` (guarded) cancels the countdown and blocks its restart from step 1 until `ui_wake_restore()` lights the screen through `backlight_on()`, which cancels it anyway (:530). `lcd_sleep()` is then called only by step 4, on the UI thread.
- Host test `tests/sleep/`: `ui_sleep_tier()` over (mv, pct, charger, usb, supported) rows; `ui_sleep_deep_after_s()` for 400/600/3000 mAh and a measured current; the swallow mask (a wake by SELECT: press, long press and release dropped, the next SELECT acts; a second button pressed while the first is held is not swallowed).

### 4.2 18-1 Platform soft sleep (agent A firmware-platform, **opus**; own review before 18-2 merges)
- **`power_sleep()`** (§3.1) in `firmware/target/arm/pp/power_sleep-pp502x.c`, under `HAVE_POWER_SLEEP` (set by `--ipodui` on the iPod Video; documented in `hardware.md` "Build variants"; the stock build compiles unchanged).

### 4.4 18-3 Wake latency (agent A; sonnet after A's design; BCM work with the BCM session) (rewritten in Revision 1 from §9's answers)
- **The lever is the panel, not the upload.** Today's wake is a full panel power-on (~265 ms on panel 3; first command at 279.8 ms, S30 [silicon]) because `LCD_SLEEP` drives the panel's reset low (§9.2). A fast wake needs a **panel-standby mode** in our BCM image: sleep in/out by DCS `0x10`/`0x11` (panel 0) or `0x0007`/`0x0100` (panel 3), GPIO48 held high, the BCM kept powered at 27 MHz. Built in the test image only as CMD `0x43` with two depths (Revision 2, `bcm2722-reference/lcd.md` §5, `host-driver.md` "Panel standby" [ours; hypothesis]): *light* = display off, power circuits on; *deep* = the panel's whole off script; both keep GPIO48 high and should differ in current, not wake time. **Sleep-out as built is ~137 ms on panel 3 at either depth** (vc2sim; it keeps the display-on ramp waits 17 + 34 + 85 = 136 ms) against 267 ms cold: standby saves the reset pulse, the 110 ms wait and the bus resync, ~130 ms. Panel 0's light wake is a single DCS `0x29` (nearly free); panels 1 and 2 have only the deep depth (~137 ms). Shortening the ramp is a separate spike [hypothesis].
- **Two-stage display sleep [ours]:** a soft sleep first keeps the BCM up with the panel in standby (and the core asleep, once stage 5i proves a wake interrupt); after `SLEEP_BCM_CUT_AFTER` (⚠️ start 30 min, set from §9.1's A/B) it cuts the BCM as today. A wake inside the first stage skips the bootstrap, the upload and the panel power-on; and, if §9.5's SRAM hold passes, the frame push too.
- **Gates:** shipped only after (a) stage 5i (a proven BCM wake source) and (b) the power A/B shows the standby arm is worth its current against the cut over a typical short sleep; otherwise P18 ships the cut-only wake (≤ 0.5 s, D4) and this stays a developer switch.
- **The upload by E2:** ~17 ms vs ~34 ms unboosted by CPU (a wash boosted; §9.7). Kept small: worth doing only for the CPU's freedom during the upload, after the E2 image upload at boot is proven ((d) in §9's order).
- **The BCM's SDRAM** is let go at the cut and re-initialised at the next video `OPEN` (~12 ms) (§9.6).
- The first frame: refreshed from the RTC (§3.2), one full-width E2 push unless the SRAM hold makes it unnecessary.
- Acceptance: D4 ≤ 0.5 s with the cut; with panel standby, target ≤ 200 ms (Revision 2: the ~137 ms ramp leaves no margin under 150 ms once a frame push and the backlight are added; tighten only if a ramp spike shortens it); the log line `wake ms: bcm= panel= frame= lit=`.

### 4.5 18-4 Deeper tier spike (agent A, opus; **time-boxed to one session; runs only if Q5 fails**)
- **Question:** can the core clock drop to 32 kHz (`CLOCK_SOURCE = 0x2000_0000`, upstream's `CPUFREQ_SLEEP` sequence, `clocks-power.md` §4 [rockbox-derived]) for the whole sleep with SDRAM kept? At 32 kHz an SDRAM controller cannot issue auto-refresh at the rate SDRAM needs [hypothesis: refresh is clocked from the bus], so the controller would have to put the SDRAM in self-refresh first; the controller's registers are known only from an emulator's reading of Apple's ROM (`XMB_RAM_CFG` `0x7000_003C`, `0x7000_0030`; `memory-map.md` §2, PP open question 1) [external]. What clocks the timers in 32 kHz mode is unknown too (PP open question 9, `interrupts-timers.md`).
- **Spike:** with the drive off and the guard region filled, run the CPU at 32 kHz for 1 s, 10 s, 60 s from IRAM (code and stack in IRAM, no SDRAM access while slow; **a developer-only exception to rule 3's "IRAM is for codecs only"** (Revision 3, L2): the spike's routine (est. ≤ 512 B) lives in a developer build only and runs on the main stack, which is already in IRAM; a shipped deeper tier needs the owner's explicit exception with its measured IRAM cost, in its own review), then back to 24 MHz and check the CRC. A loss means self-refresh is needed: dump `0x7000_0030`–`0x7000_003C` and look for a self-refresh bit as Apple's sleep path uses it (static reading of `osos` 1.3, [apple] provenance, no code copied). Any loss only costs a crash and a full boot: the drive is flushed and off first.
- **Output:** a [silicon] finding either way in `pp5022-reference/` and `data-paths.md`; a shipped tier only with its own review.

### 4.7 18-6 Battery: calibration validated, sleep counted (#70) (agent B; sonnet; owner rundown)
- **Asleep as a charge class:** batcal today ignores off-time. A soft sleep is neither off nor idle-awake: `SLEEP_EVENT_WAKE` adds one *asleep* sample (duration `slept_s`, weight `BC_SLEEP_W16`), so a run that spans sleeps still fits. `BC_SLEEP_W16` and `BC_BUSY_W16` come from D3's 24 h drops and paired power-log runs (no meter, Revision 4) instead of the 1.5 estimate; a weight the method cannot resolve keeps its estimate and is flagged.
- **The full rundown (P10 procedure, `hardware.md` "Rundown"):** charge full, 30 s log interval, the fixed playlist, Hold on, screen off, until it shuts off; then compare the learned table with `power.csv`, and check the percentage at known hours on the next discharge. Owner task.
- **Battery per day asleep:** one 24 h soft sleep from a known level, read through the learned table: the number Q1 and Q5 use. Also a 24 h deep-tier (power-off) row for the floor.
- **M2 (Q10):** as built unless the owner says otherwise.

## 6. Device-reality checklist
1. **Compiled features:** `HAVE_POWER_SLEEP` only on the iPod Video `--ipodui` build; the sim uses the stub (§3.3), so the platform path (tick stop, COP park, interrupt plan) runs **only on the device**: D1/D2/D4 are its tests. `HAVE_DIRCACHE` stays off; the HDD variant takes the same sleep path with upstream's drive power-off.
2. **Memory:** no new reservation; soft sleep allocates nothing. The audio buffer, the resident BCM image and the loader's modules stay where they are, so wake costs no reload. The sleep-entry window takes memory only through P16's `maint_take()` with its floor rule (Q11 of P16). D1's 1 MB guard region is developer-only, taken while stopped and freed after, and shrinks the audio buffer until the next rebuild (§4.0). No statics over 1 KB (`struct sleep_req`/`sleep_result` live on the **UI thread's** stack, the 8 KB main stack in IRAM; `power_sleep()`'s frame ≤ 256 B, high-water reported by 18-1; Revision 3 M1).
3. **CPU:** wake boosts only while composing the first frame; the sleep-entry window is boosted and capped (`SLEEP_MAINT_MS`); no O(N) work at wake. 18-5 lowers the lit clock.
4. **Storage:** sleep entry: one flush of what a power-off flushes, then the drive off; wake: **zero** disk access until something needs it (the drive then powers on with its ≥ 250 ms wait, est. invisible because the audio buffer is full). Awake A3 power-off after `ATA_POWEROFF_IDLE`. The sim stub reproduces the order and the lazy power-on.
5. **LCD:** the screen goes dark first at entry; at wake one full-width E2 push of the unchanged frame, then the backlight; no animation.
6. **Threads and locks:** the request is posted from any thread; quiesce, `power_sleep()` and the wake run on the UI thread (no sleep thread, Revision 3 M1; the window's jobs run on their own threads while the UI thread services input, §4.3 step 2) with every other thread blocked on queues or timeouts (frozen tick: their timeouts do not expire while asleep). Before `power_sleep()`: no mutex held by the UI thread, the storage thread idle, the tagcache thread not inside a commit (suspended at a safe point, §4.3 step 3), the audio thread paused, the COP's worker idle. Wake order: CPU, then COP.
7. **Splashes:** none. Low battery, deep timeout and refused quiesce all end in today's silent power-off; a refusal is logged (`sleep refused why=`).
8. **Persistence:** every trigger runs **the named sleep-entry subset (§4.3 step 3)**, not `clean_shutdown()`'s persistence, at entry, on the UI thread, through `SLEEP_EVENT_PREPARE` (Revision 3, M3). Power cut or battery death while asleep: the state is what a clean power-off would have left. USB mid-entry: `SQ_USB`, the sleep is abandoned and the existing USB handler runs, with no write issued after the USB event (never a power-off; Revision 1, M2). Scripts: `-sleep-persist` (cut while asleep), `-sleep-usb-entry`.
9. **Scale:** independent of the library size; the sleep-entry window inherits P16's 50k costs and cap.
10. **Deferred work, per state:** an update owed at sleep (*ready*: the window may land it; *fresh*: the initial build continues in the window, then in later sleep-entry or paused windows; *dirty*: the rebuild starts in the next sleep-entry window instead of waiting for a boot that may be weeks away, Revision 1 H3, §4.3 table); each with a script and what the user sees after wake (the updated lists, or the old ones still browsable).
11. **Stock unchanged:** `powermgmt.c`, `power-ipod.c`, `ata.c` and kernel edits under `HAVE_IPOD_UI`/`HAVE_POWER_SLEEP`; stock `.text` byte-identical (with `english.lang` held equal).
12. **Existing paths doing the same job:** upstream's idle power-off (`handle_auto_poweroff()`) → routed to sleep under `HAVE_IPOD_UI`; the shell's charging sleep (`charging_sleep_prepare()`) stays for the charger case and shares its save order; `lcd_sleep()`/backlight timeouts (#51) unchanged while awake; sleep entry runs **the named subset (§4.3 step 3)**: `clean_shutdown()` is not called and its persistence is not reused whole (it stops audio and latches the shutdown intent, §1), and each subset item calls the same function the shutdown path calls, not a copy (Revision 3, M3); **the clickwheel driver's Hold handling** (`button_read_device()` :451–490, opto off under Hold, re-init on release from the tick) is an existing path doing the same job as the sleep's Hold handling: it stays for the awake case, `power_sleep()` takes over only while the tick is frozen and hands back with `DEV_OPTO` matching the switch (Revision 3, H2); **the wheel interrupt handler** (`ipod_4g_button_int()` :324) stays the only reader of packets while awake, `power_sleep()` the only reader while asleep (IRQs masked); **frozen-kernel takeovers (Revision 4, N1; `docs/process.md` item 12 since d2afdabf3f), each with what replaces it while the tick is frozen:**

## 10. Risks
- **The poll timer itself is unproven** (Revision 1, H4): `PROC_WAIT_CNT`'s seconds unit and Timer 2 at 24 MHz with the PLL off are [rockbox-derived] at best. D2's first test; 18-1 does not merge without it.
- **A unit that looks dead.** A wake source that does not interrupt from `PROC_SLEEP` would leave the user pressing buttons at a black screen. Mitigation: the poll (§3.1) bounds every source's latency; a source with poll-only coverage is not shipped as a Q2 wake until its latency is acceptable; the failure rule returns `WAKE_DEEP`; D2 runs before 18-2 merges.
- **SDRAM loss in a long sleep** (D1 fails at 8 h): a crash and a full boot, not data loss (persistence ran at entry, the drive is off). Mitigation: shorter `SLEEP_DEEP_AFTER`, then 18-4.
- **Interrupt and tick restore bugs** (a lost COP tick, a stale mask) show as stalls minutes later. Mitigation: own review of 18-1; a wake-sleep stress test (1,000 cycles, developer row) with the panic record on.
- **Sleep current higher than hoped** (PP5022 at 24 MHz with the cores asleep is undocumented): Q5 and 18-4 are the answer; Q1's scaling keeps a small cell safe meanwhile.
- **Stale boot stamp** written at sleep entry and a USB session after the wake: removal on the USB exit path and at the first write after wake, plus P16's digest and 10th-boot walk.
- **HDD units:** spin-up after wake (~1–2 s) happens only at the first disk access, behind a full buffer; record it in `storage-choices.md`, behaviour identical.
- **Stock-UI regressions:** the idle power-off reroute is a guarded upstream edit; the stock build keeps powering off.
