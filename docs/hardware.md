## Where power and time go (in priority order)
1. **Backlight and LCD.** These draw the most power. Default backlight timeouts should be short. Use LCD sleep. Don't redraw a screen that isn't changing.
2. **CPU boost.** At 80 MHz the CPU uses several times the current it uses at 30 MHz. Boost only while something is actually happening, such as an animation, a database build or a seek, and release it the moment that stops. `cpu_boost()` calls must always be balanced.
3. **Storage wake-ups.** Flash has no spin-up, but each burst of reads still wakes the controller and the CPU. Fill the audio buffer in large bursts, then let everything sleep.
   - **Buffering policy (owner, 2026-10-09).** Never stream data into memory in small pieces; fill in big bursts and sleep (lean rule 11 in `docs/process.md`).
     - **Audiobooks:** a large book file can't fit in the buffer, and that's accepted. A short stop of about a second to reload a chunk is fine when scrubbing outside the buffered range or moving forward. Prefer to **end each fill on a chapter boundary**, so seeks within a chapter never reload. Keep enough buffered ahead that normal listening never stalls.
     - **Songs and albums** are more nuanced: gapless album playback and quick track skips want whole tracks buffered ahead. Don't apply the audiobook rule blindly there.
     - Design and measurement belong to Phase 9b (buffer and power tuning), with on-device checks in Phase 10.
4. **Decoding.** MP3, AAC and FLAC are cheap at 30 MHz. Time-stretch, EQ, crossfeed and resampling all cost CPU. Turn them off by default and enable them per use (time-stretch only for audiobooks played above or below 1×).

## Rules for every change
- **Memory**
  - No large statics, because they permanently take RAM from the audio buffer. Allocate with `core_alloc` (movable) or from the buflib. Anything over about 4 KB needs a line in the budget table below.
  - Thread stacks are small, so never put big structs on the stack.
  - Buffers shared between the tagcache thread and the audio thread are a race. Each caller supplies its own buffer.
- **IRAM:** reserve it for codec and DSP inner loops. UI code never goes there.
- **LCD updates**
  - Use partial updates with `lcd_update_rect`. Full-width bands are fastest because they go in one burst.
  - The header bar repaints only when its content changes.
  - Animations run at a fixed frame budget (about 30 fps). Skip frames instead of falling behind.
- **Input:** block on input with a timeout (`button_get_w_tmo`). Never busy-poll.
- **Pre-compute at sync time, not at browse time.** Expensive work happens once, while the library updates in the background:
  - **Album art cache:** pre-scaled RGB565 files at the exact sizes the UI uses (list thumbnail, Now Playing, Cover Flow), stored in the hidden `.rockbox/artcache/` and keyed by album. Browsing then never decodes JPEG.
  - **Database:** tagcache with the RAM cache (`HAVE_TC_RAMCACHE`), loaded at boot and rebuilt incrementally at low priority while unboosted.
  - **Sort keys and audiobook metadata** (chapter count, duration) go in the database, so the shell never opens files just to draw a list.
- **dircache vs. tagcache**
  - The UI is driven by the database, so dircache is optional.
  - On a 1 TB library dircache can take several MB of RAM. Measure it, and turn it off if the RAM is better spent as audio buffer.
- **FAT32 on 1 TB**
  - Format with 32 KB clusters. That gives a smaller FAT, fewer FAT reads and faster mounting.
  - Rely on FSInfo for free space; never scan the FAT at boot.
- **Second core (COP)**
  - Investigate which threads run on the COP today.
  - Candidates to move there: album art scaling, database work, Cover Flow rendering.
  - Any change here must be measured before and after.
- **Battery:** the voltage-to-percentage tables in `powermgmt-ipod-pcf.c` were tuned for the stock cells. Since #70 the shell learns the discharge table itself from each full run-down (`HAVE_BATTERY_LEARN`, "Automatic battery calibration" below), so a 3000 mAh unit, or any stock one, calibrates with no lab step; a full discharge with the power log still checks it.

### Chapter table capacity (`AB_MAX_CHAPTERS`, #48)
Playback reads the playing track's chapters into one `struct audiobook_chapters` carved from the audio buffer at init (`apps/playback.c`), 8 + 68 B per chapter on ARM. The cap is set in `lib/rbcodec/metadata/chapters.h`: **255** in stock (17,348 B, `.text` unchanged), **1024** under `HAVE_IPOD_UI` and `WARBLE` (69,640 B, +52,292 B out of the audio buffer), or `-DAB_MAX_CHAPTERS=n` on the command line (never per file: every translation unit must agree). Longer books stop cleanly at the cap. A packed, variable-length table (P6) would replace the fixed one.

## Planning scale
- **Realistic library (owner, 2026-10-06):** about 1 TB, mostly FLAC, so roughly **30–40k tracks and 3–4k albums**. Budgets and reservations are sized for this.
- **Stress ceiling:** keep testing at **50k tracks / 5k albums** (`tests/perf/lib50k.sh`) as a safety margin.

## Build variants (Phase 9)

### Cache durability (#85, branch `cache-persist`, 2026-10-18; not release acceptance)

build. The active RAM library stays loaded while a second (candidate) one
is built in its own generation directory, with the view pool reserved

full path (`apps/ipodui/dbjournal.c`), never into a published master file.
The audio thread never does disk I/O or waits for a publication at a
track change (one RAM bind or a hand-off to the tagcache thread). The
tagcache thread owns all journal work (open, salvage, drains, compaction):
the storage thread's 2 KiB stack would not hold it. Drains use a 4 KiB
buffer on the tagcache stack (no allocation, so they run beside a full
audio buffer). Measured with `-fcallgraph-info=su` over tagcache, the
journal and the firmware filesystem/ATA objects: the deepest drain chain
is 6,888 B from `command_queue_sync_callback` (drain 4,120 + 584, salvage
720, scan 424, `open` through `fat_create_file`/`fat_extend_dir` to the
ATA write and its reset path), 7,272 B from a scan
(`tagcache_thread` 56 + `tagcache_build` 328 + `check_dir` 56) plus 56 B
per directory level: below `build_index`'s own 8,720 B chain, of the
17 KiB stack. They run
while storage is awake anyway, or once the 32-entry queue is half full,
so no track change costs a spin-up of its own. Producers (audio, UI) never
take the queue mutex: an IRQ-off push. Play count and play time are
journaled as delta frames and a lastplayed taken before the boot replay
as a relative frame (value 0: the replay gives it the serial so far + 1
and bumps the serial, so plays keep their order across boots without
inflating it): none needs a base, so they are
journaled before, during and after the replay. The replay applies frames
in order onto the master's values; masters never fold deltas (a
candidate takes absolutes, the new active replays after publication),
so changelog exports always read the master on disk and the changelog
lags the journal until the next publication folds it in. A failed
append is checked against the reopened journal's sequence number before
it is retried (a delta frame must not land twice). Checkpoints and
compaction write only the values that differ from the master on disk
(read in chunks from the I/O block): 50k rows with 1,000 played make
3,000 frames (~180 KB), not 50k rows' worth. Rows a candidate's replay
changed carry a persistent mark (`FLAG_UI_STATS_FOLDED`, outside the
generation CRC) and are always written whole: if the active generation
fails validation, the one it was built from (the fallback) gets them
back from the journal. Update builds keep the mark (a clone), so the set
grows towards the rows played since the last full rebuild: extra frames,
never a missing value. A rebuild imports its own export of the master on
disk; when that export cannot run, the rebuild waits (the active library
stays) and retries with backoff. A failing compaction backs off too.
Compaction (stopped only, **24 B/track** snapshot: 1,200,000 B at 50k,
plus a 16 KiB I/O block) starts at 64 MiB of the 128 MiB journal. Clean
power-off waits at most **3 s** and only appends (never compacts); frames
it could not write are lost only if the power really goes, logged.
Generation validation uses one transient locked 16 KiB allocation split
into disjoint 8 KiB helper/validator regions.

**Artwork.** Records of albums gone from the library are kept until the
index or pack passes 3/4 of `ARTIDX_MAX_RECS` (49,152 of 65,536); then a
pass that walked the whole table drops them at its final commit, only
while stopped. `index.prev` keeps its slots reserved, and nothing is
deleted from inside the merge.

## Resident video image (p14-resident; `--bcmfw-video` or `--bcmfw-merged` builds)

**What:** the player's VideoCore image (`/.rockbox/bcmvideo.bin`, 203,140 B in dev41 with the AAC decoder, `bcmfw/mkvideo.py`) is also the display driver between videos, in place of the 8 KB boot image (`hello_dma`). It serves the same LCD commands (`LCD_UPDATE`, `UPDATERECT`, `POWERON`, `SLEEP`, the ready word, the info word) from the same `bcmfw/lcd.c`, so a video starts with `HELLO` + `OPEN` only: no stock-order power-down, no image upload, no 0.55 s dark panel; and the stop closes the session and hands the panel back with the image running (`bcm_video_hand_back()`, the whole frame repainted).

**Setting:** Developer list → "Resident video image: on/off" (default **on**, the owner's go) and "Video chip idle sleep: on/off" (default **off**), and (p19-battery) "Video chip core level 5: on/off" (default **off**: the regulator at Apple's level for 27 MHz, written at the swap and every wake, only on the crystal; `docs/research/bcm2722/battery-levers.md`). Saved in `/.rockbox/bcmres.cfg` (no file: on, idle off, level as found); all apply at the next boot. The bench rows `slp` and `lvl5` A/B them live. It only acts when the boot path itself swaps (the `bcmfw.cfg` toggle and its pass flag, or `--bcmfw-default`): the resident image is the ladder's first rung, then our DMA image, our CPU-push image (`--bcmfw-l1`) and Apple's vmcs. A resident rung that fails at boot writes `/.rockbox/bcmres.fail` (no strike) and is skipped until the setting is chosen again; a run-time failure drops one rung (to `hello_dma`) like any rung and counts a strike. Status, read and swap times and the live idle counters: Debug → BCM boot path: status.

**How the image gets there:** the boot path runs once the disk is mounted (the shell's start, or `main.c`'s level 1 early swap), so `bcmres_offer()` (`apps/video/bcmres.c`, `HAVE_BCMFW_RESIDENT`; in `vplayer.c` until p19-release-noplayer, shared with the player when it is built) reads the file then, in **one bulk read** into a pinned `core_alloc` block (verified by size and FNV-1a as every play is), and hands the boot path the pointer (`bcm_boot_offer_resident()`). Firmware never reads apps' files; the copy stays for good because every backlight wake uploads it again (`flash_vmcs_*` point at it). With the setting off there is no read and no block.

**Idle power plan:** the image sleeps its core between commands (`ei; sleep; di`, woken by timer compare 1 every 1 ms or the host doorbell, source 23) only while the host's gate word (`0x16C` = `"SLP1"`) is set: the boot path sets it when the resident image comes up and at every wake, the player clears it for a session (a session polls as proven) and sets it again at the hand-back. **Unproven on silicon:** no interrupt source has been confirmed on the chip (`docs/bcm2722-reference/open-questions.md` #3) and stage 5i has not run, so idle sleep defaults off. If the tick never fires, the core never wakes: `lcd_tick()` sees an update busy 2 s and the run-time fallback takes `hello_dma` (a strike). Run stage 5i before turning it on. ## Automatic battery calibration (#70)
The PP5022/PCF50605 has no fuel gauge, so the level comes from voltage through `percent_to_volt_discharge` (11 points). `HAVE_BATTERY_LEARN` learns that table from the unit's own full discharges (`docs/batcal-brief.md`; `apps/ipodui/batcal{,_core}.c`).

- **A run** opens at unplug only after a "full" latch: charger present with USB charging at 500 mA, charging done (`charging_state()` false) for 2 continuous minutes at 4100 mV or more. A 1 s timeout (RAM only) averages each period's voltage and busy share (backlight lit, boosted or disk active; a period with disk activity counts as wholly busy) into one 2-byte sample: 512 samples (1,024 B static), pairs merged and the period doubled when full (60 s, then 120 s, ...). The first 10 min of a run (surface charge) and the first 5 min after each boot are recorded but left out of the fit. Off-time adds nothing (self-discharge while off is ignored). Any power input mid-run discards it, unless its last sample is already within 50 mV of disk-safe (then the run has ended and is fitted).
- **Persistence:** `batcal.run` (header, samples, CRC-32) is written on the UI thread only, while the disk already spins (the sampler wakes the main loop when it sees the disk come up with something to write; at most one write per 5 min), and at USB connect and clean shutdown through `system_flush()`. Never below disk-safe. Temp file plus rename. A run file left without the "clean" mark is discarded at the next boot unless its last sample sits within 50 mV of disk-safe: that is the normal end, since nothing is written below disk-safe and the shutoff is not a clean shutdown.
- **Fit** (at the next boot, on a run with at least 2 h of on-time, 120 fit samples and at most 30 % busy): charge weight per sample = 1 + (`BC_BUSY_W` − 1) × busy share, normalised to 0..1 at the last sample; table point k is the moving median of the voltage at Q = (1 − k/10) × 0.97 (window 4 %, 1.5 % past Q = 0.85); 100 % is extended back over the skipped surface charge along the slope just after it; 0 % never below disk-safe + 20 mV, so 0 % still means "about to shut down" and the 5/15 % warnings keep their meaning. Sanity limits (fixed): strictly decreasing, 100 % within 3950–4250 mV, 0 % within 3400–3750 mV, every step 5–250 mV. A failed fit is logged to `ipodui.log`.
- **`BC_BUSY_W` = 1.5** is an estimate of the busy-to-idle current ratio, not a measurement. Replace it with measured class currents once a USB-C meter or an A/B rundown gives them (`batcal_core.h`).
- **Applying:** `batcal.dat` keeps the last 3 accepted fits (text, a CRC trailer); the table in use is their per-point median, ordered by sequence number. It replaces `percent_to_volt_discharge` at shell start, after settings and after `battery_levels.cfg` (the learned table wins; logged). The charge table, the shutoff and disk-safe levels and the capacity setting stay as built; at unplug the display can step a few percent.
- **Cost:** RAM 1,024 B ring + 48 B state + 120 B for three fits + 22 B (the boot-time table, for the reset); one 1 s timeout; about 1 KB written per write, only while the disk spins; zero disk wakes.
- **Device check (P10):** one full run-down with the power log on; compare the learned table with the `power.csv` curve, then the percentage at known hours on the next discharge. Watch that the last write before the shutoff lands within 50 mV of disk-safe (`ipodui.log`: `batcal fit seq=` at the next boot, or `run dropped`).

## Boot battery guard (2026-10-22, `apps/ipodui/bootbatt{,_core}.c`)
Owner report, 2026-10-22: after a full run-down under playback the unit kept starting into the menu and then cutting out hard. After the cut-off the resting voltage climbs back, the boot load (boost, storage, the video chip, the database) pulls it under, and it browns out with no clean shutdown: a bad experience and a filesystem risk. The 7G refuses to start on a flat cell; so do we.

- **Evidence [silicon, owner rundown 2026-10-22]** (`session log, backup 20261022 power.csv`, 30 s rows, continuous playback): the last row before the cut read 3,362 mV (s = 60,271, still playing). The two boots that followed, on battery, logged 3,576 and 3,569 mV in their first row; the first charging row read 3,593. **An empty cell rests about 210 mV above its cut-off.** Near the bottom playback took about 20 mV/h (3,599 mV at s = 29,311 to 3,479 at s = 50,011); the owner reads the 3,550–3,650 band as about 10 mV/h, so a cell resting there still has hours of light playback.
- **Owner decision, 2026-10-22: two rules, not one threshold.**
  1. **Resting floor `BB_FLOOR_MV` = 3,400 mV** (was disk-safe + 100 = 3,600, which refused cells with hours left). Both storage variants (rule 7). It sits 100 mV over the runtime shutoff (3,300), at the flash disk-safe (3,400) and under the HDD's (3,500); it does not follow disk-safe.
  2. **Drained latch.** A floor that low alone would let the empty cell above (rest 3,570) boot and hard-cut again, so the firmware records "drained" on disk **when the display reaches 0 %** on battery, and on battery a drained cell is refused whatever it rests at. **Power seen clears it** (a charger or USB, at boot or at runtime), and so does **a charge the firmware never saw**: a stage-1 rest median at least `BB_RECHARGE_MV` (300) over the 0 % point (the larger of the one stored with the flag and the built-in table's), about 3,720 mV on flash (review round 2: charging under Apple's firmware, or on a charger that never boots ours). An empty cell rests at 3,569–3,593 mV [silicon, owner rundown 2026-10-22], at least 120 mV under that, so a rested empty cell stays refused. **What the user sees:** once the display has shown 0 % and the unit is switched off or dies, it does not start again until it has been charged ("0 % means about to switch off"). A unit that is merely low, above 0 %, boots normally down to the 3,400 mV rest floor.
- **Rule table** (`bb_decide()` then `bb_latch_rest()`, host-tested in `tests/bootbatt/`): power present: boot (and clear the latch). No power: drained: refuse, unless the rest median reaches the recharge level (boot and clear); not drained: refuse below 3,400, else boot. No valid reading (outside 2.5–5.0 V): boot unless drained.
- **Where the flag lives: `/.rockbox/.bootbatt`, a one-sector record written in place.** No PMU register is proven spare: `clocks-power.md` §6 lists none, the RTC alarm registers (`0x11`–`0x17`) belong to `HAVE_RTC_ALARM` (and to Apple's firmware, the recovery path), and which PMU part this is remains open question 20. PP SDRAM and IRAM are not shown to hold across standby. So the record is a 20-byte struct (magic, drained, sequence, the 0 % point when set, FNV-1a sum) at the start of one sector of a preallocated hidden file, written like the #91 rename intent record (`file.c` `record_io()`, now shared): **one storage write of its first data sector, no FAT or directory write, then a write barrier.** A torn write fails the sum and reads as "not drained" (the floor still guards). It is made (one zeroed sector, then "clear") at a boot with power present or a rest over disk-safe; never on a refusal. **A missing record** (deleted over USB) or **an unusable one** (truncated, e.g. 0 bytes: removed and made anew) is repaired at boot, at the end of a USB session, and otherwise only while the disk is awake anyway and writes are allowed, with backoff (1 min doubling to 64 min after a failure), so a repair never wakes the disk on its own; the 0 % write repairs first if it must.
- **Evidence that the latch cannot wait for the shutdown [silicon, owner logs 2026-10-22]:** the rotated `ipodui.log` files in `session log, backup 20261022 rockbox/` show five boots at 17:24:01, :10, :19, :28 and :38, each stopping at line 10 with no shutdown lines: hard cut after hard cut. The power log ends at 3,362 mV while playing, and the rundown's own end is not in the logs that remain. So this unit can hard-cut before the 3,300 mV filtered shutoff fires, and a latch written only by `clean_shutdown()` might never be written.
- **When the flag is written: at 0 %.** `bootbatt_service()` runs on the UI thread every main-loop pass (`ui_main.c`, beside `batcal_service()`); a 10 s tick timeout (compares only, no I/O) wakes the loop with `np_pb_ab_wake()` while the write is owed and still possible: not latched, no charger, and over disk-safe, so below it (P18 sleep, the shutoff) it stays quiet; a lit idle loop may otherwise block. The write is due (`bb_zero_due()`) when the filtered voltage is at or under the 0 % point of the discharge table in use (`percent_to_volt_discharge[0]`, read at run time: 3,420 flash and 3,520 HDD built in, or batcal's fit, never under disk-safe + 20), with no charger or USB, while `battery_level_safe()` holds, and not already latched. **That is a normal safe write** (over disk-safe on both variants). It waits up to 30 s for the disk to be awake anyway (a refill), then accepts one wake; a failed write retries after 30 s. Once per discharge: a power input clears the flag and re-arms it.
- **The backup at the low-battery shutdown.** `clean_shutdown()` calls `bootbatt_latch_drained()` when `query_force_shutdown()` holds; it writes only if not latched and still over disk-safe (`bb_shutdown_due()`). At the 3,300 shutoff it is under disk-safe on both variants, so in practice it is skipped (sim: `ipodui-p16-bootbatt-latch-shutdown`); there is no below-disk-safe write any more. A fall through the 0 % window (20 mV on flash, 20 on HDD) faster than the 30 s wait would leave no flag; on the unit that window lasts minutes (about 12 min at the measured end-of-run rate).
- **Where the flag is read: stage 2, right after the mount** (`bootbatt_latch_check()`, after `rbfs_rename_intent_boot()`, before any app opens a file). **The guard cannot read it before storage:** a file needs `storage_init()` and the FAT, and a fixed raw sector would mean writing outside the file system. Resolved as two stages: stage 1 (the floor) still decides before storage, so a cell under 3,400 never touches the disk; only a cell over the floor reaches the mount, whose reads follow the bootloader's own (it has just read the firmware from the same disk; an HDD is still spinning). A stage-2 refusal writes nothing of its own; the #91 rename-intent recovery (`rbfs_rename_intent_boot()`, just before it) may already have written, to finish a rename a cut interrupted. That is intended: the cell rests over the floor there, so the write is as safe as any boot write. The refusal parks the disk (`storage_spindown()`, at most 3 s) before `power_off()`. It comes after the boot glyph (the logo shows first for those few hundred ms), not before it as a stage-1 refusal does.
- **Order in `init()`:**
  - `bootbatt_sample()` runs right after the tick starts (I2C and the PMU need it). It takes 5 fresh ADC conversions one tick apart (`battery_voltage_scan()`, no 400 ms cache, no filter), uses their median, and reads the power inputs. This is before `cpu_boost(true)`, which now follows the sample in the shell build and is skipped on a stage-1 refusal.
  - `bootbatt_enforce()` runs right after `lcd_init()`/`font_init()` and before the boot logo, `storage_init()`, the mount, any font load, settings and the VideoCore image. **A cell under the floor never spins up the disk, never scans the FAT and writes nothing.**
  - `bootbatt_latch_check()` (stage 2) as above.
  - A refusal shows the glyph-only low-battery image through **one call, `ui_sys_dead_battery()`**: the shell's "Connect to Power" frame without the line of text, since no font is loaded yet. The owner picks the final look later.
  - It holds the image 2 s, polling the power inputs every 100 ms. **A cable plugged in during the hold boots** (to the charging flow; a drained latch is then cleared). Powering off then would leave the unit dark on the cable, since the PMU wakes on the charger's edge, already gone.
  - Otherwise it turns off the backlight (`_backlight_off_normal()`; the backlight thread doesn't exist yet) and the LCD, then calls `power_off()` (PMU standby, as every Rockbox power-off).
- **Runtime clear:** `bootbatt_service()` clears a drained record whenever power is present and the disk is ours (not a USB host's), and `SYS_CHARGER_CONNECTED` does the same at once. A USB session clears it at its end, beside `rbfs_rename_intent_usb_exit()` in `usbscreen.c` (`bootbatt_usb_exit()`), which also repairs a record the host deleted or truncated (review round 2: charging on a Mac and ejecting used to leave it set). Script: `ipodui-p16-bootbatt-usb-clear`.
- **The hard cut:** covered when the display reached 0 % first (the write is already on disk). A cut while the display still shows 1 % or more leaves no flag, and the 3,400 floor is the only guard; by the measured table that is under the last 0.6 h of playback (3,420 to the cut at 3,362).
- **Filter seed:** in the shell build, `average_init()` seeds the 64 s voltage filter with the guard's own median (`powermgmt_seed_voltage()`), a resting reading taken before any boot load. Upstream instead reads under the boot load and adds a guess: 15 mV (flash), or 35 mV (disk). Host model (`tests/bootbatt/`): a 3,620 mV rest that sags 150 mV keeps `battery_level_safe()` true for the whole first minute on the slow path. The fast path (disk active and the level under 8 %, upstream's brown-out watch, unchanged) follows the loaded voltage within a few steps whatever the seed. **On HDD (disk-safe 3,500), a cell resting at 3,400–3,500 boots with writes already off** (`battery_level_safe()` false from the seed): it plays, but settings, resume points and the database are not saved until it charges. On flash (disk-safe 3,400) only a rest of exactly 3,400 does. The runtime shutoff itself is unchanged.
- **Who else uses these levels (checked):**
  - batcal (#70) samples only after the shell starts, so the guard cannot cut a run's last write. The run file stays on disk with its last sample near disk-safe and is fitted at the next boot that passes, the charger boot after a drained shutdown included (stage 2 then clears the latch; batcal's fit runs later in the shell). The 0 % write does not touch batcal's state or files and costs it at most one shared disk wake (batcal itself writes only while the disk spins).   - The power log, the art builder's `LOW_BATTERY` (percent), charging sleep and USB connect all run after the guard and are unchanged. The latch write is not a power-log row; it logs `bootbatt drained latch set (zero) mv=...` to `ipodui.log`. Playback: one sector on the UI thread (the disk cache's buffer, the file layer's writer lock for one record I/O), never on the audio or codec threads; a refill already in flight just shares the lock for that one sector.

That is not `query_force_shutdown()` and is over the 0 % point, so a unit asleep at about 5 % is not latched and boots on the floor, which is correct. The 10 s wake check stops below disk-safe, so it never fights sleep there.

The latch write below disk-safe may have to spin the drive up on a nearly empty cell: if it browns out during the spin-up, nothing is recorded (as a hard cut) [hypothesis, check on an HDD unit].

## Panic record (`HAVE_PANIC_RECORD`, branch `panic-record-1019`)
`panicf()` and the ARM exception handler save a sealed 164-byte record (kind, count, pc, System-mode lr/sp, thread name, the first 119 bytes of the message) in the 256 bytes just below the codec buffer, which the audio buffer no longer covers (`firmware/export/panic_record.h`, `quirks.md` 48). The core then halts as before, but the shell build draws no panic or exception screen: the last UI frame stays (no `*PANIC*`, no version). The next boot logs it right after the `boot variant` line and flushes at once:
`panic kind=<0 panicf; 1 undefined; 2 prefetch abort; 3 data abort; 4 div0; 5 SWI> count=<panics since the last logged one> thread=<name>`, `panic pc=.. lr=.. sp=..` (panicf: pc is its caller's return address, lr 0; exceptions: the faulting pc; the ARM7TDMI has no fault-address register), then `panic msg <48 characters>` per piece.
- **Cost:** 256 B off the audio buffer; fw-ui text -4,380 B net (+~730 B of record code, the screens and the backtrace unwinder gone), `_end` 1,099,376 -> 1,095,280; the two developer test rows add 264 B of text within the same 4 KiB step. One file write at the boot after a panic, while the disk spins anyway.
- **Survival is [hypothesis] until checked.** Device test (developer list, last two rows): (1) "Crash test: restart" saves a record and restarts cleanly (a `DEV_RS` reset); after the boot, `ipodui.log` must hold `panic ... msg dev test restart`. (2) "Crash test: freeze" panics for real: the screen freezes; hold MENU+SELECT until it restarts; `ipodui.log` must hold `panic kind=0 count=1 thread=<UI thread>` and `panic msg dev test freeze t=...`. Report both, and whether the reset took more than a few seconds. If (2) fails while (1) passes, the hardware reset clears SDRAM and a record needs a different home (IRAM's top or the disk).
- **Proposal, not done:** once (1) passes, restart by itself after recording instead of halting (halting only if an unlogged record is already there, so a crash at boot cannot loop), as the 7G does.

## Hang record (`HAVE_HANG_RECORD`, branch `p19-hangrec`)
A freeze leaves no panic record, so a CPU tick task (`firmware/common/hang_watch.c`) watches four threads' progress counts every 100 ms: the shell's (`ui`, its loop pass; idle while it waits for input), be_svc (`be`, UI split only), the art builder (`art`) and the storage thread (`sto`, whose idle callbacks write `config.cfg`, the logs and the resume records). One at work with no progress for 6 s (ui, be) or 10 s (art, sto) gets a record of kind 72 (0x48); no reset, so MENU+SELECT keeps it and the next boot logs it:
- `panic hang record thread=<kernel name> count=N`, then `panic pc=.. lr=.. sp=..`: pc is the interrupted instruction when the stuck thread is the one the tick interrupted (it spins on the CPU), else 0 with lr/sp from its last switch (blocked, sleeping or `ready`: switched out but runnable, e.g. a yield loop);
- `panic msg hang: <slot> no progress <s> s (<running|running-cop|blocked|blocked-tmo|sleeping|ready>) bench=<step|-> wq=<wait queue> own=<mutex owner> olr=<owner's saved lr>`, " STACK OVERFLOW" appended when a watched stack's guard word is gone;
- `panic trace ...` (a stack scan from that sp), `panic info stk ui <used>/<size> ... sto 2310/3072 mx ata=<owner|-> i2c=<owner|->`, then the log tail.
**Reading a storage deadlock:** a stuck storage thread shows `(blocked) wq=<addr> own=<thread>`: `wq` is the wait queue inside the object it waits on (look the address up in `rockbox.map`: `ata_mutex`, `i2c_mtx`, a FAT/file lock), `own` the thread holding it, and `mx ata=` / `i2c=` who holds those two now. Two threads each owning what the other waits on is a deadlock; `(running)` with a pc inside `ata_*`/`fat_*` is a spin; `!OVF` or a `sto` high-water at its size is a stack overflow.
**Not watched (exempt):** the USB screen and its session, a shutdown, a bench step's own function (its watchdog covers it), any thread's wait for input or its own queue; a disk spin-up adds 10 s; the shell waiting on be_svc adds 2 s so a stuck be_svc is named first. A thread that goes on after its record (a long stall, not a freeze) is logged at once as `hang recovered <slot> after <s>s` with the record, and the watcher re-arms (4 records a boot at most). A branch to address 0 is caught separately, as exception 5 "Jump to 0" (`pp5022-reference/quirks.md` 56).
- **Cost:** ~3 KB text, ~110 B of BSS (48 B of it uncached, shared with the COP), a 100 ms check of four words; the record write (~1 ms, once) runs in the tick interrupt without locks or file I/O.

## Deleted entries and compaction (proposal)
A deleted file's entry stays in the database, flagged (`FLAG_DELETED`), with its tag strings: tagcache only drops them when it is rebuilt. Each costs its full RAM cache share (~140 B at 50k, plus 12 B of view pool) and its slot in every list walk, and the files grow with every edit of the library over USB. Moving or re-tagging an album deletes and re-adds every track, so a library that is curated often can carry thousands of dead entries.

Proposal (not implemented): rebuild in the background when dead entries pass **10 % of the database, or 2,000**, checked after the post-USB reverse scan, only while the device is charging and idle, never during playback. A rebuild at 50k is the first-build cost (minutes on the device, boosted; the library shows "Updating Library..." meanwhile, which is why it should wait for an idle, charging device) and keeps the statistics through the changelog. A cheaper alternative, compacting the master index and tag files in place, would be new upstream-sized code; not worth it unless the rebuild proves too slow on the device.

## USB states: charger versus host (budget review H1, 2026-10-18)
The Video's USB detect is GPIO L bit 4, which is VBUS: a host and a wall charger look the same (`usb-fw-pp502x.c`). With the ARC stack, `USB_DETECT_BY_REQUEST` is set (`config.h`), so `usb.c` goes `USB_EXTRACTED` → `USB_POWERED` at VBUS and to `USB_INSERTED` (host present, class drivers on) only at the host's first request (`USB_NOTIFY_SET_ADDR` or a transfer completion). A wall charger, a USB-C charger or a charge-only cable never sends one, so the state stays `USB_POWERED` for as long as it is plugged in and no `SYS_USB_CONNECTED` is ever broadcast; `usb_inserted()` is true all that time (`state == USB_INSERTED || state == USB_POWERED`). Charging-only mode with a host (`usb_power_only`) reaches `USB_INSERTED` but configures no storage, so it never broadcasts either. The art builder used `usb_inserted()` as its "USB is coming" gate, so on a charger it refused every image read and write (and in a boosted maintenance pass spun on the refusal); it now uses `usb_storage_host_present()` (host present and not power-only) or the GUI's handover flag. The window before the gate closes is VBUS → SET_ADDRESS (the host's bus reset and first descriptor read, typically 100-300 ms) instead of none; storage is not requested until SET_CONFIGURATION, after it. **Device check:** on a wall charger, Music hold → Build Artwork finishes (`ipodui.log`: `art pass done`); with a Mac, the storage handover (`usb hand ... ack=`) stays within its usual 0-3 s while an art pass runs.

## USB mass storage throughput (#63)
**Measured on the device (2026-10-10, before `p9-usbperf`):** ~7.5 MB/s reading a mounted file with 1 MB requests (`dd`); ~5.4 MB/s for macOS's mount-time FAT scan (8,643 READs averaging 12 KB, 106 MB in 19.5 s). macOS's FSKit msdos driver reads the whole FAT (~250 MB on this 1 TB volume with 16 KiB clusters) before mounting and gives up after ~20 s, so auto-mount needs **≥ 13 MB/s** (18+ to be safe); faster copies matter for drag-and-drop anyway.

**What the code says** (file:line on `p9-usbperf`):
- Reads take the ATA DMA path if the drive offers a DMA mode: the USB buffers are `core_alloc`ed, 32-byte aligned and addressed through `UNCACHED_ADDR` (`0x1xxxxxxx`, the physical DRAM alias), which passes `ata_dma_setup()`'s 16-byte check and is handed to the controller as is (`ata-pp5020.c` `ata_dma_setup`). Writes use DMA only when `ata_disk_isssd()` is true (iFlash adapters report IDENTIFY word 163, so they should). UDMA above 2 needs IDENTIFY word 93 bit 13 or a non-zero word 76 (`ata.c` `set_features`); otherwise the mode is capped at UDMA2 (33 MB/s, still above what we see). On this unit the log shows `usb ata mode=0x42` with words 76 and 93 zero: UDMA2.
- A READ that fits one 64 KB buffer runs strictly in series (CBW, flash read, USB send, CSW); only longer READs overlap the next flash read with the current send (`send_and_read_next`). The ARC driver splits each transfer into 16 KB descriptors, primes once and gets one interrupt per transfer: no per-packet overhead found.
- With the 2048-byte virtual sectors, `phys_sector_mult` was raised to 2, so every 512-byte host write was a 1024-byte read-modify-write; now kept at the drive's value on flash (`ata-common.c`).

**What `p9-usbperf` adds:** read-ahead for sequential READs inside the existing 2 × 64 KB buffer (+1 KB for the CSW and small replies, only while USB is connected), and counters. **Prediction, not a measurement:** the read-ahead helps only the small-READ case; how much depends on how much of each 2.26 ms command is flash latency, which the counters will show. Large reads are bound by `max(flash 64 KB, USB 64 KB)` per chunk either way.

**Measurement plan (next install).** `.rockbox/ipodui.log` gets, per session:
- `usb ata mode=0x4N ssd=S w88=.. w93=.. w76=..`: the DMA mode set (`0x44` = UDMA4, `0x42` = UDMA2, `0x2N` = multiword DMA, 0 = PIO only) and whether writes may use DMA.
- `usb exit s=.. ejected=.. rd=<MB> wr=<MB>`, `usb cmd rd=<READs> wr=<WRITEs> calls=<storage calls> ra=<hits>/<fills> hs=<1: high speed>`, `usb ms busy=.. stor=.. usb=.. host=..`, `usb ata dma=<rd>/<wr> pio=<rd>/<wr> rst=<soft resets>`.
- **USB reliability (`usb-reliable`, 2026-10-15)**, at entry `usb prev pendexit=<0/1>` (`bus_reset_pending` as the previous session's `usb_core_exit()` found it; 1 = that session ended with a reset outstanding, the old cause of a deaf next plug-in), and at exit:
  - `usb bot tur=<TEST UNIT READY> inq=<INQUIRY> oth=<other CBWs> bad=<invalid CBWs, pipes halted> ign=<stale completions ignored> wrfail=<WRITEs whose storage write failed>` (READ/WRITE counts are `usb cmd rd= wr=`);
  - `usb rst bulk=<Bulk-Only resets> down=<configuration teardowns: bus reset, SET_CONFIGURATION, end of USB> bus=<bus reset interrupts> defer=<SETUPs held behind a reset> pend=<bus_reset_pending now> excl=<exclusive storage now> log=<last 8, oldest first>`; each log entry is `b` (bulk reset) or `d` (teardown) and the storage state then: 0 waiting for a command, 1 waiting for the storage handover, 2 sending blocks, 3 sending a result, 4 sending a failed result, 5 receiving blocks, 6 receiving the time, 7 CSW or next command, 8 waiting for the CSW;
  - `usb blk busy=<ms> stor=<ms> pf=<ms>`: the longest single pass of the USB thread (the host waits on it), the longest single storage call (any thread), the longest prefetch wait (bounded by `PF_WAIT_TICKS`, HZ/5).
  - **USB resets (`usb-resets`, 2026-10-16)**, the controller's own view (`usb_drv_get_stats()`, `usb-arc-reset.h`), after `blk` (the log ring is flushed around these lines so none drop):
    - `usb irq uri=<reset interrupts> pci=<port changes> sli=<suspends seen> uei=<error interrupts>`;
    - `usb irq rstreal=<resets taken: storage torn down> rstfake=<only acknowledged: PR clear, our address intact> addr=<SET_ADDRESS applied, one per re-enumeration> sdis=<0/1>/<USBMODE read back, 0x12 with stream disable>`;
    - `usb irq gap<.1s= <1s= <10s= more=` (time since the previous reset) `td=<halted>/<buffer error>/<transaction error>` (bulk dTDs retired with that status bit);
    - up to 8 `usb rbits <n> s<USBSTS> p<PORTSC byte> a<address> k<kind> e<ENDPTSTATUS byte> t<IN dTD status> g<ms since previous reset> i<ms since last bulk IN completion>`, the first 8 resets. PORTSC byte: bit 0 in reset, 1 suspended, 2 enabled, 3 connected, bits 4-5 line state (0 SE0, 1 J, 2 K), bits 6-7 speed (0 full, 2 high). Address: DEVICEADDR as the interrupt found it, `+0x80` if we had been given one. Kind: 0 port in reset, 1 the controller cleared our address, 2 not addressed yet, 3 spurious (acknowledged only). ENDPTSTATUS byte: OUT endpoints in bits 0-3, IN in bits 4-7. dTD status: `0x80` active, `0x40` halted, `0x20` buffer error, `0x08` transaction error.
    - with the developer marker `usb_sdis` in the system folder, at entry: `usb sdis=1 mode=<USBMODE>` (stream disable A/B; the bit is a no-op on the PP5022, see `pp5022-reference/usb.md` §6).
    Read as: `rstreal ≈ addr` means the host re-enumerated after every reset, so the resets were the host's (its error recovery), not the controller misreading the bus; `k0` with `p..` showing PR is a reset caught while in progress. `td` buffer errors > 0 point at TX underruns (memory bus contention); then compare a session with `usb_sdis`. Transaction errors or many short gaps with clean dTDs point at the link (cable, USB-C mod) more than the firmware.
  Healthy: `bulk=0`, `bad=0`, `pend=0`, `excl=0` after unplugging, `busy` well under a second. A `b2`/`b5` entry is a reset during a READ/WRITE (the host timed out); `defer>0` is a reset the device now survives.

Read them as: `pio` reads ≫ 0 means DMA is being skipped; `rst` > 0 means retries; `stor` ≈ `busy` and `usb` small means flash-bound; large `usb` means the USB side is the limit; large `host` with few bytes means per-command turnaround dominates (the case read-ahead and, next, an asynchronous prefetch target). Procedure: plug in, let macOS try to mount (note whether it auto-mounts and how long), copy one large file off and one on (note `dd` rates), eject, unplug, then read the log after the next disk flush.

**Prefetch ring (#81, `HAVE_USB_PREFETCH`).** In USB mode only: an 8 MB `core_alloc` (4/2 MB fallback) taken from the idle audio buffer at SET_CONFIGURATION (expect one `audio shrink want=` log line per connect), plus a worker thread that reads 256 KB ahead of sequential READs while the USB thread sends earlier READs from the ring by DMA. Freed at disconnect; the audio buffer takes it back at the next playback start (`audio_reset_buffer()`, buffer state trashed by the shrink). Correctness: any command that may change the disk drops the ring first, and a read in flight at that moment is discarded by generation; the worker never overwrites the sector the USB is sending from (host test `tests/usb/pf_test.c`). Static cost: +3.3 KB text, +223 B bss (`usb_storage.o`).

*Expected mount time (estimate, to confirm on the device):* the FAT scan is ~250 MB in ~20,300 READs of ~12.3 KB. Storage side: 250 MB at the adapter's ~21 MB/s (the #63 log: 1.35 GB of 64 KB fills in 63.6 s of storage time, ~21 MB/s; 256 KB reads should do no worse) = ~12 s, now overlapped with USB. USB side: each READ is a CBW, ~12 KB from RAM and a CSW; at ~0.45 ms per command (estimate, not measured) that is ~9 s. The two overlap, so ~12 s, inside the ~20 s limit with ~8 s margin. If the USB side turns out slower than 0.6 ms per command, it becomes the limit (`usb ms host=` will show it).

*Log (`ipodui.log` at USB exit):* `usb pf ring=<KB> hit= pend= miss= fb=` (READs all in the ring / still being read / on the ordinary path; pieces that fell back after a wait), `usb pf fill=<worker reads> mb= stall=<longest ms>/<total ms> wrstor=<ms of write storage time>`, `usb mnt cfg2rd=<ms SET_CONFIGURATION to the first READ> rd2fat=<ms from it to the first READ past the first FAT; 0: never> rd30=<KB in the first 30 s>`. A mount that works shows `rd2fat` well under 20000 and `rd30` ≥ ~250000.

## iAP memory (`--dock30` builds, `p19-iapfit`, 2026-10-26)

`IAP_LAZY_THREAD`, `IAP_RX_BUFLEN` and `IAP_STACK_SIZE` (set in `ipodvideo.h` for every `HAVE_IPOD_UI` build with the dock connector). The iAP buffers are static and sized for this player: RX 4,096 B instead of upstream's 64 KB, which holds eight of the largest inbound packets the lingoes expect, with room for certificate sections and bursts while a handler waits on the disk (SetDisplayImage's 500 B payload; the ~506 B UART maximum is [hypothesis], not checked against an accessory). A longer packet is dropped by the framer, which is upstream's overflow behaviour. TX stays at upstream's 128 B. The thread's stack stays at 8 KB: the measured worst static path (`-fcallgraph-info=su`, stock shape) is about 7.0 KB, made of lingo 4's 3,360 B frame (a `struct mp3entry` on the stack), `iap_get_trackinfo` 288 B and a track's metadata parse of up to 3,144 B (WAV/W64; MP4 2,096, ASF 2,288), with indirect calls unbounded. No `core_alloc` anywhere, so docking never touches the audio buffer and causes no playback gap.

The iap thread, its queue and the 100 ms tick come up only at an accessory's first sync/start-of-frame pair (0xFF 0x55; a lone 0xFF from line noise starts nothing), created on the USB thread (`USB_IAP_BRINGUP`). At a USB unplug (`iap_reset_state()`, upstream's session reset) the iap thread stops the receiver and the tick; the next pair starts them again. Lost queue posts are repeated: the interrupt re-posts at the next pair, at most every 100 ms, and the end is also seen at the next tick through a flag. **Caveat:** an accessory without USB power (a car or speaker dock powered only through the 30-pin's other pins) never produces a USB unplug, so once it has spoken, the 10 Hz iAP tick runs until power-off, as it always did upstream. The volume maths is integer (`apps/iap/iap-volume.h`, bit-identical, `tests/iapvol`).

## Wake budget (P18 18-A, a quiet system)

Every periodic wake costs a core wake-up (the PP5022 leaves `core_sleep()`), the thread switch and whatever the thread then touches. 18-A turned the idle polls into deadline waits. The counter is `devstats.t[].thr_wakes` (developer builds): `m0 wakes win=.. total=.. rate=..` plus one line per busy thread each minute in `ipodui.log`, and the simulator script command `wakes <label>` (`tests/ui/ipodui-p18a-wakes-dark.script`). **Simulator caveat:** the macOS simulator polls its button queue at 60 Hz (`button_queue.c`, `__APPLE__ && SDL`), so the simulator's `main` row (about 45/s in every state) is a host artefact and not a device number; on the device the UI loop only runs at its own deadlines.

| Thread | Before | After (idle awake) | Wakes for | Waits for |
|---|---|---|---|---|
| power | 2/s (HZ/2 step, ADC read each) | 0.5/s quiet (no charger, no USB, no shutdown pending, above 15 %); 2/s otherwise | step, voltage filter (one sample per elapsed 0.5 s), 15 %/5 % warnings, force shutdown, charger edge, PLL holds | 2 s, or `power_thread_kick()` (backlight lit, PCM start, USB and firewire edges) |
| buffering | 2/s while handles exist | 0 with a full buffer; floor 2/s as the level nears the watermark; cap 30 s | watermark crossing | slack / 2 MB/s, or `Q_WATCH` (forward seek of 32 KB or more, base handle, watermark change) |
| scroll | 7.6/s, always | 0 with no scrolling line (the shell scrolls itself; only developer lists use the engine) | scrolling lines | `scroll_thread_kick()` when a line is added |
| backlight | 1/s always | 0 with no timer running; one wake at the nearest timer end otherwise | timeout, LCD sleep, ignore window | nearest timer; events (`BACKLIGHT_TIMER_SET` when a timer starts outside the thread) |
| tagcache | 1/s | 1/s in 18-A; P19 19-1a: see below | owed work | see below |
| main (UI) | lit: 20/s while a panel drifts (visible); dark: 0.2/s or less (unlit face: 1/min) | unchanged | animation, header clock, unlit minute | `ui_*_wake` deadlines |

**Fresher-than-it-was is not needed.** With the quiet power step (2 s), `voltage_now` and the percentage change every 2 s instead of every 0.5 s: batcal's 1 s samples and the power log's 4 Hz sub-samples read a value up to 2 s old (it was already a 128-sample average, 64 s time constant), which is fine for both. The backlight thread counts its timers by the ticks it really waited; a timer started outside the thread (the PWM fade's LCD-sleep countdown, the ignore windows, `lcd_set_sleep_after_backlight_off()`) posts `BACKLIGHT_TIMER_SET` and starts counting at the next wait, and nothing counts after the power-off lock. `tests/ui/ipodui-p18a-lcd-sleep-timing.script` checks the LCD sleeps 60 s (59.98 s measured) after the backlight goes off.

**P19 19-1a (quiet pollers, 2026-10-24).** The rest of the back end now waits for deadlines too (pure waits in `firmware/common/quiet_wait_core.c`, host test `tests/quietwait/`; `qw_legacy` / sim `quietpoll legacy` brings back every old cadence):

| Thread | Before (dark play) | After (dark play) | Waits for |
|---|---|---|---|
| audio | 2/s (HZ/2 always) | 0 between tracks; HZ/10 only while an automatic skip is pending (the FIQ's notice); HZ/2 while paused until the codec's standby | events (buffering, codec, PCM's direct posts, keys) |
| ata (storage) | 2/s (HZ/2 always) | 0 with the drive off; per refill: one kick, the standby deadline, the power-cut deadline (host model: 3 wakes); 2 s cap while lit and in standby | `last_disk_activity + sleep_timeout`, the `stor_pwr` hold or `power_off_tick`; `storage_quiet_kick()` on an access |
| power | 0.5/s | 0.1/s (10 s step: quiet, playing, dark); the sleep timer's end exact | step, sleep timer, kicks (backlight lit, PCM start, USB/firewire, shutdown, sleep timer set) |
| tagcache | 1/s | lit or work owed: 1/s, unchanged; dark with nothing owed: the earliest *future* retry back-off, paused-window age or export quiet period, never under 1 s, at most 30 s; plus one kick per drive power-up | `tagcache_quiet_kick()` from every producer and `storage_set_awake_hook()` (see `changes-from-rockbox.md` 2.29.1) |

Measured (sim): one 4 min FLAC, dark, 40 s legacy vs 60 s quiet: audio 80 -> 0, power 20 -> 6, tagcache 40 -> 2 wakes (pollers ~3.5/s -> ~0.13/s); `tests/ui/ipodui-p19a-wakes-long.script` (a 90 s track, 30 s legacy vs 40 s quiet): audio 59 -> 0, power 15 -> 4, tagcache 29 -> 1 (0.025/s). Dark refills (`stor_buffer`, 60 s): 3 power-ups, 3 tagcache kicks + 1 cap wake. Paused with Backlight Off past the 3 min age (`ipodui-p19a-wakes-bloff.script`): tagcache 60 in 60 s, the old 1/s, because the maintenance window's work is wanted and the window stays shut (MAINT_NO_LIT); the past age deadline itself is not polled (host test: 120 wakes/h in the blocked cases). Device numbers come from `m0 polls a=W/T s=W/T t=W/T p=W/T` (waits/timeouts per poller, at most every 10 min) in M-1. Known limits: the dock (FireWire) charger line, GPIOL bit 3, has no interrupt on this target (only USB detect, GPIOL bit 4, does), so a dock charger plugged in during dark play is seen at the next power step, up to 10 s (was 2 s); USB-C charging is USB VBUS and is kicked. Paused with Backlight Off (or a key held, or a paused video) and maintenance wanted, the tagcache poll stays at 1/s. A pending commit or scan keeps the tagcache poll at 1/s while playback holds it off; the PLL `LOAD` hold drops up to 10 s after a hi-res pause; batcal's 1 Hz timeout stays (no thread wake; folding it into the step only pays with a tickless kernel, 19-12).

**P19 19-1c (codec placement, 2026-10-24).** **Decoding is pinned to the CPU** (owner, 2026-10-24; no CPU↔COP migration; the UI moves to the COP later). The default is the plain path:
- the codec gets upstream's api with no COP view;
- nothing is kept back in the codec slot (the 12,288 B worker stack goes back to the codec);
- MP3's synthesis runs inline (`codec_api.cop_assist` false; bit-exact with the single-core path, host test `tests/mpainline/`).

On a full PCM buffer the codec sleeps until the level drains to a low watermark instead of the HZ/20 poll:
- the watermark is half the band above the boost watermark, at least 0.25 s of it, and the sleep is at most 1 s;
- the FIQ cannot post, so it is a deadline from the drain rate;
- a message still wakes the codec at once.

Sim, dark, codec thread: FLAC 19.1 -> 2.15 wakes/s, MP3 19.1 -> 2.3, hi-res FLAC 2.2, crossfade 2.1. On the device the dark codec thread was 44/s plus `codec cop` 38/s (§1A of the P19 brief); with the decode on the CPU the call traffic and the COP thread go, and D leaves ~2/s [estimate until M-2]. The COP decode ("2nd core") and the screen rule (`apps/codec_place_core.c`, `tests/codecplace/`) remain only as developer A/B modes for M-2. Developer rows: "Codec core" (CPU / A/B screen / A/B 2nd core; next codec load) and "Codec full wait" (watermark / poll 20/s), kept across restarts as marker files.

## PP5022 band governor (G1, `ppgov-impl`, 2026-10-25; off by default)

`docs/design/pp-governor.md`; the policy in `firmware/pgov_core.c`, the glue in `firmware/pgov.c`. **Off unless the marker file `pgov_on` is in the system folder** (read at boot by `clockpol_init()`); off, the clock follows today's rules (24 / 30 / 80 MHz, `clockpol`, the holders) through the same code. On: the CPU's tick samples both cores' idle time (stamped in `core_sleep()`) every 10 ms, the band follows the measured need (band 0 = 24 MHz with the PLL off, lit or dark; band 2 = 30/48/60/80 MHz, proportional), the holders are 30 MHz floors, `cpu_boost()` means 80 MHz now and a release steps down after the dwell; the power thread applies a change. No voltage change and no 100 MHz in G1 (`STRAP_OPT_A`'s grade is read and logged: `gov boot grade=…`).

- **Size** (`fw-ui-mod`, against the same tree without `HAVE_PP_GOV`): `.text`+`.rodata` **+3,822 B** (budget ≤ 4 KB), statics **+114 B** (budget ≤ 256 B; `core` 40, `st` 36, the idle words 16), `.iram` **+160 B** (`set_cpu_frequency()`'s 48/60 MHz cases and the two stamps in `core_sleep()`, both IRAM functions already), runtime RAM 0, no new thread, no new steady wake (the tick task runs in the existing tick; the power thread is kicked only on a decision change: ~0.03 a second in the simulator's dark FLAC).
- **Logs** (`ipodui.log`, tag `gov`): `boot grade= max= strap= chip= on=`; `band=B/MHz from= why=load|sat|floor|boost|dwell|cap util=%` on each change (ui_log folds repeats within 1 s); `sum at= t= b0= b1= b2= b3= vlow=` (‰ of time per band) and `tr up= dn= boost= sat=` with every 5-minute `clk stats` line.
- **Simulator** (synthetic traces, energy proxy [estimate]; `docs/design/pp-governor.md` §5.4): the G1 configuration's day mix 0.995 of today's rules, lit Now Playing −16 %, lit browsing −11 %, heavy formats +5–11 %; no misses.
- **Device checks pending** (nothing here has run on silicon): (1) 48 and 60 MHz have never run on this unit (Apple's recipe, the 80 MHz sequence); (2) ATA UDMA and the BCM2722 host port at 48/60 MHz (between the 30 and 80 MHz they run at today) [hypothesis: fine]; (3) the lit screen at 24 MHz with the governor's own up-moves instead of the 30 MHz hold; (4) the tick's per-core sampling on silicon (the COP's idle word, uncached). **Procedure:** put an empty `pgov_on` in the system folder, reboot; use the unit normally for a day (lit browsing, a dark album, an AAC track, a library scan); then send `ipodui.log*`. Pass: `gov boot` logged; `gov band=` lines with 48/60 present and no new `pcm underrun` or `panic` lines; the `gov sum` lines show b0 ≥ 900 ‰ in dark FLAC stretches. Remove the marker to return to today's behaviour.

### Stage 2 (`p19-pgov2`, 2026-10-26; developer builds only, off by default)

`docs/design/pp-governor.md` §16. Markers in the system folder, each on top of `pgov_on`: **`pgov2_on`** runs the stage-2 policy as a shadow (band 0/1 at `DCDC1 0xEB`, band 3 at 100 MHz where `STRAP_OPT_A`'s grade is 0 or 1; logged as `gov s2 …`, nothing applied); **`pgov2_apply`** applies it (refused while the UI split is `cop`). ## Rundowns and A/B tests (developer power log, #10)
There is no current sensing on this hardware, so the log records what exists: voltage and level, charger state, and how much of each interval the CPU was boosted, the backlight lit, the LCD awake and the disk active. A test compares two runs by voltage drop over the same time with those shares held equal. Developer builds only (`HAVE_IPOD_UI_DEVMODE`; `--ipodui-release` and stock have none of it).

**Switch:** About, hold SELECT + PREV for 3 s, then the Developer list's last two rows. "Power log: on/off" starts and stops it. "Power log every: N s" steps 30 → 60 → 5 s (default 30 s for a rundown, 5 s for an A/B). While on, `/.rockbox/power.cfg` holds the interval, and the log resumes at the next boot with a `boot <date>` row, so a rundown survives a restart or a crash. Off removes the file.

**File:** `/.rockbox/power.csv`, appended, rotated once to `power.csv.1` past 4 MB (remove the old `.1`, then rename; a row is ~120 B, so about 4.8 days at 30 s: one file holds a whole rundown). The files are pulled and cleared with each backup. Columns:

| Column | Meaning |
|---|---|
| `s` | seconds since boot (resets at each boot: look for the `boot` row) |
| `mv`, `pct` | `battery_voltage()` (mV, averaged by powermgmt) and `battery_level()` (−1 unknown) |
| `charger`, `charging` | 0/1 each |
| `play` | 0 stopped, 1 playing, 2 paused |
| `boost_pct`, `bl_pct`, `lcd_pct`, `disk_pct` | % of the interval's 4 Hz sub-samples with the CPU boosted, the backlight lit, the LCD awake, the disk active |
| `dac_allow`, `dac_sb` | the developer "DAC standby" switch; the codec in standby now |
| `dac_sleeps`, `dac_wakes` | cumulative standby counts (wrap at 65536) |
| `vol_db` | volume, dB |
| `dropped` | rows lost before this one (ring overflow; should stay 0) |
| `mark` | empty for a periodic row; else the mark: `on <date>`, `boot <date>`, `every=Ns`, `off`, `usb`, `poweroff`, or a test's `powerlog_mark()` tag |
| `idle_pct`, `cop_idle_pct` | Fit-1 M0: % of the interval the CPU (COP) core slept in `core_sleep()`; -1 in a mark row or the simulator |
| `cpu1`, `cpu1_pct`, `cpu2`, `cpu2_pct` | the two threads with the most CPU time in the interval, and their % of it (interrupts count to whatever ran under them) |
| `disk_cmds`, `disk_kb` | ATA commands issued and KB moved in the interval (saturate at 65535) |
| `disk_wakes`, `disk_by` | commands that found the disk asleep, and the thread that issued the most commands |
| `stor_on_pct`, `stor_ons`, `stor_ons_total` | #114: share of the interval the storage adapter had power (on or standby), its power-ons in the interval, and since boot (saturates at 65535). `ipodui.log` adds `stor pwr on/off ms= reason=` per change and an hourly `stor pwr hour span_s= cycles= wasted= on_pct= allow=` |

The M0 columns come **after** `mark`, so the first 17 column numbers are unchanged (old `awk -F,` lines keep working); a parser that reads `mark` as "the rest of the line" must stop at its comma (tags never contain one). Counters come from `firmware/export/devstats.h` (developer builds only).

A mark row is written when the mark is made, with the shares so far; the interval's own row still comes on time. Test code (an A/B harness, the BCM offload phases) calls `powerlog_mark("tag")` from `apps/ipodui/powerlog.h`, any CPU-core thread.

**Cost and disk:** a 4 Hz timeout only while on (the ISR writes RAM); a 7,116 B ring of 192 36-byte rows (6,348 B before #114, 4,044 B before Fit-1 M0) (96 min at 30 s, 16 min at 5 s), a pinned `core_alloc` made when the log goes on and freed when it goes off (a static until 2026-10-18; switched on during playback by the developer row, the 6 KB comes from the audio buffer until the next rebuild of it). The ring goes to the file at storage idle, when the disk spins anyway, once a mark is pending, the ring is 3/4 full or 5 min have passed; also at USB connect and clean shutdown. At the low-battery shutoff only on the flash variant: there `clean_shutdown()` runs `system_flush()` below disk-safe too (`apps/misc.c`, the `batt_safe` guard is `HAVE_DISK_STORAGE` only), so the log's last rows go out; the hdd variant skips the flush below disk-safe and loses them. Only when the disk has stayed asleep until the ring is 7/8 full does the shell wake it for one write (`ipodui.log`: `power log forced write n=`). Expect that at 5 s with the screen off and a long buffer: every ~14 min, a few hundred ms of disk.

**M0 log lines** (`ipodui.log`, developer builds, log on or off; RAM until the next storage-idle flush, at most a minute late):
- `m0 tap2pcm ms=M why=play|skip|seek|resume`: a playback request to the playback channel's first PCM (after the DAC wake).
- `m0 disk wake by=T rd|wr n=S play=P t=S`: a command that found the disk asleep, by thread (at most 4 a main-loop pass, then `m0 disk wakes more=N`). Stopped and dark, expect none but the log flushes; anything else is what keeps the flash awake (C1).
- `m0 disk sleeps=N fails=F resets=R irq=I[ polling]`: on a change of F, R or the interrupt mode. F > 0: the adapter refused standby (it then reads as "active"); R: failed commands retried; `polling`: C4b's interrupt was not seen and the driver went back to polling.
- `db scan ms= n=[ cut]` / `db commit ms= ok= n= b=`: the database timings (` cut`: a scan USB cut short; `b`: boosted) that calibrate the simulator's x200-400 factor.
- `udma ...`: the C7 experiment (`docs/fit1-brief.md` A.6).

**USB-C meter calibration (optional, owner):** an inline USB-C meter between the charger and the iPod reads charger current, not battery drain, so take **differences between states** with the battery full (charging current near 0, `charging` = 0 in the log). Hold each state 2 min and add a `powerlog_mark` or note the time: screen lit vs off (Hold); stopped vs playing (dark); Developer › boost (80 MHz) vs not; a USB copy (disk active) vs idle (standby, `disk_pct` 0); with a video build, BCM on vs off. Write the mA per state next to the log's rows; they replace `BC_BUSY_W` and the estimates in `docs/hardware-fit-audit.md`.

**Rundown (P10 battery curve, 3000 mAh):** charge to full and unplug. Set the interval to 30 s, switch the log on, add a `powerlog_mark` or just note the time, start the fixed playlist at a fixed volume, Hold on, screen off, and leave it until it shuts off. Copy `power.csv` off over USB (the `usb` row marks the end of discharge). The `mv` vs time curve sets the large-cell table (`percent_to_volt_discharge`) and the flash disk-safe floor (§3.6.4 of the Phase 9 brief).

**A/B (30 min each, same unit):** charge to the same starting voltage (within 20 mV) or run both halves from the same level band, as the curve is flattest at 40–80 %. Set 5 s. Run A for 30 min, change one thing (DAC standby off, LCD sleep, an offload phase), run B for 30 min, with the playlist, volume, Hold and backlight unchanged. Compare `mv` drop per hour between the marks with `bl_pct`, `boost_pct` and `disk_pct` matched; repeat A after B, because voltage sag is not linear in time. Each 30-min half gives ~360 rows; a half with the screen lit or a forced write in it is suspect.
