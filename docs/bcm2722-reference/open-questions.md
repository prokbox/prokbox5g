# 15. Open questions

Ordered roughly by how much they block someone programming the chip. Each says what is known, and how it could be settled.

## Highest impact

0. ~~Two kernels the alignment rules don't explain.~~ Answered by `quirks.md` #18 (`vstr` line) and #19 (scalar r7); every decoder kernel now passes vc2sim under the silicon readings (dev26), pending a device confirmation.
0b. *(was 0)* **Two kernels the alignment rules don't explain.** The luma and chroma loop filters left some edges unfiltered on silicon (chip output = source) where vc2sim filters, and intra 16×16's plane mode differs by 1–3 levels (S22 dumps, `selftest1.bin` tests 7, 8 and 3). On the loop filters' vertical edge the chip's p side matches vc2sim while its q side (the columns right of the edge) is left as the source: a store of those columns is lost, not a decision. Intra 16×16's plane mode differs by 1–3 levels (rounding or a ramp operand). Until settled, the image runs them in C (`h264_dsp.h` `H264_BAD_*`). *Settle:* fit those dumps against vc2sim with candidate flag/predicate semantics (`vbitplanes`/`setf`/`ifnz`, `vdist` compares).
1. **Which other vector forms differ from the model.** *Progress:* the loop filter's seven start-up forms (`BSL1`, `BSF1`, `BSM1`, `BSR1`, `BSX1`, `BSS1`, `BSZ1`) all agree with the C on silicon [silicon] sitting 4 (2026-10-26, session log `jvpu: forms … (vpu2 ff)`; `quirks.md` #51), so they come off this list. Forms the kernels use that no session has checked one by one are still [hypothesis]: `vst8`/`vst8v` layouts, `vasr.1`, `vmax.1`/`vmin.1`, `vmulhr.0`, `vmulm.1`, `vadd.2` (80-bit), and the transposed `.1.t` operands. *Settle:* a bench pass that runs each against its scalar model and logs any difference.
2. **`vst8` and `vst8v` store layouts**, and the store's t5 block bits. *Settle:* store-locating tests as for `vst16` (`isa-vector.md`). **Partly answered** [silicon] sitting 2: an aligned `vst8` of row 0 stores at its address in the modelled layout (ALGN VS80); `vst8v` and the t5 bits are still open.

## Host interface and protocols

24. **The bootstrap bytes** (`A1 81 91 02 12 22 72 62`) and the BCM boot ROM: what they configure; whether other bootstrap modes exist.
25. **Why two banks.** What the ALT bank is for after the bootstrap, and whether its address space differs from the main bank's. **Partly answered** (`brief-map-power.md` §7) [apple]:
    - Apple's driver keeps one lock per bank and takes full 32-bit addresses on both, so the space is the same.
    - It sends the display's bulk pixel writes on the ALT bank and everything else on the main bank: two software channels, as the brief says.
    - Still open on silicon: whether the latches are independent, and whether the ALT bank needs the write-ready wait (Apple doesn't wait). Stage PW7.
26. **Reconciling Apple's transport descriptions.** From the BCM side `vmcs.bin` stores a host-interface block address at `0x1FC` and uses offsets +16/+17/+32/+33 within per-channel blocks; from the ARM side (siggifly) `0x1F8` must read 1 and `0x1FC` points at an 8-slot directory of 0x50-byte ring records with 16-byte pointer blocks. These are probably the same structure seen from two ends, but no one has matched them field by field. Also: which side writes the `1` at `0x1F8`.
27. **The NOR `vmcs`** command set beyond Rockbox's: commands `0x13` and `0xA` (issued by the boot ROM), word 0 of `LCD_UPDATERECT`'s header (`0x34`), and the TV commands.
28. **The BCM → host interrupt** (GPIO 23 → host GPIO C bit 6) on silicon.
29. **A first-NAL refusal on one file** [hypothesis]. S28: our image refused the very first NAL (the SPS) of a 118 MB episode with `HP_E_UNSUPPORTED`, while a file with a byte-identical avcC played; host decoder, demuxer and vc2sim all take the stream. Either bytes changed between the file and the chip's FIFO for that file only (the audio buffer's peek, or the port under a large first packet), or the chip's state differs. Since S28 the port has read back right every time (S30: the first packet's bytes in the FIFO equal the host's), which weighs against the first. dev32's guard words 48–55 record the refused NAL's bytes and the check (file and line); not yet seen on a refusal (`host-driver.md` §8a; device-session-1.md, session 28).
30. **Sessions started at a file's first sample decode nothing** [hypothesis]. S28 stage 7: 7.5 s with no picture until a seek restarted the session. S29 and S30: every session started at sample 0 took every packet (0 in flight, progress idle) and showed none; S30's counters were 0 decoded and `0x22`/`0x33` errors, about one per packet. These files open with SPS, PPS, a 701-byte x264 SEI, a 239-byte IDR and 7-byte P_Skip pictures, and the first packet's bytes in the FIFO equal the host's (S30). A restart at a later key plays. vc2sim decodes the same start pixel-exact. *Settle:* dev37 records the session's first decode error (check, NAL type and bytes) in guard words 48–55; the check names the decoder path that differs (`host-driver.md` §8b).
31. **A held last frame at a fixed place** [hypothesis]. S30: the chip stopped presenting and the picture froze; the owner saw the freeze at the same point on replays, so it is deterministic. In the same run a stall that a pause and a restart did not cure was cured by leaving and re-entering (a reload); whether that stall was this freeze is not recorded. *Settle:* dev36 reloads by itself after a restart that does not move the picture, and logs the chip's report first; the progress word and the first decode error at that point (dev37) locate it; replaying that stretch in vc2sim from the same key compares the two.
32. **Packets consumed slowly or not at all while the chip is alive** [hypothesis]. S30: 16 records in flight, 14 queued, 18 decoded, heartbeat and `STATUS` answering, the progress word inside a macroblock (`0x3100_0048`); grey (concealed) pictures elsewhere in the same run, cleared by the next IDR. Whether the decoder loops, waits or runs very slowly on some macroblock is not known. *Settle:* two progress snapshots a known time apart (the macroblock address and the packet count) and the chip's clock word (dev37's still report).
33. **What a reload clears that a restart does not.** A restart (`CLOSE` + `OPEN`) keeps the image's statics, the VRF, the SDRAM set-up and the self-test's once-per-boot state (the clock drops to 27 MHz at `CLOSE` and goes back up at `OPEN`); a power cut clears all of them. S30's stalls cured only by a reload say one of these carries a fault forward [hypothesis]. *Settle:* restart variants that reset one piece each (the VRF, SDRAM, the decoder's arena, the image's statics), run at a known stall point.

## Audio (`audio.md`)

34. **Where GPIO 1–3 go.** To the WM8758's audio interface beside the PP5022's I²S (the reading in `audio.md` §5), to a TV/line path, or nowhere. *Settle:* with the pins as inputs, sample `0x10002820` in a core loop while the host plays a tone; count edges per pin against the 1 MHz counter (a frame clock reads fs, a bit clock 32–64 × fs). Read only; nothing driven.
35. **Whether the data line can be driven safely.** The candidate is GPIO 1. It showed no edges while the PP played (S32), and Apple parks it as a driven output after every video, so it is probably on a net of its own, not the PP's data line (`audio.md` §5) [hypothesis]. No register is known that puts the PP5022's I²S data pin into high-Z (`audio-spike.md` §8). *Settle:* GPIO 1 as an input, pull-up then pull-down (`+0x60`–`+0x68`), read its level with the PP's audio off, playing, and stopped (`TXFIFOEN` clear, codec clocks running). A floating net follows the pull in all three. Only then drive it (stage 8a-1).
36. **The block's clock.** Whether `0x10004800` needs Apple's two clock-manager clocks (24.576 MHz and 2.048 MHz, ids 2 and 3) and which registers those are; what bit 23 of `+0x00` means. **Partly answered (S35, S36c):** without the clock-manager clocks, bit 23 set with GPIO 2/3 on function 2 and the codec awake (S35) and never with them as inputs (S36c), so bit 23 most likely means "the external clocks are seen" and the block is a clock slave (`audio.md` §5, "Clock direction") [hypothesis, strong]. **Further (2026-10-23):** Apple's clock manager maps id 2 to `0x1000_1C34` and id 3 to `0x1000_1C38` (its id → register switch @5334; `brief-map-peripherals.md` §4.2) [apple]. *Still open:* what those two clocks feed (perhaps the FIFO/DMA side, or a master mode Apple never uses). *Settle:* dev45's 8a-1 with the codec awake: bit 23 with clocks seen, and the edge counts in the reply. **From the power map:** Apple's ids 2 and 3 are the clock words `0x1000_1C34` and `0x1000_1C38`, both fed from PLL C (`brief-map-power.md` §5) [apple]. *Still open:* what Apple's ids 2 and 3 feed (perhaps the FIFO/DMA side, or a master mode Apple never uses). *Settle:* dev45's 8a-1 with the codec awake: bit 23 with clocks seen, and the edge counts in the reply.
37. **Control bits.** What `0x6001`, `0x6209`, `+0x10 = 1` and the `+0x14` divider select (word length, format, channel order). Apple writes nothing else to the block, so no master/slave bit is set anywhere (`audio.md` §5) [apple]. *Settle:* dev45's four sample layouts with the owner's verdict per tone; then the start bits (`HP_OP_TONE`'s optional sixth word, subsets of `0x6209`) one at a time.
38. **DMA channel 5 details.** The length unit (bytes, by Apple's 16-byte silence block), and what `+0x20`, `+0x24` and `+0x2C[23:0]` report. *Settle:* log them while a known-length chain plays.
39. **Where GPIO 1's net goes.** If it is the BCM's own data output, something outside both chips merges it with the PP's data before the WM8758's single DACDAT input: a selector set by a PP GPIO, a gate (both outputs idle low), or the PP's I²S input (the WM8758's ADCDAT net). *Settle:* the pull test of #35. If the net floats, play 8a-1's tone and listen: silence means a selector must be set. Then look for a PP GPIO that `osos` changes around `audio_enable 1`, statically through the player manager (`0x1017_7814`), or on Apple's firmware by reading the PP's `GPIOx_INPUT_VAL`.
40. **What the PP5022's I²S data pin does when the transmitter stops.** It could drive low, drive the last bit, or float. The same goes for the block in reset (`DEV_RS` bit 11), with its clock gated (`DEV_EN` bit 11), and with `DEV_INIT2` bit 8 set (the "I2S pin group" bit both firmwares clear; Apple never sets it). Rockbox's stop leaves `TXFIFOEN` set. It matters only if #35 finds the line shared. *Settle:* the #35 pull test, repeated under each of these PP states.

## Memory access (`memory-access.md`)

41. **Does the PP's DMA deliver anything through the port?** S8's lab timed it into the SRAM host frame (27.6 ms a frame unboosted, 10.4 ms boosted) and read back clean, but the CPU methods had just written the same bytes there, so that readback cannot tell a transfer from none. Into the SDRAM FIFO it went from partly wrong (S32: first word missing, later words shifted) to nothing at all (S34: every size from 256 B to 32 KB, every word wrong but a CPU-rewritten word 0). Whether the engine's writes reach the port at all, reach it at a shifted address, or reach only SRAM is unknown. **S35 ran that lab into SRAM and SDRAM with a unique pattern: nothing landed in either**, at any size (`session 35 bcmtest.log`), so the target memory is not the cause. *Settle:* the PP's DMA memory → memory first (does the engine write anything at all), then into the port at width 16, with a request line, and through the PP's second engine (`../data-paths.md` DP-2; PP `open-questions.md` #12, #30, #11).
42. **What is at and above `0x0014_0000`.** No session has read past the end of SRAM, and no source reports an alias or a fault there. *Settle:* from the core, write a unique word at a free SRAM address and read the same offset + `0x14_0000`, `0x20_0000` and `0x100_0000`, with an exception handler armed; then the same reads from the host.
43. **The port's finer rules.** A write starting at 2 mod 4 lands 2 bytes low (bits 1:0 ignored) [silicon, inferred] CR1 2026-10-25 (`memory-access.md` §11.4, #70). Whether a lone 16-bit write to `DATA` commits by itself: **no** [silicon] sitting 2 (ALGN PLH1, PLH3, PLH5: the unpaired last halfword is dropped; `quirks.md` #35); whether `DATA` reads auto-increment after one `RD_ADDR` (our port sets the address per word); whether the ALT bank reaches the same address space (#25); whether the host can use `0xFE00_0000` or the core `0xC000_0000`; whether the host's `0xC040_0000` aliases SDRAM. *Settle:* one lab pass of host writes and reads against a pattern the image lays down and reports.
44. **Does port traffic slow the chip?** Host writes land while the core decodes (S12) with no visible arbitration; whether they steal SRAM or SDRAM cycles from the core, the vector unit or the LCD DMA is unknown. *Settle:* a timing kernel on the core, alone and while the host streams a full frame, at both clocks.

45. **Byte and halfword stores into SDRAM.** Word accesses to SDRAM are right from the core, the vector unit and the host (S11, S12), and byte stores are right in SRAM (S17). No session has checked an `stb` or `sth` that lands in SDRAM: whether the controller masks the other byte lanes, writes the byte replicated, or does a read-modify-write that can race with the host. S35's stage 9 failed as if bytes went wrong: the AAC decoder keeps its channel elements in SDRAM (`.sdbss`) and writes their flags by byte stores. AU 0 was refused with libfaad error 1 (a gain-control flag read as set), AU 1 decoded wrong, and AU 2 was refused with error 12; the same clip is bit-exact in vc2sim. *Settle:* dev42's `HP_AAC_MEMPROBE` (stage 9 runs it after the video `OPEN`). It fills 16 bytes by words, stores `0x11` at +1, `0x22` at +6, `0x3344` at +8 and `0x5566` at +14, then reads back by words and by `ldb`/`ldh`, in SRAM and at SDRAM offset `0x39FFF0`. The host also reads the SDRAM words over the port. Right lanes read `A5A511A5 A522A5A5 A5A53344 5566A5A5`, bytes `33442211` (`memory-access.md` §3). **Answered for that pattern** [silicon] S36c: right in SRAM and SDRAM, at both clocks, and the host read the same words. The narrower question is #46.
46. **Why the AAC decoder still fails on the chip.** S36c, stage 9: the tables were the same as the image file (`1fa225f3` three ways), memprobe was right, every AU read back right, and OPEN was right. Yet 155 of 200 AUs were refused at 150 MHz and 142 at 27 MHz, and the rest decoded wrong. The refusals **differ between runs**: AU 0 failed with libfaad error 1 at 150 MHz and error 17 at 27 MHz; then AUs 1–3 failed with error 1 in one run, and with error 12 (after a wrong AU 1) in the other. A fixed instruction-semantics difference would fail the same way every time. **Ruled out in vc2sim** [ours, 2026-10-15]:
    - The device's own flow (its image defines, a fresh boot, rotating slots, aac9's 200 AUs) is bit-exact, with SRAM and SDRAM filled from five different seeds.
    - Each candidate semantics flipped alone fails differently from the chip: `ldsb (rs+ri)` zero-extending, `mulhd.ss` as unsigned or low word, and register shifts of 32 unmasked (the decoder runs `asr` by 32 about 1,024 times per channel per AU, with no effect on the output).
    - The 32-bit `ldh rd, (rs+off)` with the offset ≡ 2 mod 4, which `aac_memcpy`'s halfword path uses to copy the second `ic_stream`, cannot be wrong: the H.264 decoder uses the same form in `h264_mv_pred`, `h264_residual` and `h264_finish_picture`, and decodes bit-exact on silicon.

    What the AAC decoder does and H.264 does not: it keeps 40 KB of channel state in SDRAM (`sce`/`cpe`, `.sdbss`) and writes it with scalar byte and halfword stores, then reads it back at once [hypothesis: a store followed at once by a load of the same SDRAM word can return stale data, depending on timing; memprobe's stores were all done before its loads]. *Settle:* the next build's stage 9 adds three things:
    - `HP_AAC_MEMSTRESS`: word, byte and halfword stores each followed at once by a load, a byte or halfword stored into a word and then the word read, and `aac_memcpy`'s halfword copy and `aac_memset`, over 4 KB of SDRAM (`0x39E000`) and 512 B of SRAM as the control.
    - `HP_AAC_STATE`: libfaad's parse checkpoints after every AU. `bcmfw/aac/test/aac_dev_sim.py --diff bcmtest.log` names the first checkpoint where the chip leaves vc2sim, and every AU checks that the second `ic_stream` hashes the same as the first.
    - A third run with `AAC_FLAG_BYTE_COPY` (the decoder's copies and clears a byte at a time).

47. **Does the BCM's clock or the target memory set the port's write rate?** Into SRAM with the BCM at 27 MHz the rate followed the PP's clock (S8). Into SDRAM during video, with the PP at 80 MHz, the CPU copy measured 17–18 MB/s with the BCM at 150 MHz and 10–12 MB/s at 27 MHz (S33, S34). *Settle:* at a pinned PP clock, write a frame into SRAM and into SDRAM at BCM 27 and 150 MHz, with the decoder idle and busy (`../data-paths.md` DP-1).
48. **Does COP decoding on the PP stop or delay the WM8758's clocks?** With the PP's COP decode switch on, a video's soundtrack never started (S36c) and stage 8a-0 saw no clocks on GPIO 2/3; that shows PCM did not run, not that the COP stops the clocks. *Settle:* 8a-0's probe during **music** played with COP decode on and elapsed confirmed moving (`../data-paths.md` DP-3; `docs/fit2-brief.md` §12.1 on branch `wheel-touch`).
49. **Panel standby without a reset** [ours; hypothesis]. Every wake today runs the full power-on: reset pulse, 110 ms, bus resync, scripts, about 265 ms on panel 3 [measured]. With GPIO 48 kept high through the dark spell, our wake skips the reset part. Two depths are built:
    - *light*: display off only, the power circuits left on; the wake is the display-on ramp (17 + 34 + 85 ms of waits on panel 3);
    - *deep*: the whole off script; the wake is the init and on scripts.
    Unknown on silicon: whether the panel comes back with the right picture and gamma, the real wake time, and each depth's standby current. In vc2sim both wakes take about 137 ms against 267 ms cold. Panels 1 and 2 have no light depth. *Settle:* stage 5s (looks after each wake, the image's own power-on timing, the meter phases).
50. **SRAM while the core sleeps with the BCM powered.** [measured]: a power cut loses everything (`memory-access.md`). Nothing has been measured below a cut. Expected to hold [hypothesis: on-chip static RAM with the supply up]. If it holds, a wake needs no frame upload. *Settle:* stage 5i reads the whole framebuffer back after its minute asleep; stage 5s does the same after every standby.
51. **The boot upload by the PP's second DMA engine at address 0.** [measured, S37]: engine 2 lands every word in BCM SRAM while the BCM is held after its bootstrap, but only in the `0xE0000` window and one piece at a time. Apple uploads its image this way [apple-RE]. Not yet run: a real image at 0 in back-to-back 64 KB pieces, each re-sending its address, then the start. *Settle:* stage 5s uploads a 192 KB block (the image, then a filler) by CPU and by engine 2 in turn, reads every word back before the start, then starts it and shows a frame.
52. **Answered** [silicon] stage 3d, 2026-10-26: GPIO 49 toggles on our panel, period 14,740 µs (67.8 Hz, 14,738–14,744), a 58 µs pulse; a present on every 2nd edge ran the walk at 33.9 fps with 0 late frames (`research/bcm2722/render3d.md`, "On silicon"). The original question: **The tearing-effect signal on silicon** (`graphics.md` §5; now measured by stage 3d's TE probe, and Apple's handling read: `lcd.md`, "Tearing"). Apple waits for the panel's TE edge on GPIO 49 (interrupt source 11, which also measures the frame period) [apple]. Our images push without waiting, and nothing tore visibly in UI use [silicon S7, by eye], but a full-motion game or Cover Flow sweeps the whole screen every frame. Unknown: whether GPIO 49 toggles on our panels, the panel's refresh period, and whether a 14.26 ms push started at the edge stays behind the scan. *Settle:* a bench image that timestamps 64 GPIO 49 edges with the 1 MHz counter, then pushes a moving bar synced to the edge and unsynced, photographed.
53. **A panel push straight from any source and pitch** (`graphics.md` §2). `UPDATERECT` pushes a rectangle of our framebuffer by DMA [silicon S4 onward]. The drift and a compositor would rather push a window of a texture (another base address, a 600-byte pitch) with no copy. The DMA engine's 2-D mode suggests it works [hypothesis]; no image has done it. *Settle:* push a 160×240 window out of a 300×300 picture at an odd row offset, and read the panel back or photograph it.
54. **Per-pixel scalar fetches from SRAM and SDRAM** (`graphics.md` §3). *First figure* [silicon] stage 3d, 2026-10-26: the textured span costs 25–74 cycles a pixel in SRAM including span set-up, against a 14-instruction loop (two dependent loads); the isolated per-fetch cost is still B6's to measure. An affine layer or a textured span fetches one texel per pixel at a computed address; the vector unit has no known gather. The cost per fetch (cache hit, SRAM miss, SDRAM miss) sets the affine and 3D budgets, which are guesses until then (about 10 cycles a pixel assumed). *Settle:* a timing kernel over 64 K random addresses in SRAM and in SDRAM, at 27 and 150 MHz.
55. **Answered** [silicon] stage 3d, 2026-10-26: every check frame equals vc2sim's at 27 and 150 MHz (ten frames, 100 s of rendering with the LCD DMA running); the cost is 1.14–1.64 × the simulator estimate and scales exactly with the core clock (`research/bcm2722/render3d.md`, "On silicon"). The original question: **A large scalar C program at 150 MHz under sustained load** (stage 3d, `research/bcm2722/render3d.md`). The 3D render test is our second big body of C on the chip after the video decoder. It renders 10 s scenes back to back with the LCD DMA running in parallel, and uses 64-bit divides and multiplies in triangle set-up. Unknown on silicon:
    - whether its frames come out bit-exact with vc2sim;
    - its real cost per pixel against the simulator's instruction counts (a 14-instruction pixel loop, 1.03 cycles each, no memory stalls modelled);
    - whether the panel DMA reading the other framebuffer slows the core (#44).

    *Settle:* stage 3d. Two checksummed frames per scene against `bcm-devtest-r3d.h`, plus each run's setup/raster split and frame times.

## From the product brief (2722-PB01-R, re-read 2026-10-23)

56. **Bus bypass mode.** The brief: "Bypass mode allows host access to memory-mapped peripherals with BCM2722 in power-down", a "power-efficient bypass mode", and "Bus Bypass Mode" between the host interface and the display controller and secondary memory interface in its block diagram [external].
    - If the PP can reach the LCD through the BCM while the BCM is powered down, a lit, idle UI could run with the chip off. That's a new power state below today's lit floor (`power.md`; P19 bench row B9's question asked from the other side).
    - **Read 2026-10-23** (`brief-map-power.md` §8): Apple never uses it. `osos` reaches the panel only through the BCM's port, and `vmcs.bin` writes no register that could enter it [apple]. The one unexplained BCM control line is `GPO32` bit 15, which Apple raises before cutting bit 14 in its hibernate sequence (#57). How bypass is entered here is unknown. The candidates are that pin, automatic entry in power-down, or a bootstrap setting (#24) [hypothesis].
    - *Settle:* stage PW6 (`brief-map-power.md` §9), after PW5. It parks the chip with the panel expecting pixels, then writes 256 × `0x0000` to `DATA`/`ALT_DATA` in the cut state and in Apple's retain state. A black square on white means bypass. Owner's go for each powered-down variant.
57. **Sleep and hibernate.** The brief lists four power modes: run, sleep, hibernate, power-down. It gives a 0.6 V core in hibernation, against 0.8–1.2 V running [external].
    - We use run, the core's `sleep` instruction (stage 5i) and power-down (the cut).
    - **Mapped 2026-10-23** (`brief-map-power.md` §2–§3) [apple]:
      - **Run:** Apple scales the clock (5–150 MHz) and the regulator level with load.
      - **Sleep:** the RTOS's `ei; sleep; di`.
      - **Hibernate:** the gencmd `power_control videocore=1` parks the chip. It moves the core to the crystal, zeroes the PLLs, clears the GPIO event enables, moves its stack to SRAM, idles SDRAM, writes `0x1F0 = 0xA5A5_0000` and busy-polls. The host then sets `GPO32` bit 15, waits 5 ms and clears bit 14. Waking reverses the pins, then the host writes `0xA5A5_0001` and the chip answers `0xA5A5_0002` after restoring its clocks and SDRAM.
      - **Power-down:** `videocore=0`, then both pins low.
    - Apple's wake path continues the parked loop, so it expects SRAM and the registers to survive bit 14 low with bit 15 high [apple]. Bit 15 is most likely the hibernate (retention) request [hypothesis].
    - No register write selects 0.6 V.
    - Nothing in `osos` 1.3 calls the hibernate path statically.
    - *Settle:* stage PW5, Apple's sequence with SRAM and SDRAM CRCs and the key read of `0x1F0` after the wake. Owner's go: it drives `GPO32` bit 15, which Rockbox never has.
58. **A scaler in the display controller.** The brief: "Scalable image output with pixel level interpolation", "up to 24-bit internal precision", and "configurable refresh rate" [external].
    - Our video path scales in software on the vector unit (2:1 box), and `graphics.md` assumes no fixed-function graphics.
    - If the LCD interface can scale while it pushes, video and photo scaling would cost no core time [hypothesis].
    - *Settle:* look in Apple's code for writes to the LCD block (`0x10004000` on) beyond the known run and format words (`lcd.md`). Then a device check that pushes a smaller rectangle with any such bits set.
    - **Answered for the LCD (2026-10-23)** [apple]: Apple's code writes nothing in the LCD block beyond the control, run length, run format (`0x1F` from the panel record), FIFO, chip select 0 timing words, index and data (`lcd.md` §1; `brief-map-peripherals.md` §3). No scaler, depth or refresh bits are ever set. The scaling claim most likely belongs to the TV/RGB timing generator at `0x1000_2C00`, which takes a 640-sample input line and puts out 704 samples: #62.
59. **The caches** (128 Kbit, instruction and data) [external]. Every image of ours runs with them off (`boot-and-clocks.md` §2).
    - Their gain on SDRAM data (video frames, JPEG sources, textures, samples) is unmeasured.
    - **Read 2026-10-23** (`brief-map-power.md` §6): Apple flushes the whole cache at run time only after writing code (relocating a loaded library @88a0, and one library start @91a4). It never flushes for the host-written rings and statics in SRAM, and uses no alias addresses [apple]. Reading [hypothesis]: the caches front SDRAM only, and bit 16 (set once SDRAM is up) enables caching it.
    - *Stage PW2* times loads in SRAM and SDRAM under `0x1000_0C00` = 0, `0x8000_0000` and `0x8001_0000`, and checks coherence both ways with the host.
    - *Settle:* bench row B7's loads timed with the cache off and on (the enable sequence is known from Apple's start-up), with the host's writes flushed first.

## How to settle most of these

A small test image that runs one instruction or register access per check, records the result in SRAM, and is read back by the host has answered every silicon question in this manual so far. Keep each check independent (its own inputs, a fresh fill pattern on its output), place a guard around low SRAM, and compare against a model that is itself checked against Apple's code.
